# 調査指示：サイト内リンクのutm撤去とGA4クリックイベントへの置き換え（現状調査）

作成日：2026-09-25
種別：**調査のみ（コード変更・コミット・push禁止）**
配置：`lifecompass-next/docs/fixes/active/internal-utm-to-ga4-event/investigation.md`
対象リポジトリ：`lifecompass-next`（主）、`freenough-main`（**読み取りのみ**）

---

## 背景

`www.freenough.com` の中のページ間リンクに、utmパラメータが付いている箇所がある。確認済みのものは、一人法人LPの下部CTA（`utm_source=hojin_lp`）。ほかに、過去の運用ルールで次のパターンも作られている。

- ツールページ → シミュレーター：`utm_source=tools&utm_medium=referral&utm_campaign={tool_name}_tool`
- ブログ記事 → ツール／シミュレーター：`utm_source=blog&utm_medium=referral&utm_campaign={topic}_blog`（`blog_article_template.md` v1.2の命名規則）

サイト内のリンクにutmが付いていると、GA4では、そのクリックの時点で流入元がutmの値に置き換わる。その結果、本来の集客経路（検索・X・noteなど）が見えなくなる。このため、**サイト内リンクのutmはすべてやめ、ブログ一覧の `blog_cta_click` と同じ方式のGA4クリックイベントで計測する**方針とする。

今回は、その実装方針を決めるための現状調査だけを行う。

**方針の範囲外（今回撤去しないもの）**：外部サイトから `www.freenough.com` へ入ってくるリンクのutm（note.comの記事内リンク `utm_source=note…`、Xのプロフィールリンクなど）。これらは正しい使い方なので、そのまま残す。

## 開始時の状態と作業ルール

- 開始時、`lifecompass-next` は `main` で、未追跡ファイルは本指示書（とこのフォルダ）だけのはず。違う場合は、何も触らずに `git status` を報告して止まること
- `freenough-main` は `git status` と現在のブランチを報告するだけ。ブランチの作成・切り替え、ファイルの変更は一切しない。パスが分からなければ、作業前にKENZOに確認する
- 本調査で作ってよいファイルは、このフォルダ内の `report.md` と、調査用の一時スクリプト・スクリーンショットだけ。**リポジトリ内の既存ファイルは変更しない**
- コミット・pushはしない
- 検証中は、GA4・AdSenseへの通信を遮断する（`google-analytics.com`・`googletagmanager.com`・`googlesyndication.com` など）
- `tsconfig.tsbuildinfo` が書き換わったら、元に戻す
- `localStorage.clear()` などの破壊的な操作をする場合は、事前に、対象のオリジンが検証専用であることを確認・報告する。判別できなければ操作せずにKENZOに確認する
- devサーバーを止める場合は、ポートからPIDを特定して個別に止める。`taskkill /IM node.exe` のような一括終了は使わない。**Claude Codeが起動していないプロセス（KENZOが起動したdevサーバーなど）は止めない**。止める必要があるときはKENZOに依頼する
- 処理が終わっても、`docs/fixes/active/` フォルダ自体は削除しない

## 調査項目

### 1. utmの全件洗い出し（両リポジトリ）

`utm_`・`utm` を含む箇所を、両リポジトリのすべてのファイルから探す。対象は、コード（`.ts`・`.tsx`・`.js`）、記事本文とfrontmatter（`.md`・`.mdx`）、定数ファイル、`scripts/`、`docs/`（`blog_article_template.md` を含む）。`node_modules`・`.next`・`raw-data` は除く。

文字列の直書きだけでなく、**utm付きのURLを組み立てる関数や定数**（例：`URLSearchParams` に `utm_source` を入れる処理、utm文字列を返すヘルパー）も探すこと。

各箇所について、次の表の形で報告する。

| 列 | 内容 |
| --- | --- |
| リポジトリ・ファイル:行 | |
| 種別 | コード／記事本文／frontmatter／定数・ヘルパー／ドキュメント／検証スクリプト |
| リンク元のページ | そのリンクが表示されるページ（分かる範囲で） |
| リンク先 | 相対パス・basePathつきパス・`SITE_URL` などの定数起点、外部URLの別 |
| サイト内か外部か | `www.freenough.com` の中への移動か、外部への移動か |
| utmの値 | source・medium・campaign・contentなど |
| 同じクリックで送っているGA4イベント | あればイベント名とパラメータ。なければ「なし」 |

最後に、件数を「サイト内リンク／外部へのリンク／外部から入ってくる用の文字列（note用の定型文など）／ドキュメントのみ」に分けて集計する。

記事本文にutm付きのリンクが多数ある場合、全件を表に並べる必要はない。記事ごとの件数と、パターン（値の組み合わせ）の一覧でよい。

### 2. 既存のGA4イベントの実装

`blog_cta_click`・`tool_to_simulator_cta_click`・`tool_calculate`、ほかにあればすべてのカスタムイベントについて、次を報告する。

- 送信している場所（ファイル:行）と、呼び出しの経路（共通のヘルパー関数があるか、`window.gtag` を直接呼んでいるか）
- イベント名とパラメータの一覧（パラメータ名・値の例）
- **ページ移動の直前に送るイベントの扱い**：`transport_type: 'beacon'` の指定、`event_callback` を待ってから移動する処理、`next/link` と `<a>` のどちらに付いているか。移動によって送信が失われる可能性がある作りかどうか
- `gtag` が読み込まれていないとき（localhostなど）にエラーにならない作りか
- 両リポジトリで、同じヘルパーや同じ書き方を使っているか。片方にしかない場合はその旨

### 3. gtagの読み込み条件と測定ID

- 両リポジトリで、gtagを読み込む条件（ホスト名の判定など）と、その実装箇所
- **両リポジトリの測定ID（`G-` で始まるID）が同じかどうか**。IDそのものは報告に書かず、「同じ／違う」だけを報告する。環境変数から読んでいる場合は、変数名と、Vercel側の設定を見ないと分からない旨を書く
- `/asset-simulator` 配下（`lifecompass-next`）と、それ以外（`freenough-main`）の間を移動したとき、同じGA4プロパティの中での移動として扱われる構成かどうか（コードから読み取れる範囲でよい）

### 4. utmを受け取って使っている処理

リンク先のページで、utmパラメータを読み取って何かをしている処理があるか（例：`useSearchParams` や `location.search` で `utm_source` を見て表示や動作を変える、localStorageに保存する）。あれば、ファイル:行と内容を報告する。utmを撤去したときに動作が変わる箇所を把握するため。

### 5. 現在のイベント送信の実測（可能な範囲で）

localhostではgtagが読み込まれないため、次の方法で、クリック時に送られるイベントを記録する。

- Playwrightの `addInitScript` で、`window.gtag` と `window.dataLayer` の呼び出しを記録するスタブを入れる（外部への通信は遮断したまま）
- 対象：ブログ一覧のCTA（`blog_cta_click`）、ツールページからシミュレーターへのCTA、一人法人LPの下部CTA
- クリックの直前・直後に記録された呼び出しの内容と、移動先のURL（utmが付いているか）を報告する

コードの作り上、スタブでは記録できない場合（ホスト名の判定で呼び出し自体が行われないなど）は、無理に実測せず、その理由とコード上の呼び出し経路の説明で代える。**判定を回避するためにコードを書き換えることはしない。**

## 報告の形式

- 結果を `docs/fixes/active/internal-utm-to-ga4-event/report.md` にまとめ、チャットにも要点を報告する
- 各項目に、根拠（ファイル:行、grepのコマンドと出力、スクリーンショット、記録したイベントの内容）を付ける。根拠のない「問題なし」「該当なし」は書かない。該当なしの場合は、探したコマンドと、0件だった出力を付ける
- 調査の途中で、方針（サイト内のutmをすべてやめる）の前提が崩れる事実が見つかった場合は、その時点で報告する。例：両リポジトリの測定IDが違う、utmを読んで動作を変えている処理がある
- 実装の提案は書いてよいが、提案と事実ははっきり分けて書く

## KENZOへの確認事項（Claude Codeは対応不要）

コードからは分からないため、KENZOがGA4の管理画面で確認する。

1. **カスタム定義**：`blog_cta_click` などのイベントパラメータが、カスタムディメンションとして登録されているか（管理 → カスタム定義）。登録されていないパラメータは、レポートや探索で使えない
2. **utmに依存しているレポート**：`utm_source=tools`・`blog`・`hojin_lp` で絞り込んでいる探索レポートや、保存したレポートがあるか。あれば、イベントでの計測に移したあと作り直す必要がある
3. **キーイベント**：`tool_to_simulator_cta_click` などをキーイベント（旧コンバージョン）に設定しているか
