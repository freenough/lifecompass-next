# Product Spec:退職後 余剰キャッシュフロー再投資機能

版:確定版(投資調査2回・按分ルール議論を経て確定)

---

## 1. 背景・目的

現行の資産シミュレーター(`simulate.ts`)は、取崩期(退職後)の年間収支が黒字
(収入 > 支出)の場合、その黒字分を運用されない現金として滞留させるだけの
設計になっている。これは、年金等の収入が生活費を上回る退職者が、その黒字を
従来通り運用に回すという現実の行動を表現できていないというギャップである。

本機能は、このギャップを埋めるオプトイン機能として、退職後の黒字を特定口座
(課税口座)で運用継続できるようにする。

---

## 2. スコープ

### 対象

- 取崩期(`isRet`)における年間黒字(`income > expense`)の発生年
- 対象口座:特定口座のみ(本人`tax`・配偶者`spTax`)

### 非対象(意図的に対象外とするもの)

- **NISA・iDeCo**:一切触れない
  - NISAは時価管理のため生涯上限(1,800万円)の判定ができないという既存の
    制約と衝突する余地をなくすため
  - iDeCoは受給開始後の追加拠出が制度上不可能なため
- **現金(cash)**:トグルOFF時の従来動作(黒字は現金として滞留)は変更しない
- **黒字額の一部のみ投資**:金額指定・按分率入力などのUIは追加しない。
  トグルON時は黒字全額が対象
- **取崩戦略(比例取崩・現金優先・課税優先)との連動**:黒字の行き先は
  取崩戦略の選択に関わらず一律で特定口座。取崩戦略は「不足時にどの口座から
  取り崩すか」のみを決定するものとし、黒字処理とは独立に扱う

---

## 3. 型定義・データモデルの変更

```typescript
// SimParams型に追加
interface SimParams {
  // ...既存フィールド
  retirementSurplusReinvest?: boolean; // 既存のmcStdDynamic?等と同じoptionalパターン。デフォルトfalse
}
```

- `profile.ts`側のシリアライズ/デシリアライズに新規フィールドを配線
- デフォルト値`false`により、既存の保存済みプロファイル・URL共有データには
  一切影響がない(フィールド欠落時は`undefined`→falsy評価)

---

## 4. 計算ロジック仕様

### 4.1 黒字時の処理(トグルON時)

取崩期の年間収支計算箇所(`const surplus = income - expense;`付近)において、
`surplus >= 0`かつ`retirementSurplusReinvest === true`の場合:

1. 本人・配偶者それぞれの「その年の収入」を按分比率計算用に再計算する
   (既存の`baseInc`構築ロジックと同じ条件分岐を、本人・配偶者別に分離して
   もう一度計算する。新規の状態変数は持たず、既存パラメータから都度導出する)
2. 按分比率に基づき、`surplus`を本人分・配偶者分に分割する
3. 本人分を`tax`・`taxCostBasis`に、配偶者分を`spTax`・`spTaxCostBasis`に
   それぞれ同額加算する(積立期の拠出処理と同じ2行パターンを流用)
4. 加算は既存のGrowth適用(取崩期の`rR`+ショックによる運用益計算)より後の
   タイミングで行う(年末積立方式と整合。運用益計算のタイミング自体は変更しない)

### 4.2 按分比率の計算式

按分対象となる「収入」は以下の合計とする:

- 給与収入(退職前の本人・配偶者の年間家計入金額。通常、取崩期には該当なし
  だが配偶者が本人より遅く退職するケース等を考慮し含める)
- 年金受給額(本人`penAmt`・配偶者`spPenAmt`。受給条件を満たす年のみ)
- 収入イベント(期間収入・一時収入。`owner`フィールドで本人/配偶者を判別)
- iDeCo年金形式受取の税引後手取り額(本人`idecoAnnualPension - pensionTax`・
  配偶者`spIdecoAnnualPension - spPensionTax`。それぞれ0未満にならないよう
  `Math.max(0, ...)`を適用、既存の`income`加算ロジックと同じ扱い)

按分対象**外**とする収入(黒字判定の`income`を経由しない別経路のため):

- 退職金(`severanceGross`/`spSeveranceGross`)
- iDeCo一時金(退職所得として別途集約課税されるもの)

```
selfShare = selfIncome / (selfIncome + spouseIncome)
spouseShare = spouseIncome / (selfIncome + spouseIncome)

// 両者の収入合計が0の場合のフォールバック
if (selfIncome + spouseIncome === 0) {
  selfShare = 0.5;
  spouseShare = 0.5;
}

selfSurplus = surplus * selfShare
spouseSurplus = surplus * spouseShare
```

### 4.3 costBasis更新

```typescript
// 本人
tax += selfSurplus;
taxCostBasis += selfSurplus;

// 配偶者(配偶者口座が存在する場合のみ)
if (p.spouse) {
  spTax += spouseSurplus;
  spTaxCostBasis += spouseSurplus;
}
```

黒字分は元本として扱うため、残高とcostBasisに同額を加算する。これを漏らすと、
将来の取崩時に黒字分まで含み益として誤って課税される(過大課税バグ)。

## 5. UI仕様

### トグル配置

- 取崩戦略選択(比例取崩・現金優先・課税優先)の近傍に配置。黒字/赤字で
  挙動が変わることが視覚的にわかる位置とする

### 文言

- 「退職後、収入が支出を上回った分を運用する」を基本文言とする
- 実装時、UIコンポーネントのスペース制約次第で文字数調整の余地あり
  (意味を変えない範囲での短縮は実装フェーズでUI担当の裁量とする)

### デフォルト値

- OFF固定。既存プロファイル・過去記事の数値への影響をゼロにするため

---

## 6. 既存機能との整合性

| 項目 | 整合性の確認結果 |
|---|---|
| 3つの取崩戦略 | 黒字処理は戦略選択と独立。戦略はあくまで不足時の取崩順序のみを決定 |
| モンテカルロ(MC) | Growth適用は黒字加算より前に実行済み。既存の年末積立方式と整合、位置変更不要 |
| NISA生涯上限チェック | 本機能はNISAに触れないため、既存の上限判定不可という制約と衝突しない |
| `analyze.ts`側の指標 | `finalAssets`等はtotalAssetsベースのため無改修。`YearlyTable.tsx`等の口座別内訳表示は意図通り数値が変化するのみ(コード変更不要) |
| 田中・山本・中村3キャラクター | デフォルトOFFのため影響なし。仮にONでも定常的な黒字年が存在しないため実質影響なし(確認済み) |

## 7. エッジケース仕様

| ケース | 挙動 |
|---|---|
| 本人・配偶者の収入合計が0(黒字はiDeCo一時金や退職金のみで発生する等、通常想定しづらいが理論上あり得るケース) | 50:50按分にフォールバック |
| 配偶者が存在しない(`p.spouse`が未設定) | 黒字全額を本人の`tax`/`taxCostBasis`に加算(按分計算自体をスキップ) |
| 黒字が発生するが`retirementSurplusReinvest`がfalse | 従来通り`cash`に加算(既存動作を変更しない) |
| 特定口座の`toAge`(積立終了年齢)を過ぎている場合 | 積立期の`taxActive`判定は取崩期には適用されないロジックのため、本機能には影響しない想定。念のため実装時にtaxActive相当のガード条件が誤って適用されていないか確認する |

## 8. 検証計画

- `scripts/verify-*.js`系に新規テストケースを追加
  - 境界値:黒字ちょうど0円、本人収入のみ・配偶者収入のみ、両者収入0(50:50フォールバック)
  - 代表ケース:本人年金300万・配偶者年金100万・支出300万(黒字100万→75万:25万に按分される既存の合意例)
  - iDeCo年金受取を含むケース(按分比率にiDeCo年金税引後額が正しく合流しているか)
  - costBasis加算後、取崩時の含み益課税額が黒字加算前と比べて正しく減っている(過大課税になっていない)ことを確認するラウンドトリップ検証
- `full-verify.js`への組み込み
- トグルOFF時、既存の全テストケースの結果が一切変化しないことを確認する
  回帰テスト(最重要:既存動作へのデグレがないことの担保)

## 9. 実装フェーズ分割案

- **フェーズ1**:型定義追加(`SimParams.retirementSurplusReinvest`)・
  `simulate.ts`の黒字処理分岐追加・按分ロジック実装・検証スクリプト

## 10. 未解決事項・将来検討

- 現状、`p.spouse`が存在しない単身者ケースでは按分計算自体が発生しないため、
  按分ロジックの実質的なテストカバレッジは配偶者ありケースに限定される
- 将来、配偶者側にも独立した収入イベント(`owner: 'spouse'`)が複雑化した場合、
  按分比率計算の再計算ロジックとイベント側の仕様変更が乖離しないよう、
  変更時は本Specの4.2章を参照して整合性を確認すること
