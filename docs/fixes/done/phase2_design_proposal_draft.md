## 0. デプロイ前に必要な追加タスク（フェーズ1への追補、フェーズ2ではない）

資産管理ツール統合（フェーズ1）は本設計時点でまだ本番デプロイ前。`AssetSnapshot`/`HojinAssetSnapshot`には既に`profileId: string`フィールドが下地として存在する（フェーズ1では常に`'default'`固定、`storage.ts`の`withDefaultProfileId`で後方互換補完）一方、`AssetHolding`（現在の保有資産）には`profileId`が一切無いという非対称が実コード確認で判明した。

**対応：本番デプロイ前の今のうちに、`AssetHolding`にも`profileId: string`を追加する**（`Snapshot`と同じ`withDefaultProfileId`相当の後方互換パターンで、既存データは`'default'`扱い）。本番データがまだ存在しない状態でスキーマを揃えられるため、マイグレーション不要でクリーンに対応できる。

この対応はフェーズ2の実装指示書とは別に、**フェーズ1デプロイ前の小さな独立タスクとしてClaude Codeに指示する**。

## 1. コンセプト

資産管理ツールに新設する「プロファイル」は、**予実管理（シミュレーターの予測 vs 資産管理ツールの実績）のための単位**。1プロファイル＝1人物（本人・別人物いずれも想定）の「予測 vs 実績」セット。

- 用途はケースバイケース：本人の実績記録だけに使うことも、別人物（家族・note連載キャラクター等）の予測と実績を並べて管理することも想定
- シミュレーター側プロファイルへのリンクは**任意**（`linkedSimulatorProfileId: number | null`）。リンクなしで実績記録だけに使う使い方も正式にサポートする
- リンクは**片方向の参照であり、所有関係ではない**。資産管理ツール側からシミュレーター側プロファイルを書き換えたり削除したりすることはない

---

## 2. データモデル・ストレージ方式（v2で統一）

**設計原則：キーを分割せず、単一ストレージキーの中でprofileIdによって区分する。** フェーズ1で`Snapshot`側に既に敷かれていた「単一配列＋profileIdフィールド」という下地に、他のデータも統一する。

| データ | ストレージキー | 方式 |
|---|---|---|
| 保有資産（`AssetHolding[]`） | 既存の`lifeCompassAssetHoldings`（変更なし） | 配列の各要素に`profileId`フィールドを追加（0節の追補タスク） |
| スナップショット履歴 | 既存の`assetSnapshots`相当（変更なし） | 既にある`profileId`フィールドをそのまま使う |
| CompanyState（法人設定） | 既存の`hojinCompanyState`（**キー名は変更しない**） | 中身を`{ default: <既存の設定>, [profileId]: <設定>, ... }`という**profileIdキー付きのマップ構造**に変更。§3で撤回した「別キー方式」の代わりにこちらを採用 |

- アクセサ層（`getCompanyState(profileId)` / `saveCompanyState(profileId, state)` / `deleteCompanyState(profileId)`）は維持する。内部実装は上表の通りマップ構造にする
- `id`：資産管理ツールプロファイル自体のID。シミュレーター側の`Date.now()`方式とは切り離し、UUID方式（`crypto.randomUUID()`等）で独立発行する
- `name`：表示名
- `birthDate`：生年月日（新規）
- `linkedSimulatorProfileId`：シミュレーター側プロファイルID。nullable

### グローバル管理データ
- `assetManagerProfiles`：プロファイル一覧
- `assetManagerCurrentProfileId`：現在選択中のプロファイルを指す明示的ポインタ（新設）
- `assetManagerMigrationVersion`：移行処理のバージョン管理フラグ（7節参照）

### 2-1. ID方式・アクティブプロファイルポインタ
調査1で判明した通り、シミュレーター側は「同名上書きでID使い回し」「アクティブプロファイルの明示ポインタなし」という設計。この脆さを資産管理ツール側に持ち込まない。独立したUUID方式＋`assetManagerCurrentProfileId`という明示的なポインタを新設する。シミュレーター側の`ProfileDrawer`／`loadInitialProfile()`には手を入れない。

### 2-2. 年齢（生年月日）とシミュレーター側`curAge`の整合
- シミュレーター側の`curAge`は変更しない（`profile.ts`はロックファイル）
- 資産管理ツール側は`birthDate`から算出した年齢を独自に表示・使用する
- **フェーズ2ではシミュレーター側`curAge`との自動整合チェック（ズレ警告）は実装しない**（`curAge`は静的なスナップショット値で時間経過とともに乖離するため、単純比較はノイズになる。将来検討事項として保留）
- 新規プロファイル作成時、リンク先シミュレータープロファイルを選択したら、その`curAge`から逆算した生年月日を初期値としてサジェストする（補助のみ）

## 3. プロファイル削除の仕様

- 資産管理ツールプロファイルを削除すると、そのプロファイルに属する保有資産・スナップショット・CompanyStateは**まとめてカスケード削除**する（単一キー内でprofileId一致要素をfilterする形になる）
- リンク先のシミュレータープロファイルは**絶対に削除しない**（参照であり所有関係ではない）
- 逆に、シミュレータープロファイル側が削除され`linkedSimulatorProfileId`の参照先を失った場合：エラーにはせず、UI上「リンク切れ」状態として表示する。資産管理ツール側のデータ自体は一切削除しない

---

## 4. CSV Export/Import

- 既存の「区分」列・「年月」列によるルーティングの仕組みを拡張し、**「プロファイルID」列を追加**する
- Exportは現行方針（表示トグルとは無関係に常に全データ）を踏襲し、**全プロファイル分をまとめて1つのCSVに出力**する
- Importは各行の「区分」列に加えて「プロファイルID」列も見て、対応するプロファイルのストアに書き込む（表示トグルは引き続き参照しない）
- これにより複数プロファイルにまたがる一括編集・一括インポートが可能になる

---

## 5. JSON Export/Import

- **全プロファイル一括のまま**とする（KENZOと確認済み）。現行の「完全バックアップ＝置き換え」という意味をそのまま複数プロファイルに拡張する
- プロファイル単位のExport/Importは今回のスコープ外。必要になれば将来の拡張候補とする

---

## 6. 全データリセット機能

- 現行は個人／法人／両方、設定値の削除有無を選べる確認ダイアログ形式
- プロファイル導入後は「現在のプロファイルのみ」と「全プロファイル」のスコープ選択が新たに必要になる。これは設計思想レベルの分岐ではなく実装時に追加すればよいUI項目のため、詳細は実装指示書側で扱う

---

## 7. 既存データの移行方針

フェーズ2導入時点で、KENZOの環境には既に「プロファイル概念のない」実データが存在する（資産管理ツールの保有資産・スナップショット履歴、`hojinCompanyState`の単一グローバル値）。

**移行方針（確定）：**
- 保有資産・スナップショット履歴・CompanyStateの3つを**1つの移行処理としてまとめて**「デフォルトプロファイル」に割り当てる
- 移行処理は`assetManagerMigrationVersion`で管理し、**必ず冪等**にする（複数回実行してもデフォルトプロファイルが重複作成されない）
- 移行ロジック自体の検証は安全なテストデータ／ロジックの単体検証で行い、本番相当の実データでのリハーサルは行わない（過去の事故の再発防止）

---

## 8. PortfolioPanel（シミュレーター「現在PF」パネル）との関係

- 自動同期・書き込み連携はスコープ外（`PortfolioPanel.tsx`はロックファイル）
- 予実管理の可視化として、資産管理ツール側に読み取り専用のグラフ（シミュレーターの予測ライン＋資産管理ツールの実績プロットを重ねる）を新設する
- シミュレーター側の予測値取得は`simulate()`/`analyze()`を**呼び出すだけ**（内部ロジックは変更しない）で実現できるか、実装フェーズでClaude Codeに確認させる

### 8-1. 将来拡張として明記（フェーズ2では実装しない）
「2026年8月時点で立てた予測」と「2027年8月の実績」を並べて比較するには、当時の予測を再現できる**予測スナップショットの保存**が将来的に必要になる可能性がある。フェーズ2のスコープには含めないが、後から追加できるよう設計上の余地は意識しておく。

## 9. このフェーズのスコープ外（今回やらないこと）

- シミュレーター側`ProfileDrawer`／`curAge`／ID発行方式自体の改修
- PortfolioPanelとの自動データ同期
- シミュレーター側`curAge`との自動整合チェック（ズレ警告）
- 予測スナップショットの保存
- JSON Export/Importのプロファイル単位モード

## 10. 定数

- `MAX_ASSET_PROFILES`：資産管理ツール側プロファイルの上限。シミュレーター側`MAX_PROFILES`とは別定数として管理する。当面は同じ値（10）を踏襲する

## 11. 参照用イメージ

```
AssetManagerProfile {
  id: string (UUID)
  name: string
  birthDate: string | null
  linkedSimulatorProfileId: number | null   // 片方向参照、所有関係ではない
}

// 単一キー・profileIdで区分（キー分割しない）
lifeCompassAssetHoldings: AssetHolding[]   // 各要素にprofileId追加(0節)
assetSnapshots: AssetSnapshot[]             // 既にprofileIdあり
hojinCompanyState: { [profileId]: CompanyStateSettings }  // マップ化

グローバル:
  assetManagerProfiles
  assetManagerCurrentProfileId
  assetManagerMigrationVersion
```
