# 調査指示書:sitemap.xml のツール一覧を動的生成化するための事前調査

## 背景

現在、`sitemap.xml`の生成ロジックにおいて、`/tools/`配下の各ツールURLは
`STATIC_PATHS`という手動リストに個別登録する設計になっている。

直近のセッションで、`resident-tax-timing`ツールの登録漏れを修正した際、
無関係な過去セッションで追加された`retirement-ideco-timing`も同様に
未登録だったことが判明した(実際には10ツール中8ツールしか`STATIC_PATHS`に
登録されていなかった)。手動リストに頼る設計だと、今後ツールを追加するたびに
同種の登録漏れが繰り返されるリスクが高い。

この問題を解消するため、`src/app/tools/`配下のディレクトリ構造を動的に
読み取ってサイトマップに反映する方式への変更を検討したい。本指示書は、
その設計・実装に着手する前の**調査専用**のフェーズである。

## この調査の位置づけ・厳守事項

- **本フェーズはコードの変更を一切行わないこと。** 目的は現状の実装を正確に
  把握し、報告することのみ。
- ファイルの読み取り・grep・`git log`等の調査コマンドは自由に実行してよいが、
  いかなるファイルの編集・作成・削除・リネームも行わないこと。
- 設計案の提示や実装方針の判断は本フェーズの範囲外。「こう変更すべき」という
  提案があれば報告書の末尾に「所感」として書いてよいが、コード変更は次回以降の
  別指示書で扱う。

## 調査してほしいこと

### 1. sitemap.xml の生成方式そのもの

- `sitemap.xml`はどのファイルで、どういう仕組みで生成されているか
  (例:Next.js App Router のネイティブ`app/sitemap.ts`、独自スクリプト、
  `next-sitemap`等のパッケージ、静的ファイルの手動更新、など)
- 生成が実行されるタイミング(ビルド時/リクエスト時/CI上の別スクリプト)
- そのコンテキストで`fs`モジュール等を使ったファイルシステムの読み取りが
  可能か(例:Edge Runtime指定などで`fs`が使えない制約がないか)

### 2. `STATIC_PATHS`の現在の完全な中身

- 定義箇所のファイルパスと、現時点で登録されている全エントリ
- ツール由来のパス以外(固定ページ、その他)が混在していないか。混在して
  いる場合、それぞれの内訳
- `STATIC_PATHS`以外にサイトマップへ手動登録が必要な箇所が他にもないか
  (例:ブログ以外の動的コンテンツで同様の仕組みがないか)

### 3. `src/app/tools/`配下の実際のディレクトリ構造

- 各サブフォルダが1ツール=1URLという対応で一律になっているか
  (例外:共通の`page.tsx`・`layout.tsx`・`_components`等、ツールのURLに
  対応しない特殊フォルダの有無とその命名パターン)
- ディレクトリ名からURLスラッグへの対応関係(単純にフォルダ名がそのまま
  スラッグになっているか、変換が必要なケースがあるか)
- `toolMetadata.ts`(`TOOLS`配列/`TOOL_MAP`)との対応関係。ディレクトリ
  存在チェックとメタデータ側のツール一覧が実質的に同じ集合と言えるか、
  ズレがあり得るか(例:メタデータには登録済みだがディレクトリ未実装、
  またはその逆のケースが起こり得る設計か)

### 4. 除外すべきツールが存在する可能性

- 過去または現在、「意図的に非公開」「開発中」「サイトマップに含めたくない」
  という理由でディレクトリは存在するがURLとして公開したくないツールが
  存在した/する可能性があるか(git履歴・コミットメッセージ・コード内コメント等から
  確認できる範囲でよい)
- もしそのようなケースがあった場合、`STATIC_PATHS`の手動管理が実は
  意図的な「公開フィルタ」として機能していた可能性はないか

### 5. ブログ側の動的生成パターンとの比較

- `getAllPosts()`等、ブログ記事をサイトマップに動的反映している既存の
  実装箇所のファイルパスと実装方式
- そのパターン(ファイルシステム走査 or CMS的なデータソースからの取得)が
  ツール側にもそのまま応用できそうか、それとも実行コンテキストの違い
  (例:ブログは`.md`ファイル走査、ツールは`page.tsx`を含むディレクトリ走査で
  必要な処理が異なる)によって単純流用が難しいか

## 報告してほしい形式

- 上記1〜5それぞれについて、確認した事実を簡潔に(コード引用は必要最小限)
- 不明な点・調査しても判断がつかなかった点があれば明示すること
- コード変更は行っていないことを報告の冒頭で明記すること
