# 調査指示：full-verify.js のメモリ使用量が約4.6GBに達している原因

作成日：2026-09-26
種別：**調査のみ（実装・修正は一切行わない）**
対象リポジトリ：`lifecompass-next`
起点テンプレート：`docs/fixes/INSTRUCTION_TEMPLATE.md`

---

## 背景

`fix/hojin-personalization-rate`の作業中に、`scripts/full-verify.js`が通常の実行（Node.jsのデフォルトのヒープ上限、約4GB）で、最後のFAQ抽出のセクションで「JavaScript heap out of memory」になり、終了コード134で止まるようになった。

- ヒープ上限を8GBにすると全件PASSする
- プロセス全体の最大メモリ使用量は、変更前のmainで約4,639MB、変更後で約4,662MB。変更前から上限ぎりぎりで、テストを3件追加したことで上限を超えた
- 計算の不具合ではない

full-verifyはすべての完了報告の土台なので、通常の実行で落ちる状態は放置できない。**このタスクは、なぜこれほどメモリを使うのかを特定する調査のみを目的とする。**

Claude Codeが前回挙げた仮説（各verifyスクリプトが`ts-node`をそれぞれ登録し直している）は、まだ確かめられていない。仮説に引きずられず、測定で確かめること。

---

## 調査1：full-verify.js の構造

- 各セクション（各verifyスクリプト）を、同じプロセスの中で`require`しているのか、子プロセスとして起動しているのか
- `ts-node`（またはそれに類するTypeScriptの読み込み手段）が、どこで何回登録されているか
- モジュールのキャッシュ、グローバル変数、大きな配列などが、セクションをまたいで残り続ける作りになっていないか

## 調査2：セクションごとのメモリの測定

- 各セクションの開始時と終了時の`process.memoryUsage()`（`rss`・`heapUsed`）を測り、セクションごとの増加量を一覧にする
- どのセクションで大きく増えるか、増えた分がセクションの終了後に解放されているかを示す
- 特に、次の2つを重点的に見る
  - 最後のFAQ抽出のセクション（ここで上限を超える）
  - モンテカルロのセクション（固定シード版と参考値版）

## 調査3：原因と改善策の候補

- 測定結果から、メモリを多く使っている原因を特定する（推測ではなく、測定値とコードの根拠を示す）
- 改善策の候補を挙げ、それぞれの効果の見込みと変更の範囲を示す（例：セクションごとに子プロセスで実行する、`ts-node`の登録を1回にまとめる、など）。実装はしないこと
