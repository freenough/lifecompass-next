# 調査指示：資産管理ツール プロファイル機能（フェーズ2）導入前の事前調査

作成日：2026-08-29
種別：**調査のみ（実装・修正は一切行わない）**

---

## 背景

2026-08-26のセッションで、資産管理ツール（個人/法人）の統合作業一式が完了した（`AssetHolding`型の共通化、CSV/JSON周りの全面刷新、過去月「断面」バグの一括修正など。詳細は当該セッションの引き継ぎメモを参照）。

次のフェーズ2では、資産管理ツールにプロファイル機能（複数プロファイルの切替・生年月日ベースの年齢トラッキング等）を導入する予定。ただし設計を確定させる前に、既存の関連実装がどうなっているか不明な点が3つ残っており、まずこれを事実確認する必要がある。

**このタスクは調査のみを目的とする。** 調査結果を持ち帰り、KENZOとの設計チャットでフェーズ2の仕様（プロファイルIDの命名・発行ロジックの一元化を含む）を確定させる。憶測での実装や、調査の過程で気づいた不具合の“ついで修正”は行わないこと。

---

## 調査1：プロファイル管理の構造（シミュレーター側 `ProfileDrawer`）

**確認したいこと**
- プロファイルのID発行方式：名前ベース（名前をキーとして使う）か、UUID等の独立ID発行式か
- localStorageのキー構造（プロファイル一覧・各プロファイルの実データがそれぞれどんなキー名・データ構造で保存されているか）
- プロファイルの作成・切替・削除・リネームそれぞれのタイミングで、上記のキー構造がどう変化するか

**対象ファイル**
- `ProfileDrawer`本体のコンポーネントファイル
- プロファイルの永続化・ID発行ロジックが入っているstore/hook/libファイル（`ProfileDrawer`から参照している箇所を辿って特定すること）

**報告フォーマット**
- ID発行方式について、該当コード箇所を抜粋しながら説明
- localStorageのキー構造を具体例（実際のキー名とサンプルデータ形状）付きで説明

## 調査2：CompanyState（法人設定）とプロファイル切替の連動確認

**背景**
`CompanyStateSettings`は`useSimulatorStore`を一切参照しない独立stateであることが分かっている。そのため、プロファイルを切り替えても法人設定（実効税率・法人PF配分等）が追従しない可能性があるが、実際にそうなっているかは未確認。

**確認したいこと**
- `CompanyStateSettings`が実際に`useSimulatorStore`（またはプロファイル切替の仕組み）と接続されているか、コードを読んで確認する
- 実際にプロファイルAで法人設定を変更した後にプロファイルBへ切り替え、その後Aに戻した場合、法人設定の値がどうなるか（保持される／Bの値に上書きされる／グローバルに1つしかない、等）を実際に動作させて確認する。コードを読むだけで判断がつかない場合は、安全なテストデータで実機（ブラウザ）動作確認を行うこと

**対象ファイル**
- `CompanyStateSettings`コンポーネント
- `useSimulatorStore`の定義ファイル

**報告フォーマット**
- 現状の挙動を「追従する／追従しない／プロファイルという概念自体が法人設定に存在しない」のいずれかで明記し、根拠となるコード箇所を添付
- 実機確認を行った場合は、確認手順と結果（スクリーンショット等）を添付

## 調査3：シミュレーター「現在PF」パネル（`PortfolioPanel.tsx`）と個人資産管理ツールの接続有無確認

**背景**
シミュレーター本体の「現在PF」パネル（`PortfolioPanel.tsx`、ロックファイル）と、個人資産管理ツールは、概念的にはどちらも「現在の資産内訳」を持つ。データが実際に連携しているのか、それとも独立した複製なのかが未検証。現時点では独立複製と推測されているが、確認できていない。

**確認したいこと**
- `PortfolioPanel.tsx`が参照しているデータソースと、個人資産管理ツール（`AssetManagementPage.tsx`および`src/lib/assetManagement/storage.ts`等）が参照しているデータソースが同一か別かを特定する
- 別々の場合、両者間でユーザーが手動で数値を合わせる必要があるのか、あるいは今後同期させる設計余地があるのかという観点でのデータフローを整理する

**遵守事項（重要）**
- `PortfolioPanel.tsx`はロックファイル。**読み取りのみ**とし、一切変更しないこと

**対象ファイル**
- `PortfolioPanel.tsx`（読み取り専用）
- `AssetManagementPage.tsx`
- `src/lib/assetManagement/storage.ts`（および関連のstore/lib）

**報告フォーマット**
- データソースが同一か独立複製かを明記
- 簡単なデータフロー図（テキストで可）と、根拠となるコード箇所

## 全体の遵守事項

- 本タスクは調査のみ。実装・修正・リファクタリングは一切行わない（調査中に見つけた不具合があっても、この場では修正せず報告のみに留める）
- ロックファイル（`types.ts`/`profile.ts`/`PortfolioPanel.tsx`/`simulate.ts`/`analyze.ts`/`montecarlo.ts`/`blog.ts`/`blogTopics.ts`/`concerns.ts`）への依存・変更は一切ゼロを維持すること
- 報告には必ず実際のコード抜粋を添付すること。「〜と思われる」「おそらく〜」といった推測のみの報告は不可（過去のセッションで、文章のみの報告が実態と食い違っていたことが複数回あったため）
- 検証を行う場合、本番相当の実データ環境は絶対に使わないこと。安全なテストデータ・別プロファイル等で行うこと

## この調査結果の使い道

この3件の調査結果を持ち帰り、KENZOとの設計チャットで以下を確定させる：
- プロファイルIDの命名・発行ロジックの一元化方針
- 生年月日ベースの年齢トラッキング機能の設計
- CompanyStateをプロファイル単位で持たせるべきか、フェーズ2の対応範囲に含めるべきかの判断
- PortfolioPanelとの連携要否の判断（連携させる場合はロックファイル変更の是非を含めて別途承認が必要）
