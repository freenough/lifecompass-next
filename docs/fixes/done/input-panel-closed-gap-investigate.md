## 手順(この順番を厳守。今回は原因特定のみで停止し、修正は実装しないこと)

1. 添付画像と同じ幅(3列KPI表示になる幅、640〜1024px想定)のブラウザで「入力を閉じる」状態にする
2. 「入力を編集」ボタンと「固定モード/MCモード」の間の空白部分を、DevToolsの要素選択(inspect)で直接クリックする
3. どのDOM要素がその空間を占めているか(ハイライト表示・タグ名・クラス名)を確認する。フォーム本体(SimulatorFormのラッパー)がその時点で実際に`display:none`または非レンダリングになっているかどうかも合わせて確認する

5. 3〜4の結果を、**要素名・クラス名・該当CSSプロパティと数値、および該当ソースコードの場所(ファイル名・行)**の形で報告する

## 想定される原因パターン(参考。決め打ちしないこと)

- フォームは実際には非表示になっているが、フォームを囲む親コンテナに固定の`margin-bottom`や`min-height`が残っている
- トグルボタン自体のラッパーに、開閉状態と無関係な固定の余白(`mb-*`等)が付いている
- フォームの折りたたみにtransition/animationを使っており、`max-height`や`height`の初期値がアニメーション用に大きく設定されたまま、closed状態でも一部残っている

## 追記(2回目の調査依頼)

前回の調査(768px幅、Playwright/Chromium)では空白が再現しなかったが、KENZOさんの実ブラウザ(幅を`window.innerWidth`で正確に測定: **975px**、DevTools切り離し・ズーム100%で確認済み)では空白が明確に見えている。975pxも640〜1024pxの範囲内であり、前回確認した768pxとレイアウト上の分岐点(sm:640, lg:1024)をまたいでいないため、本来は同じ挙動になるはずである。

**手順(引き続き原因特定のみ、修正は実装しないこと):**

1. ブラウザの実際のウィンドウ幅を975pxちょうどに設定して(DevToolsのレスポンシブモードでカスタム幅975pxを指定、またはウィンドウを975pxにリサイズして`window.innerWidth`で975であることを確認してから)検証する
2. 768pxと975pxの両方で、「入力を閉じる」状態にしたときの以下を比較する:
   - 前回同様、gap空間の中点への`elementFromPoint`の結果
   - 左パネル本体(`lg:w-80`)の実際のheight・bottom値
   - フォームラッパー(`SimulatorForm`)が本当に非表示になっているか
3. 768pxと975pxで結果に差がある場合、**その差を生んでいる分岐条件(CSSのブレークポイントやJSのwidth判定)を特定する**。例えば、`sm:`(640px)以外にも`md:`(768px)を使っているクラスが紛れ込んでいないか、レイアウト全体で使われている全ブレークポイント(sm/md/lg/xl)を洗い出して報告する
4. 975pxで実際に空白(41pxを大きく超えるサイズ)が再現するかどうかを実測する。前回報告の「41pxで開閉に差なし」という結論が975pxでも成り立つか確認する
