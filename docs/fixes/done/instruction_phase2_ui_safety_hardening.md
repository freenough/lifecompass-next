# 実装指示：フェーズ2①安全策強化 — CompanyState保存方式の完全統一・上書き確認への影響表示

作成日：2026-08-29
種別：**実装（修正）**
関連：`instruction_phase2_ui_followup.md`（1節の条件分岐をこの指示で確定させる）／`instruction_phase2_bugfix_stale_draft.md`（2節の未保存確認ダイアログをCompanyStateにも適用）／`instruction_phase2_ui_save_semantics.md`（1節の上書き確認ダイアログを拡張する）

---

## 背景

前回までの一連の対応で、保有資産については「下書き保持→明示保存ボタン→`beforeunload`警告→プロファイル切替時の未保存確認ダイアログ」という一貫したフローが実装された。一方、`CorporateSettingsSection.tsx`（CompanyState、法人設定）は、`instruction_phase2_ui_followup.md`1節の対応後も、**保存ボタンを押さずに他のプロファイルへ切り替えようとすると、確認なしでその場の内容が自動的に確定されてから切り替わる**という挙動が残っている（保有資産側は同じ状況で必ず確認ダイアログが出る）。

これは、同じ「保存し忘れたまま別のプロファイルに行こうとした」という状況に対して、画面によって挙動が異なるという一貫性の欠如であり、加えて、本ツールは今後KENZO本人以外の不特定多数が使う可能性を踏まえると、次の2点は軽視できないリスクと判断した：

1. CompanyStateが確認なしに自動確定されてしまうこと（意図しない上書きが警告なく発生しうる）
2. `instruction_phase2_ui_save_semantics.md`で実装した「上書き保存」の確認ダイアログ（`window.confirm('「' + name + '」はすでに存在します。上書きしますか？')`）が、名前が一致するかどうかしか示しておらず、**実際に何が上書きされるのか（金額や件数）が確認画面から分からない**ため、誤って別プロファイル（＝別人の可能性がある）の保有資産を上書きしてしまうリスクを十分に低減できていないこと

この2点について、以下の通り安全策を強化する。

---

## 1. CompanyStateの保存方式を保有資産と完全に統一する（必須・例外なし）

`instruction_phase2_ui_followup.md`1節では「他フィールドの保存タイミングの実態次第で判断する」という条件分岐にしていたが、今回、**調査結果によらず無条件で**、CompanyStateを保有資産と全く同じ挙動に統一することを確定する。

- CompanyStateの編集は下書き状態として保持し、保存ボタンを押すまでlocalStorageへ書き込まない（既にこの部分が実装済みなら維持）
- 未保存の変更がある状態でページを離れようとしたら`beforeunload`で警告する（既存の`UnsavedChangesContext`の仕組みを利用。実装済みなら維持）
- **【今回追加】未保存のCompanyState変更がある状態でプロファイルを切り替えよう（一覧の「読込」等）とした場合、`instruction_phase2_bugfix_stale_draft.md`2節と全く同じ確認ダイアログを出すこと**：「保存されていない変更があります。保存せずにプロファイルを切り替えますか？」（OK＝破棄して切り替える／キャンセル＝切り替えず現在の画面に留まる）
- **確認なしに自動保存・自動確定される経路を一切残さないこと。** 現状の「確認なしに勝手に保存されてから切り替わる」という挙動は、たとえ実装上の都合（フォームの他フィールドとの兼ね合い等）があっても許容しない
- 保有資産用の未保存確認ダイアログの仕組み（`holdingsDirty`とその確認処理）を流用・共通化できる場合は共通化してよいが、CompanyState用に別途フラグ（例：`companyStateDirty`）を持たせても構わない。挙動が保有資産と完全に一致していることが必須条件であり、実装方法は問わない

---

## 2. 上書き保存の確認ダイアログに、具体的な影響（金額・件数）を表示する

`instruction_phase2_ui_save_semantics.md`1節で実装した上書き保存の確認ダイアログを拡張し、名前の一致だけでなく、**何がどう変わるのかが一目で分かる内容**にする。

- 確認ダイアログ（`window.confirm`、またはより表現力のあるモーダルに変更してもよい。ネイティブ`confirm`のままなら文言に情報を追加する形で対応可）に、少なくとも以下を含めること：
  - 上書き対象のプロファイル名（既存通り）
  - 上書き対象プロファイルの**現在の保有資産件数・合計評価額**（例：個人分＋法人分）
  - 今画面に表示されている**保存しようとしている内容の保有資産件数・合計評価額**
  - 上記2つを対比できる形式にすること（例：「『〇〇』はすでに存在します。上書きすると、現在の内容（資産◯件・合計¥◯◯◯）が、今画面の内容（資産◯件・合計¥◯◯◯）に置き換わります。よろしいですか？」）
- 上書き対象が**現在アクティブなプロファイルではない**場合（`instruction_phase2_ui_save_semantics.md`1節で対応した、名前欄に別プロファイルの名前を入力して上書きするケース）は、特に誤操作のリスクが高いため、ダイアログの文言でその点も明示すること（例：「現在編集中の内容を、別のプロファイル『〇〇』に上書きします」といった一言を追加する）
- 合計評価額の算出は、既存の集計ロジック（一覧表示等で使っているもの）を再利用してよい。新規に計算方法を作らないこと
- ネイティブ`window.confirm`は改行やレイアウトに制約があるため、情報量が増えて読みにくくなる場合は、カスタムの確認モーダルコンポーネントに置き換えてよい（KENZOの判断は不要、実装側の裁量で構わない）。ただし、既存の「OK＝実行／キャンセル（またはモーダルを閉じる）＝何もしない」という挙動は維持すること
