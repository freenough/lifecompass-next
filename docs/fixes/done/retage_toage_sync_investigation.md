# 調査のみ：退職年齢延長時、口座別toAgeが連動しない疑いの検証

## 背景

各口座(`nisa`/`ideco`/`tax`)は`retAge`とは独立した`toAge`フィールド(積立終了年齢)を持つ構造になっている。旧HTML版の感度分析(`drawSens()`)には、退職年齢を動かす際に`penAge`(年金開始年齢)が連動しない旨の`[WARN-9]`コメントが既に存在するが、**口座別`toAge`が連動するかどうかについては言及がない**。

以下2箇所で、「退職年齢を延長する」操作をした際に口座別`toAge`が追従しているかを確認したい。

1. `AiPanel.tsx`の`buildAIPayload()`内「退職2年延長」改善案(`pRet = {...p, retAge: p.retAge + 2}`相当の処理)
2. `SensitivityPanel.tsx`の退職年齢スライダー(`ssRet`相当)

**このタスクは調査のみ。`simulate.ts`・`AiPanel.tsx`・`SensitivityPanel.tsx`等、プロダクトコードは一切変更しないこと。**

## 確認してほしいこと

### 1. simulate.tsの積立停止条件の実装確認

`simulate()`内で、各口座への積立(`con`の加算)を止める条件が何を参照しているか確認せよ。

- `age < acct.nisa.toAge`のように口座別`toAge`を見ているのか
- それとも`age < retAge`のようにグローバルな`retAge`を見ているのか
- 口座によって参照先が異なる(例:NISAは`toAge`、iDeCoは`retAge`)可能性もあるため、3口座(nisa/ideco/tax)それぞれ個別に確認すること

### 2. AiPanel.tsx「退職2年延長」改善案の実際の挙動確認

現在の実装(`pRet = {...p, retAge: p.retAge + 2}`相当)で、`acct.nisa.toAge`等が`retAge`と同時に更新されているかを確認せよ。

- 更新されていない場合:実際にsimulate()を実行し、「延長した2年間、口座への積立が行われないまま収入だけがある」という状態になっているかどうかを、田中誠のプロファイルで具体的に検証せよ(例:延長前後で該当2年間の各口座残高・積立額を比較)
- 更新されている場合:その処理がどこで行われているか(コンポーネント名・処理内容)を報告せよ

### 3. SensitivityPanel.tsxの退職年齢スライダーの同様の確認

同様に、退職年齢スライダーを動かした際に口座別`toAge`が連動するかを確認せよ。感度分析は複数の変数(利回りΔ・退職年齢Δ等)を同時に扱うため、`toAge`非連動によって結果がどの程度歪みうるか、具体的な数値例(田中誠プロファイル・退職年齢+3年程度)で確認せよ。

### 4. 影響の大きさの見積もり

もし(2)(3)で「連動していない」ことが確認された場合、実際にどの程度の計算誤差につながるかを見積もってほしい。具体的には:

- 田中誠プロファイルで「退職2年延長」を行った際、`toAge`を連動させた場合(正しい計算)と連動させない場合(現状の実装)とで、最終資産・資産寿命・`minRatio`にどの程度の差が出るか
- この差が「無視できる誤差」なのか「実用上看過できない差」なのか、数値から判断材料を示すこと

## 完了報告フォーマット

- simulate.tsの積立停止条件の参照先(口座別、行番号ではなく関数名・変数名で報告)
- AiPanel.tsx「退職2年延長」の実際の挙動(連動しているか否か、していない場合は田中誠での具体的な数値差)
- SensitivityPanel.tsxの退職年齢スライダーの実際の挙動(同上)
- 影響の見積もり(無視できる誤差か、修正が必要な水準か)
- 参照した関数・コンポーネント名(行番号ではなく)
- `full-verify.js`実行結果(ロジック変更なしのため、既存の回帰が壊れていないことの確認のみ)

## 注意事項

- **プロダクトコードの変更は一切行わない**。バグと確認された場合の修正方針は、この調査結果を見てKENZOが判断する
- 数値はシミュレーターの実行結果から取得(手計算しない)
- もし調査の結果「連動していないが実務上の影響はごく僅か」と判明した場合も、その旨を正直に報告すること(過大にも過小にも見積もらない)
