# 調査専用タスク：資産管理ツール実装に向けたLifeCompass側の現状調査

## 位置づけ
これは**調査専用**の指示です。実装・ファイル作成・既存ファイルの変更は一切行わないでください。
調査結果をレポートとして返してください。設計判断はこのチャット側で行います。

## 背景
`lifecompass-next`(LifeCompass)側に、既存のFIREシミュレーターとは独立した新機能「資産管理ツール」を追加します。位置づけはシミュレーターと並ぶ主要機能で、既存の10ツール(`toolMetadata.ts`)とは別枠です。

このツールは、現在シミュレーターのウィザードの一部である「現在のPF」入力(個人の金融資産をNISA・iDeCo・特定口座等のカテゴリ別、資産クラス別に入力するステップ)とは**完全に独立した新規実装**とします。`simulate.ts`・既存の「現在のPF」入力フローには一切触れません。

ただし、将来的にこの新ツールがシミュレーターの入力データソースとして統合される可能性があるため、今回の調査では「現在のPF」の実際のデータ構造を把握し、将来の統合を妨げない(かつ今回は触れない)形で新ツールの設計に活かしたいと考えています。

## 調査してほしいこと

### 1. 「現在のPF」入力のデータモデル
- 「現在のPF」ステップが実装されているファイル(コンポーネント・型定義)を特定してください
- 入力データの型定義(TypeScript interface/type)を報告してください。特に以下を明らかにしてください:
  - カテゴリ(NISA・iDeCo・特定口座・現金等)の一覧がどこで定義されているか
  - 各カテゴリ内で「配偶者」のサブアカウントを持つ構造(添付画像で確認した「配偶者のNISA」等)の実装方法
  - 資産クラス(全世界株・先進国債券等)の一覧がどこで定義されているか、それが独自の定数ファイルか、`simulate.ts`内部に密結合しているか

### 2. 資産クラスの定義箇所と結合度
- 資産クラス一覧(全世界株・先進国債券等)を定義しているファイルを特定し、そのファイルが`simulate.ts`や他のロックファイルとどの程度密結合しているか(型のexport元、想定利回り等のパラメータもここにあるか)を報告してください
- このファイルを新ツールから**読み取り専用でimportする**ことが技術的に可能か、あるいは値を複製する方が安全か、判断材料となる情報を報告してください(結合度が高い・低いの実態を示すこと)

### 3. 永続化方式
- 「現在のPF」の入力データは、現在どのように保持されていますか(ページ遷移・リロードで消える一時的なReact stateか、localStorageに保存されているか)
- 保存されている場合、キー名・データ構造を報告してください

### 4. UIコンポーネントの再利用可能性
- 添付画像で確認した「カード形式(カテゴリごとにセクション分割)+口座ごとの入力欄+追加ボタン+配偶者アコーディオン」というUIパターンを実装しているコンポーネントを特定してください
- このコンポーネントが汎用化されているか(props経由でカテゴリ名等を渡せる作りか)、あるいは「現在のPF」専用にハードコードされているか報告してください
- 新ツールで似たUIを作る場合、このコンポーネントを流用できそうか、新規実装が必要そうか、実装コストの見立てを報告してください

### 5. simulate()への入力経路の確認(参考情報として)
- 「現在のPF」の入力データが、最終的に`simulate()`にどのような形で渡されるか(型変換の有無等)を報告してください。これは今回変更しませんが、将来の統合可能性を検討する際の参考にします
