# 指示書:住宅ローン完済境界年の按分処理 実現可能性調査

**このセッションの役割:** 調査(および実装可能性の判断)。実装そのものはまだ行わないこと。設計判断を伴う分岐に達したら停止して報告すること。

## 背景

期間短縮型の繰上返済において、完済年齢が小数(例:67.25歳)で算出されるのに対し、`simulate.ts`の年次ループが整数年齢でしか判定できないため、「効果が本来0.25年分しかないのに、境界を跨げばまるごと1年分(158.3万円)の効果として計上され、跨がなければ0円になる」という粗さが生じている。この粗さを解消するため、完済境界年に限定して按分計算(端数年分だけ返済額を減らす)を局所的に追加できるかを調査する。

## 調査してほしいこと

1. **`simulate.ts`の年次ループの構造確認**
   - `mortgage`の`extraExp`計上部分(178-215行目付近)が、他の支出項目(生活費・教育費等)の計算とどう合算されているか
   - 按分処理(境界年だけ`payment × 端数比率`にする)を、この`mortgage`ブロック内だけで完結させられる構造になっているか、それとも年次ループ全体の合算方式に影響が及ぶ構造か

2. **按分の対象範囲の確認**
   - 期間短縮型のみが対象(返済額軽減型は完済年齢が変わらないため対象外、という前回の整理で合っているか再確認)
   - 境界年は「新しい完済年齢の整数部分の年」の1年だけで良いか(例:67.25歳なら、67歳の年の支払いを158.3万円×0.25(=端数のみ計上)にする、といった形で合っているか。計算式の妥当性も検討すること)

3. **既存フィクスチャ・他イベント種別への影響確認**
   - この按分処理を追加した場合、住宅ローン以外のイベント種別(収入・生活費・教育費・年金等)の計算ロジックに一切変更が及ばないことを確認する
   - 前回追加した繰上返済フィクスチャ(21ケース+今回追加予定のケース)が、按分処理追加後にどう変わるか(値の再計算が必要になることを前提に、影響範囲を洗い出す)

4. **改修規模の見積もり**
   - 按分処理の追加が「小規模な局所変更」で済むか、それとも年次ループの構造自体に手を入れる必要があり「大規模」になるかを判断する

## 判断基準

- 局所的な按分処理(住宅ローンのブロック内で完結し、他のイベント種別・年次ループの構造そのものには影響しない)として実装できる場合 → 実装可能と判断し、実装方針を報告(実装はまだ行わない)
- 年次ループの構造上、局所化が難しく大規模な改修が必要と判明した場合 → その旨を報告し、「今回はMath.ceil修正+一括支出計上のみに留め、UIに精度の注記を追加する」という代替案に切り替える判断をこのチャットで行う

## 報告フォーマット

- `simulate.ts`の年次ループ構造の要約(該当コード引用)
- 按分処理を局所的に実装できるかどうかの判断とその根拠
- 実装できる場合:按分の計算式案・改修規模感・既存フィクスチャへの影響範囲
- 実装が難しい場合:その理由と、代替案(Math.ceil修正+注記追加)への切り替え提案

**実装はまだ行わないこと。調査結果をこのチャットに報告し、方針確定後に別途実装指示書を作成する。**

## 参考:同時に承認済みの別対応(こちらは実装可)

以下2点は既に方針確定済みのため、この調査と並行して実装して構わない。

1. **一括支出の計上**(`simulate.ts`):`hasPrepay`ブロック内に、`age === expEv.prepayAge`の年に`extraExp += expEv.prepayAmount!`を追加する分岐を実装(既存の`age >= evAge && age < endAge`判定とは独立)
2. **表示丸めの暫定修正**(`LifeEventTimeline.tsx`):完済年齢表示の丸めを`Math.round`から`Math.ceil`に変更(期間短縮型のみ対象)

ただし、按分処理が実装可能と判断された場合、2番の`Math.ceil`修正は不要になる可能性が高い(按分処理があれば表示とシミュレーションは自然に一致するため)。按分処理の調査結果を待ってから2番を実装するか、それとも先に暫定対応として2番を入れておくかは、調査報告を見てこのチャットで判断する。**このため、2番の実装は保留し、1番(一括支出計上)のみ先に進めてよい。**

新規フィクスチャの追加(繰上返済年の一括支出反映確認)も、1番の実装と合わせて行うこと。
