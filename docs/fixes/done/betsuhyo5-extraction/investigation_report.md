## 1. XML取得方法・別表第五ノードの構造サマリー

### 取得方法
e-Gov法令API v2(2025年3月公開、`https://laws.e-gov.go.jp/api/2/swagger-ui`)の
`GET /api/2/law_data/{law_id}` エンドポイントで取得した。

```
https://laws.e-gov.go.jp/api/2/law_data/340AC0000000033?response_format=xml
```

- `law_id=340AC0000000033`(所得税法、昭和四十年法律第三十三号)
- レスポンスは`<law_data_response>`というJSON的な包み構造(実体はXML)で、
  `<law_info>`(法令基本情報)・`<revision_info>`(改正・施行情報)・`<law_full_text>`
  (実際の法令本文、Diet標準の法令XMLスキーマ)の3部構成。ファイルサイズ約16.4MB。
- ダウンロードした生ファイルは `betsuhyo5-extraction/raw-data/shotokuzei_raw.xml`
  (2026-08-13追記:`.gitignore`に`docs/fixes/**/raw-data/`を追加し、`raw-data/`配下は
  commit対象外にした。スクリプト(`extract_betsuhyo5.py`・`check_boundaries.py`)から
  e-Gov法令API v2で再取得可能なため)。

### 別表第五ノードの構造
`<law_full_text>`内、`<AppdxTable>`要素として1つだけ存在する(`<AppdxTableTitle>別表第五</AppdxTableTitle>`、
`<RelatedArticleNum>年末調整等のための給与所得控除後の給与等の金額の表(第二十八条、第百九十条関係)</RelatedArticleNum>`)。

- 内部は`<TableStruct>`(サブテーブル、`<TableStructTitle>`が（一）〜（八）の8個)で構成
- 各`<TableStruct>`は`<Table>`→`<TableRow>`→`<TableColumn>`の入れ子。1サブテーブルあたり
  `<TableRow>`が62個(ヘッダー3行+データ59行)、8サブテーブル合計で**496個**の`<TableRow>`
- **表形式**(colspan/rowspanを使う本格的な表組み)。セル結合が多用されている:
  - 冒頭行:「651,000円未満→0円」がcolspan="2"で結合された1セル
  - 「651,000円以上1,900,000円未満」の行は、結果セルが`rowspan="3"`で
    「給与等の金額から650,000円を控除した金額」という**数値ではなく計算式のテキスト**になっている
    (この区間は定額控除なので、1円単位で列挙せず数式表記で済ませている)
  - それ以外の区間(1,900,000円超〜6,600,000円)は、4,000円刻みで「以上/未満/控除後の金額」を
    数値で列挙する本来の表形式
- **紙面節約のための3列並列レイアウト**:1つの`<TableRow>`に「給与等の金額(以上/未満)+控除後の金額」の
  組が横に3セット並んでいる。ただしこの3セットは同一行内で連続する収入区分ではなく、
  ページ内で縦方向に並ぶ3本の帯(バンド)がそれぞれ独立した収入区分の連続列であり、
  3つを横に並べて印刷紙面を節約しているだけ(いわゆる新聞の段組と同じ発想)。
  そのため、単純に「1行=3件のデータ」として機械的に読み進めると、収入額が正しい昇順に
  並ばない(帯をまたいで前後関係が崩れる)。

## 2. 施行日バージョンの調査結果

- 取得したXMLの`<revision_info>`は`current_revision_status: CurrentEnforced`、
  `amendment_enforcement_date: 2026-08-12`(問い合わせ日と一致)であり、
  **API既定のクエリ(日付指定なし)は「問い合わせ時点で施行中の版」を1つだけ返す**設計になっている
  ことを確認した。`law_revision_id`にも`340AC0000000033_20260812_508AC0000000064`のように
  施行日相当の日付が版として組み込まれている。
- 取得したXML全体を検索したところ、`別表第五`という文字列は56箇所に出現するが、
  `<AppdxTableTitle>別表第五</AppdxTableTitle>`(＝別表そのものの見出し)は**1箇所のみ**。
  つまり、**新旧複数バージョンの別表第五が1つのレスポンス内に併存することはない**。
- 内容面でも、控除の最低保証額が「650,000円」であることを本文中の計算式テキスト
  (「給与等の金額から650,000円を控除した金額」)で直接確認した。旧版(令和7年11月30日以前施行、
  最低保証額550,000円)の記述は見当たらない。→ **令和7年12月1日施行版(現行)であることを確認済み**。
- 結論:併存の心配は不要。ただし「今取得した版が常に最新か」は問い合わせ時点に依存するため、
  実装する場合は取得のたびに`revision_info`の`amendment_enforcement_date`をログ等に残し、
  税制改正のたびに再取得・再検証する運用が前提になる。

## 3. 全行抽出の可否

**プログラムでの抽出は可能だが、「1行=1件のデータ」という単純な走査では成立しない**(上記1.の
3列並列レイアウトのため)。正しく抽出するには、各`<TableStruct>`ごとに3本の帯を分離し、
帯ごとに縦方向へ独立して読み進める必要がある。加えて、先頭区間(651,000円未満・651,000円〜
1,900,000円)は数値ではなく計算式テキストのため、通常の数値パースとは別に特別扱いが要る。

### 構造から算出した件数(実際に全帯を正しく分離して数え上げたわけではなく、行数×帯数から算出した理論値)
- サブテーブル（一）:データ行59行のうち、帯1(左端)は「651,000円未満」1件+
  「651,000〜1,900,000円」の計算式1件=実質2件のみ(以降はrowspanで空欄になり打ち切り)。
  帯2・帯3はフルに59件ずつ稼働。→ (一)の実質件数 ≈ 2+59+59 = **120件**
- サブテーブル（二)〜（八)(7個):特殊区間なし、3帯とも59件ずつフル稼働。
  → 各 59×3 = 177件、7個で **1,239件**
- 合計理論値:120+1,239 = **約1,359件**(651,000円未満・651,000〜1,900,000円の2区間+
  1,900,000円〜6,600,000円を4,000円刻みで列挙した件数)

(参考:機械的に「1行=3件」で単純分割した一次試行スクリプト`extract_betsuhyo5.py`では
1,193件が抽出されたが、上記の帯またぎ・colspan結合の影響で収入額の前後関係が
一部崩れており、この1,193という値自体は正しい行データとしては使えない。上記1,359が
構造から見積もった参考値であり、これも「実際に3帯を正しく分離・結合して検証した」
数値ではない点に注意。全行を正しい順序で機械抽出するには帯の継ぎ目を解決する追加実装が必要)

### 抽出データのサンプル(先頭・末尾、境界値照合で個別に確認した行)
- 先頭:「651,000円未満」→0円
- 2件目:「651,000円以上1,900,000円未満」→「給与等の金額から650,000円を控除した金額」(計算式)
- 3件目以降(1,900,000円超):「1,900,000円以上1,904,000円未満」→1,250,000円 のように
  4,000円刻みで数値が列挙される
- 末尾:表全体の最後の数値は「6,600,000」(＝表がカバーする上限、国税庁No.1410の
  「収入金額660万円未満」という説明と整合)

## 4. 代表収入額・境界値5点以上での照合結果

`check_boundaries.py`で、対象の収入額を含む行を直接検索し、その行が実際にどの4,000円区分
(「以上」の値)に対して計算されているかを特定した上で、本ツールの`calcSalaryIncomeDeduction()`
と同一の式をその「以上」値に適用して突き合わせた。**8点全て完全一致**。

| 収入額(円) | 別表第五の該当区分(以上) | 別表第五の控除後金額 | 本ツールの式で同じ「以上」値を計算した結果 | 一致 |
|---|---|---|---|---|
| 1,900,000(区分境界) | 1,900,000 | 1,250,000円 | 1,250,000円 | ✅ |
| 1,904,000 | 1,900,000(その次の区分の起点相当) | 1,250,000円 | 1,250,000円 | ✅ |
| 3,000,000 | 2,996,000 | 2,017,200円 | 2,017,200円 | ✅ |
| 3,600,000(区分境界) | 3,596,000 | 2,437,200円 | 2,437,200円 | ✅ |
| 4,000,000 | 3,996,000 | 2,756,800円 | 2,756,800円 | ✅ |
| 5,000,000 | 4,996,000 | 3,556,800円 | 3,556,800円 | ✅ |
| 6,000,000 | 5,996,000 | 4,356,800円 | 4,356,800円 | ✅ |
| 6,600,000(表の上限・区分境界) | 6,596,000 | 4,836,800円 | 4,836,800円 | ✅ |

さらに651,000円未満(→0円)、651,000円〜1,900,000円(→「収入−650,000円」)の2区間も、
本ツールの実装(この範囲は一律650,000円控除)と文言レベルで完全に一致することを確認した。

### 重要な発見:「近似」ではなく「4,000円区分への丸め方」の差でしかない
別表第五は、4,000円幅の区分ごとに、その区分の**下限額(「以上」の値)を使って速算式を1回だけ
計算し、その結果を区分全体(4,000円分)に一律適用する**、階段状(ステップ関数)の表である。
一方、本ツールの`calcSalaryIncomeDeduction()`は同じ速算式を**収入額そのものに連続的に**適用する。
つまり式自体は完全に同一で、差が生じるとすれば「4,000円区分のどこに実際の収入額が
位置するか」による丸め差のみであり、その最大値は理論上
「区分幅4,000円 × 適用税率」で頭打ちになる(30%区分で最大1,200円程度、20%区分で最大800円程度、
10%区分で最大400円程度、650,000円定額区間・850万円超の195万円上限区間は差ゼロ)。
これはCLAUDE.md/コード内コメントに記載していた「別表第五との差は数百円未満」という
記述を、実際の一次データで裏付け・定量化できたことを意味する。

## 5. 実装方針への所見

**結論:抽出自体は技術的に可能だが、投資対効果に見合わない。現行の速算表近似を継続することを推奨する。**

理由:
1. 4.の照合により、速算表近似は別表第五と**式レベルで同一**であり、差は4,000円区分への
   丸めに起因する最大数百円(30%区分で最大1,200円)の誤差にとどまることが定量的に確認できた。
   この誤差は「退職後の住民税キャッシュフロー試算ツール」のような概算ツールの用途では
   実務上ほぼ無視できる水準。
2. 一方、別表第五を正しく機械抽出するコストは小さくない:
   - 3本の帯(バンド)を分離して縦方向に読み進めるロジックが必要(帯またぎの継ぎ目処理)
   - 冒頭の2区間(650,000円未満・650,000〜1,900,000円)は数値ではなく計算式テキストのため、
     結局この部分は静的テーブル化できず、何らかのハードコードされた特別処理が要る
     (＝別表第五を使っても、この区間だけは今の速算表方式と同じことをする必要がある)
   - 抽出したデータをどう保守するかという運用コストが増える(次回改正時に再度この
     複雑な抽出ロジックを検証し直す必要がある)
3. 速算表近似を続ける場合の対応は、コード内コメント・ツールのUI注記(既に実装済み)で
   「別表第五との差は最大数百円程度」という定量的な説明に更新する程度で十分。

**もし将来的に厳密な別表第五準拠が必要になった場合の代替案(今回は実装しない、所見のみ):**
- 全区間を静的テーブル化するのではなく、**650,000円未満・650,000〜1,900,000円の2区間だけは
  現行の速算表ロジックのまま**にし、1,900,000円超〜6,600,000円の範囲のみ4,000円刻みの
  ステップ関数(丸め処理)を追加する部分的な対応であれば、抽出・保守コストを抑えつつ
  最後の数百円のズレも解消できる可能性がある(ただし今回は判断材料の提示のみに留める)。
- 静的データとして固定する場合、抽出スクリプト自体は`reference/`配下相当の場所に保存し、
  次回税制改正時に再実行して差分を目視確認する運用が現実的(自動再生成パイプラインは
  過剰、というのがこの調査を踏まえた所見)。

## 付記:作業中に判明した実装上の注意点(次回同種の調査・実装で役立つ内容)

- Windows環境でPythonの標準出力を`>`でファイルにリダイレクトすると、既定でcp932(Shift-JIS)
  エンコーディングで書き出され、日本語が文字化けする。`open(..., encoding='utf-8')`で
  明示的にファイルへ書き込む必要がある(本調査の`check_boundaries.py`で対応済み)。
- e-Gov法令API v2の`law_data`エンドポイントはXML全文が16MB超と大きいため、実装時に
  毎回フル取得するのではなく、別表部分だけを抽出してキャッシュする設計が望ましい。
