# 調査指示書:配偶者iDeCo設定変更で本人のiDeCo受取額(手取り)が変動する疑い

**種別:調査のみ(実装はしないこと)**
**背景:** KPIカード「iDeCo受取(手取り)」(本人のみの値のはず。内訳カードの「本人」欄と一致する数値)が、配偶者のiDeCo設定(残高・加入年数・受取方式・受取開始年齢)を変更しただけで変動する現象をKENZOが発見。本人・配偶者の計算は独立しているべきだが、Stage Bで発見した「配偶者残高の強制合算」と同種のクロスコンタミネーションが別の箇所にも残っている可能性がある。

---

## 再現条件(報告より)

- 変更前:配偶者のiDeCo関連設定が全て0/未設定
- 変更後:配偶者のiDeCo残高300万円、iDeCo加入年数10年、iDeCo受取方式=年金、iDeCo受取開始60歳を設定
- 結果:本人の「iDeCo受取(手取り)」(見出しカード、`idecoTotalNetWithdrawal`相当)の値が約34万円増加した

本人側のパラメータは一切変更していない前提。もし本人側パラメータも同時に変更していた場合は、その点も含めて再現条件を確認すること。

---

## 調査してほしいこと

### 1. 本人の`idecoTotalNetWithdrawal`(またはこれに相当する値)の算出経路を洗い出す
- `analyze.ts`内で本人のiDeCo手取り額を算出する関数・変数を特定する
- その算出に使われている入力(`snaps`の各年次スナップショット、`idecoAnnualGross`、`idecoTaxPaid`等)が、**配偶者のフィールドを一切参照していないか**を確認する

### 2. `simulate.ts`内の本人iDeCo処理ブロックが配偶者パラメータを参照していないか確認する
- 本人の年金受取ブロック・一時金受取ブロックの中に、`p.spouse?.xxx`のような配偶者パラメータへの参照が紛れ込んでいないか
- 特に、Stage Bで発見した「配偶者残高の強制合算」ロジックのように、**本人側の処理が配偶者側の状態(受取開始済みかどうか等)を条件分岐に使っている箇所がないか**

### 3. 累計課税額(`idecoTotalTax`)の算出が影響していないか確認する
- 以前の調査(累計課税額のロジック検証)では、本人の`calcPensionTaxDiff`は本人自身の年金額のみを参照し配偶者は無関係と確認済みだが、**今回の34万円の変動がこの累計課税額側の変化に起因していないか**、`idecoTotalNetWithdrawal = idecoTotalGross - idecoTotalTax`のような差し引き計算のどこかに配偶者由来の値が紛れていないか、あわせて確認する

### 4. 数値を実測し、原因箇所を特定する
- 上記再現条件を実際に再現し、本人の`idecoTotalNetWithdrawal`(および関連する中間変数)が配偶者設定変更の前後でどう変わるか、変数単位でログ出力し比較すること
- 変動が発生している場合は、どの中間変数から値がズレ始めているかを特定すること
