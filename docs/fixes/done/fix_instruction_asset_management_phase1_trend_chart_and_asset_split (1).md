## 1. 【最優先・重大】Export時のファイル名に内部コードネーム「LifeCompass」が混入している

JSON Exportで生成されるダウンロードファイル名が `lifecompass_assets_2026-08-18.json` のように、内部の開発コードネーム「LifeCompass」を含んだ状態でユーザーに渡っていることが確認された。

このプロジェクトでは、内部開発コードネーム「LifeCompass」はユーザー向けのテキスト・URL・ファイル名など、外部に見える箇所に一切表示してはならないというルールがある。ダウンロードファイル名はユーザーが直接目にし、場合によっては人に共有する可能性もある箇所のため、これは軽微な表示崩れではなく**ブランド漏洩の重大な不具合**として最優先で対応すること。

### 1.1 対応内容

1. まず、Export機能（JSON Export／CSV Export）のファイル名生成箇所を横断的に検索し、「lifecompass」「LifeCompass」等の文字列がファイル名やその他のユーザー向け出力に含まれていないか確認する（本ツール以外の既存Export機能にも同様の問題がないか、念のため確認すること）
2. ファイル名を、サイトのユーザー向けブランド名に沿った命名に変更する（例：`freenough-assets-2026-08-18.json`、`資産管理_2026-08-18.json`など。具体的な命名は既存の他のExport機能（あれば）の命名規則があればそれに合わせ、なければkebab-case・半角英数字ベースで違和感のない名称にすること）
3. CSV Exportのファイル名についても同様に確認・修正すること
4. 修正後、実際にダウンロードされるファイル名を完了報告に明記すること

### 1.2 検証

- JSON Export・CSV Exportそれぞれでダウンロードされるファイル名に「lifecompass」の文字列が一切含まれていないことを実機で確認する
- ソースコード全体（`grep -ri lifecompass` 等）で、本ツール関連のユーザー向け出力箇所に同様の混入がないか横断確認する

## 2. CSV Importの追加（自社フォーマット限定）

現状CSV Exportのみでインポートがない状態だが、これは意図的な仕様（Export/Importロードマップの段階Aでは「JSON Export/Import＋CSV Export」のみとしていたため）。ただし、以下の理由から**自社のCSV Exportと同じ列レイアウトのCSVを読み込むImport機能**は、今回の段階Aに含めて実装する。

### 2.1 スコープの整理（重要）

- **今回実装する**：自社のCSV Exportが出力する列構成と完全に一致するCSVのみを読み込むImport。列の意味が事前に分かっているため、ユーザーによる手動カラム対応付けUIは不要
- **今回実装しない（段階B・将来）**：任意フォーマットのCSVをアップロードし、ユーザーが手動で列を対応付けるUI
- **今回実装しない（段階C・将来）**：楽天証券等、証券会社の出力ファイルを自動認識してインポートする機能

段階B・Cの検討状況（マッピングUIの必要性、証券会社ごとのフォーマット差異への対応コスト等）は変更しない。今回追加するのはあくまで「自社フォーマットとの往復」に限定したシンプルな機能。

### 2.2 実装内容

- 「CSVをインポート」ボタンをExport/Importコントロール内、既存のJSON Import・CSV Exportボタンと並べて配置する
- CSVのヘッダー行が、既存CSV Exportの出力列と完全に一致するかを検証する。一致しない場合は「対応していないCSV形式です」等、分かりやすいエラーメッセージを表示し、取り込みを中断する（部分一致や曖昧な列推測は行わない。それは段階Bのスコープ）
- ヘッダーが一致した場合、CSVの各行を`AssetHolding`にパースし、**JSON Importで既に実装済みのid基準マージロジックをそのまま再利用**する（新たにマージロジックを実装し直さない）
- CSV Exportの出力対象が`AssetHolding[]`のみ（スナップショットは含まない）であることに合わせ、CSV Importも同様に保有資産（holdings）のみを対象とする。スナップショットの読み込みは引き続きJSON Import側の役割とする

### 2.3 検証

- 自社のCSV Exportで出力したファイルをそのままCSV Importで読み込み、正しく`AssetHolding`として復元されることを確認する
- ヘッダーが一致しない（列が欠けている、順序が違う等）CSVを読み込ませた場合に、エラーメッセージが表示され、データが不正な形で取り込まれないことを確認する

### 2.4 Export/Importボタンのレイアウト再編成

CSV Import追加にあわせて、Export/Importコントロール全体のレイアウトを見直す。現状「JSONでエクスポート／CSVでエクスポート／JSONをインポート」が横一列にフラットに並んでいるが、以下の2ボックス構成に変更する。

- **左側のボックス「JSON」**：「JSONでエクスポート」「JSONをインポート」の2ボタンを内包。キャプション（例：「保有資産・記録履歴すべてを含む完全バックアップ」）を添える
- **右側のボックス「CSV」**：「CSVでエクスポート」「CSVをインポート」の2ボタンを内包。キャプション（例：「保有資産のみ。表計算ソフトでの確認・編集用」）を添える

配置は**左＝JSON、右＝CSV**の順とする。理由：JSON Exportは保有資産＋記録履歴（スナップショット）を含む完全なバックアップである一方、CSV Exportは保有資産のみで記録履歴を含まない非対称な関係にあるため、まず完全バックアップであるJSONを主導線として左（先）に置き、CSVは「保有資産データを外部の表計算ソフトで編集してサイトに反映する」ための補助的な導線として右（後）に置く。

ユーザーの想定利用フロー（参考）：JSONで現在の状態を丸ごと保存・復元する／CSVでダウンロードして保有資産データを表計算ソフト上で更新し、CSV Importでサイトに反映する／反映後、改めてJSON Exportで完全な状態を保存し直す。この2つの使い分けが伝わるよう、キャプションの文言を工夫すること（上記の文言例は目安であり、より分かりやすい表現があれば調整してよい）。

## 3. 資産推移セクションに折れ線グラフを追加

現状「資産推移」セクションはテーブル（記録日／資産合計額）のみだが、**総資産額の推移を示す折れ線グラフ**を追加すること。

### 3.1 仕様

- X軸：記録日（`YYYY-MM`）、Y軸：資産合計額（`totalAmount`）の折れ線グラフ
- Rechartsを使用し、既存の円グラフと同様`next/dynamic`＋`{ ssr: false }`の動的importパターンを踏襲する
- 表示位置：既存の「資産推移」テーブルと同じセクション内（テーブルの上または下、どちらでも実装しやすい方でよい）
- スナップショットが**2件未満**の場合、折れ線グラフは意味を持たない（点が1つ、または0個）ため、グラフの代わりに「記録を重ねると推移がグラフで確認できます」等のメッセージを表示すること
- スナップショットが2件以上になったら通常通りグラフを描画する

### 3.2 検証時のテストデータ準備方法

同じ月に複数回「記録する」を押しても、`date`（`YYYY-MM`）をキーに上書きされる設計のため、1つの月内では複数点を作れない。動作確認のため、以下いずれかの方法でテストデータを用意すること：

- **推奨**：既存のJSON Export機能でエクスポートしたファイルを編集し、`snapshots`配列に過去の月（例：`2026-03`〜`2026-07`）のダミーエントリを追加した上でJSON Importで読み込む。既存のExport/Importコードパスをそのまま使うため、実装に手を加える必要がない
- 上記が難しい場合、開発時のみブラウザDevToolsコンソールから該当localStorageキーに直接複数件の配列をセットしてもよい（本番コードには影響しない一時的な検証手段として）

完了報告には、実際にどちらの方法で複数点のグラフ描画を確認したか明記すること。

## 4. 【バグ修正・最優先】JSON Import時のスナップショットが重複する

実機検証中、同じ`date`（例：`2026-08`）を持つスナップショットをJSON Importで複数回取り込むと、上書きされず**単純に配列へ追加され、同じ月のエントリが複数件残る**ことが確認された（実機で`2026-08`が3行に重複）。

前々回の完了報告では「`AssetSnapshot`は`date`（自然キー）で一致→上書き、不一致→新規追加」という実装内容が報告されていたが、実際の挙動と一致していない。以下の対応を行うこと：

1. まず`exportImport.ts`（または該当ファイル）の現在のImportロジックを確認し、報告内容と実際の挙動が食い違っている原因を特定する（例：マージ処理自体が呼ばれていない、`date`の比較条件に不具合がある、等）
2. `date`が一致するスナップショットは**上書き**、一致しないものは**新規追加**という、当初の意図通りの挙動に修正する
3. 修正後、同じ月のデータを含むJSONを複数回Importしても、その月のエントリが1件のみになることを実機で確認する
4. 併せて、既存の重複データ（この修正前にImportで生まれた重複行）をどう扱うかも報告に含めること（ユーザーの実データを勝手に削除しない方針は維持しつつ、明らかな同一日付の重複について、UIやデータ整理でどう扱うのが妥当か所見を添えてよい）

この修正は、3章の折れ線グラフ機能の動作検証（複数月分のテストデータをImportで用意する）の前提条件になるため、**先に対応すること**。

## 5. 「その他」カテゴリの資産クラスを4択に分割

現在「その他（暗号資産・保険等）」として1つにまとめている資産クラスを、以下の4択に分割する。

### 5.1 新しい選択肢構成

| 選択肢 | 内部値（例） | 用途 |
|---|---|---|
| 不動産 | 既存の`不動産`のまま | 現物不動産等（変更なし） |
| 暗号資産 | 新規（例：`暗号資産`） | ビットコイン等の暗号資産 |
| 保険 | 新規（例：`保険`） | 貯蓄性保険等 |
| その他 | 既存の`その他`のまま、**表示ラベルは元の「その他」に戻す** | 企業型DC・財形貯蓄等、上記に当てはまらない汎用の受け皿 |

### 5.2 理由（背景）

将来、この資産管理ツールで扱っている資産クラスを既存シミュレーター側（`profile.ts`のASSET_CLASSES、別タスク）に反映する際、暗号資産と保険とでは期待リターン・ボラティリティの前提が大きく異なる。1つの選択肢にまとめたままだと将来分離できなくなるため、今のうちに項目として独立させておく。

### 5.3 実装内容

- `categories.ts`の資産クラス一覧に`暗号資産`・`保険`を追加（既存15種→17種）
- `ALLOWED_ASSET_CLASSES_BY_CATEGORY`の「その他」カテゴリの許可リストを`['不動産', '暗号資産', '保険', 'その他']`に更新
- `getAssetClassLabel`の「その他」特別変換（「その他（暗号資産・保険等）」表示）は不要になったため削除し、内部値`その他`はそのまま「その他」と表示する形に戻す
- 不動産・その他と同様、暗号資産・保険もmu/sigma/group（期待リターン等）は意図的に未設定でよい（本ツールは将来予測を行わないため）
- `classColors.ts`の`ASSET_CLASS_COLOR_MAP`に、暗号資産・保険それぞれの固定色を追加すること。既存の8色（検証済みパレット）とは別に、既存の補助色（不動産・その他・現金等）と同様の考え方で、視認性を確保した色を選定してよい。凡例・色ドット・ツールチップという二次エンコーディングが常にセットで表示される前提を維持すること
- 既存データ（この変更前に保存された`その他`のholdings）は変更・強制移行しない。ユーザーが今後編集する際に新しい選択肢が適用される

## 7. 検証要件

1. JSON Export・CSV Exportのファイル名に「lifecompass」が一切含まれていないこと（1章）
2. 自社CSV Exportで出力したファイルがCSV Importで正しく復元されること、非対応形式のCSVではエラー表示になること（2章）
3. Export/Importボタンが「左＝JSON（2ボタン＋キャプション）／右＝CSV（2ボタン＋キャプション）」の2ボックス構成で表示されること（2.4節）
4. JSON Importで同じ`date`のスナップショットを複数回取り込んでも、重複せず1件に上書きされること（4章）
5. スナップショットが2件未満のときは折れ線グラフの代わりにメッセージが表示されること
6. 3.2の方法でテストデータを用意し、スナップショットが2件以上ある状態で折れ線グラフが正しく描画されることを確認
7. 「その他」カテゴリのドロップダウンが「不動産／暗号資産／保険／その他」の4択になっていること
8. 円グラフ・凡例・両テーブル（資産クラス内訳／資産配分の変化）すべてで、暗号資産・保険それぞれに固定色が割り当てられ、表示箇所間で色がズレていないこと
9. 「資産配分の変化」テーブルの各行に色ドットが表示されていること
10. `tsc --noEmit` / `npm run build` / `full-verify.js` が引き続きクリーンであること
11. ロックファイルへの差分が引き続きゼロであること
