## 1. 現金カードの追加（バグ修正）

- `ACCOUNT_CATEGORIES`（`categories.ts`）に定義されているはずの「現金」が、`AssetManagementPage.tsx`側のレンダリングから漏れている。5カテゴリすべて（現金／NISA／iDeCo／特定口座／その他）が表示されるよう修正すること
- **現金カードは他カテゴリと異なり、資産クラスの選択UIを持たない**：
  - 入力は金額のみ（既存の資産シミュレーター側UIの「現金残高」と同じ扱い）
  - 内部データ上は`AssetHolding`の`assetClass`に固定値（例：`'現金'`）を設定してよい。ただしこの固定値は2章の資産クラス一覧（`ASSET_CLASSES`）には追加しない、現金カード専用の特別値として扱うこと
  - 円グラフ（資産クラス内訳）には「現金」として他の資産クラスと並べて表示する
- 前回の完了報告で保留になっていた「現金カテゴリの新規行デフォルト資産クラス＝短期債・MMF」という論点は、この変更により解消される（資産クラス選択自体が不要になるため）

## 2. レイアウトのレスポンシブ対応

### 2.1 デスクトップ（目安：768px以上）

既存の資産シミュレーター（`/asset-simulator/`本体）と同じ左右2カラム構成にする：

- **左サイドバー**：カテゴリ別入力カード（現金／NISA／iDeCo／特定口座／その他）。常時展開（折りたたみなし）。既存シミュレーターの左サイドバーと同様、独立スクロール可能な領域にする
- **右メイン**：FIRE進捗パネル・円グラフ（資産クラス内訳）・資産配分の変化テーブル・Export/Importコントロール
- 入力値の変更は右メインにリアルタイム反映されること（既存シミュレーターの「変更→即座に反映」という体験を踏襲する）

### 2.2 モバイル（目安：768px未満）

- **上部**：カテゴリ別入力カード。初期状態は折りたたみ（collapsed）。各カードは折りたたみ時「カテゴリ名＋合計金額＋開閉アイコン」の1行表示（例：`NISA　合計: 1,200万円　▼`）、タップで展開すると資産クラス別の内訳行・追加ボタンが表示される
- **下部**：FIRE進捗パネル・円グラフ・資産配分の変化テーブル・Export/Importコントロール（デスクトップと同じ内容・同じ順序）

### 2.3 実装方針

- 「入力カード群」コンポーネントと「サマリー群」コンポーネントを分離し、CSSブレークポイント（既存コードベースのブレークポイント定義があればそれを踏襲）で配置を切り替える設計にすること
- 無理に単一の共通コンポーネントに両パターンを詰め込まず、配置（左右 or 上下）と折りたたみの有無をブレークポイントで出し分ける形でよい
- `AssetHoldingCard.tsx`は「常時展開」と「折りたたみ可能」の両方の見た目を扱える設計にする（props等で開閉状態を制御できるようにする）

### 2.4 参考にすべき既存実装（重要）

デスクトップの左右2カラム構成・独立スクロール領域・折りたたみブロック（例：既存シミュレーターの「詳細指標」の開閉パターン）は、ゼロから設計せず、**既存の資産シミュレーター本体の実装を参照して踏襲すること**。具体的には：

- 既存シミュレーターのメインページのレイアウトコンポーネント（左サイドバー／右メインの分割方法、各カラムのCSS・スクロール設定）
- 「詳細指標」等、既存にある折りたたみUIパターン（開閉アイコン・アニメーション・状態管理の実装方法）
- 使用しているブレークポイント定義（既存のTailwind設定等があればそれに合わせる。新たに独自のブレークポイント値を定義しない）

**参照はあくまで「読んでパターンを踏襲する」ことが目的で、コンポーネントやロジックを直接importしてはならない**（0章のロックファイル制約と同じ考え方）。CSSのユーティリティクラスやTailwind設定など、プロジェクト共通の定義を使うのは問題ないが、`PortfolioPanel.tsx`や`simulatorStore.ts`等のロックファイルにあるコンポーネント・stateロジックを資産管理ツール側からimportすることは引き続き禁止。

見た目・操作感を既存シミュレーターに近づけることで、「同じサイトの別ツール」という一貫性を持たせるのが目的である旨、実装時に意識すること。

## 3. カテゴリ×資産クラスの選択制約

### 3.1 資産クラス一覧の追加

`categories.ts`の資産クラス一覧に、新規で **「その他」資産クラス**を1件追加する（既存10件＋不動産＋その他＝合計12件）。

- 用途：暗号資産・貯蓄性保険・企業型DC/財形貯蓄など、既存資産クラスに対応しない保有資産の受け皿
- 不動産と同様、期待リターン・ボラティリティ・相関係数（mu/sigma/group）は意図的に未設定でよい（本ツールは将来予測を行わないため）

### 3.2 カテゴリごとの選択可能資産クラス（確定）

| 口座カテゴリ | 選択可能な資産クラス |
|---|---|
| 現金 | なし（1章の通り、金額のみ） |
| NISA | 標準10資産クラスのみ（不動産・その他は選択不可） |
| iDeCo | 標準10資産クラスのみ（不動産・その他は選択不可） |
| 特定口座 | 標準10資産クラスのみ（不動産・その他は選択不可） |
| その他 | 不動産／その他（新設）の2択のみ（標準10資産クラスは選択不可） |

### 3.3 実装方法

- `categories.ts`等に、カテゴリ→選択可能資産クラスのマッピング定数を新設する（例：`ALLOWED_ASSET_CLASSES_BY_CATEGORY`）
- `AssetHoldingCard.tsx`の資産クラスドロップダウンは、このマッピングに基づいて選択肢をカテゴリごとにフィルタリングすること
- 既存データ（この制約導入前に保存されたholdings）が制約外の組み合わせ（例：iDeCo×不動産）を持っていた場合の扱い：
  - データ自体は削除・強制変更しない（ユーザーの入力データを勝手に書き換えない）
  - 表示上は許容し、編集時に選択肢を変更する場合のみ新しい制約が適用される、という挙動でよい
  - 明らかに不整合な組み合わせがある場合、警告表示（任意、必須ではない）を検討してもよいが、必須要件ではない

前回指示書の検証要件（9章）に加えて、以下を確認すること：

1. 現金カードが表示され、金額入力のみでUIが完結すること（資産クラス選択UIが出ないこと）

5. `tsc --noEmit` / `npm run build` / `full-verify.js` が引き続きクリーンであること
6. ロックファイルへの差分が引き続きゼロであること
