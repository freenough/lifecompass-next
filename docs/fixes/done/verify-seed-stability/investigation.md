# 調査指示：`full-verify.js`で偶発的にFAILが出る原因の特定（現状調査）

作成日：2026-09-26
種別：**調査のみ（コード変更・コミット・push禁止）**
配置：`lifecompass-next/docs/fixes/active/verify-seed-stability/investigation.md`

---

## 背景

`full-verify.js`は、完了報告のたびに「PASS件数/FAIL件数」として提示され、実装が正しいことの根拠として扱われている。ところが、同じコードのまま再実行しても、実行のたびにFAILの件数が変わることがある（偶然FAILが出る）。

原因として疑われるのは、モンテカルロシミュレーション（`runMC()`等、資産寿命の破綻確率を計算する処理）が`Math.random()`のような非決定的な乱数を使っており、検証スクリプトがその結果に対して固定の期待値（例：破綻確率は◯%であること）をassertしている場合、実行のたびに結果が微妙にぶれてFAIL/PASSが変わる、というものである。

これが起きていると、次の問題がある。

- 「full-verify.js全PASS」という完了報告の信頼性が損なわれる（今回のFAILが、直した実装のせいなのか、単なる乱数のブレなのか区別できない）
- CIやStop Hookで強制している「常にPASSであること」という前提が崩れる

今回は、原因を正確に特定し、対処方針を決めるための調査を行う。**この時点でコードの修正は行わない。**

## 調査項目

### 1. 乱数の発生源の洗い出し

`src/`配下（`lifecompass-next`のみでよい。`runMC`・モンテカルロ関連のロジックがこのリポジトリにのみ存在する前提。もし`freenough-main`にも存在すれば、そちらも対象に含める）で、`Math.random()`または他の非決定的な乱数生成（`crypto.getRandomValues()`等）を使っている箇所をすべて洗い出す。

各箇所について、次を報告する。

- ファイル:行
- 何のために使っているか（モンテカルロの1試行ごとのランダムウォーク、など）
- シードを受け取る引数があるか、完全に内部で`Math.random()`を直接呼んでいるか
- 呼び出し元をたどり、本番の`simulate()`/`analyze()`/`runMC()`など、記事の数値算出にも使われる共通関数かどうか（`technical-principles.md`のルール「確定数値は本番関数を直接呼ぶ」に関わるため）

### 2. `full-verify.js`と関連する`verify-*.js`のうち、乱数に依存する検証の洗い出し

`scripts/verify-*.js`・`scripts/full-verify.js`の中で、モンテカルロの結果（破綻確率、資産寿命の分布など）に対して数値の一致や範囲をassertしているテストを洗い出す。

各テストについて、次を報告する。

- ファイル:行、テスト名
- 期待値の種類（完全一致か、許容範囲を持たせたレンジ判定か）
- 実際に複数回（10回程度）連続実行し、FAILになる頻度・FAILしたときの実測値と期待値の差を記録する

### 3. 再現の実測

`npm run` 等で、同一コード・同一入力のまま`full-verify.js`を10回連続実行し、各回のPASS/FAIL件数を記録する。ばらつきが確認できれば、その回のログ（FAILしたテスト名と実測値）を`report.md`に添付する。ばらつきが確認できない場合も、10回分の結果をそのまま報告する（「再現しなかった」という事実も重要な調査結果）。

### 4. 対処方針の選択肢の整理（提案。事実とは分けて書く）

次のような選択肢が考えられるが、それぞれの実現可能性・影響範囲をコードから調べ、提案として記載する。事実の調査結果と混在させないこと。

- **選択肢A：乱数生成にシード付きの疑似乱数（seedable PRNG）を導入し、`verify-*.js`からは固定シードで呼び出す。** 本番のUIやブログ記事算出では、従来通りシードなし（真にランダム）で動作させる。実装への影響範囲（`runMC()`等のシグネチャ変更が本番コードに及ぶか）を調べる
- **選択肢B：乱数を使うテストのassertionを、完全一致ではなく統計的に妥当な許容範囲（例：理論値±3標準偏差）に緩める。** シミュレーション試行回数と許容範囲の関係も含めて検討する
- **選択肢C：乱数を使うテストだけ`full-verify.js`から分離し、別枠で「参考値」として扱う（PASS/FAIL判定から除外する）**

各選択肢について、実装の手間（触るファイル数、ロックファイルに該当するか）とリスク（本番の乱数の質に影響しないか）を簡潔に記す。
