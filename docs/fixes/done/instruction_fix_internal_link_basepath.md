# 指示書:ブログ内部リンクのbasePath欠落バグ 根本修正

## 背景

`src/lib/blog.ts`の`applyBasePathToHtml()`は、画像の`src="/images/..."`には
`/asset-simulator`を自動付与しているが、リンクの`href`は対象外になってい
る。このため、記事のMarkdown内で`/blog/xxx`のようにprefixなしで内部リンク
を書くと、本番で実際に404になることが実機確認済み(`fire-checklist.md`内
の`/blog/montecarlo-simulation`等で確認)。

一方、`ideco-nisa.md`のように、執筆時点で手動により`/asset-simulator/...`
とprefix付きで書かれている記事も存在する。単純に全てのリンクへ機械的に
prefixを追加すると、こうした記事で**二重付与**(`/asset-simulator/asset-
simulator/...`)が発生し、別の404を生み出してしまう。

そのため、本タスクは「調査(棚卸し)→実装→検証」の順で進める。**調査結果
を報告した時点で一度立ち止まり、想定外の内容(下記チェック項目に当ては
まらないパターン等)が見つかった場合はプランニングチャットに報告し、実装
は保留すること。**

## Phase 1:調査(棚卸し)

`src/content/blog/`配下の全Markdownファイルを対象に、本文中の内部リンク
(Markdownの`[テキスト](パス)`形式、および本文に生HTMLの`<a href="...">`
が使われている場合はそれも含む)を洗い出す。

以下の観点で分類すること:

1. **すでに`/asset-simulator`でprefixされているリンク**(例:
   `/asset-simulator/tools/ideco-withdrawal`)→ 触ってはいけない対象
2. **`/`から始まるが`/asset-simulator`が付いていない内部リンク**(例:
   `/blog/montecarlo-simulation`、`/tools/xxx`、`/app`)→ 修正対象
3. **外部リンク**(`http://`または`https://`で始まる、他ドメイン宛)→
   触ってはいけない対象
4. **アンカーリンク**(`#`から始まる)、**mailtoリンク**→ 触ってはいけない
   対象
5. **相対パスでも絶対パスでもない、上記に当てはまらない書き方**が見つかっ
   た場合は、個別にプランニングチャットへ報告すること(機械的に判断せず、
   ここで一度止まる)

**成果物:** ファイルごとに「該当リンクの本文中の書き方」「分類(1〜5の
どれか)」を一覧化して報告すること。特に分類2に該当する記事・箇所数を
明記すること。

## Phase 2:実装方針の確定

Phase 1の結果を踏まえ、`applyBasePathToHtml()`(または同等の変換処理)を
拡張し、**分類2のリンクにのみ**`/asset-simulator`を自動付与するロジックを
実装する。

実装時の必須要件:

- 判定ロジックは「`href`が`/`で始まり、かつ`/asset-simulator`で始まって
  いない場合のみ、prefixを付与する」という条件にすること(分類1・3・4を
  誤って変換しないため)
- 外部リンク(`http`/`https`始まり)・アンカー(`#`始まり)・mailtoは対象
  外であることを、実装後のテストケースで明示的に確認すること
- 画像の`src`変換ロジック(既存の`applyBasePathToHtml()`内の処理)は変更
  しないこと(意図せず壊さないよう、別ロジックとして追加する)

## Phase 3:検証

- 実装後、Phase 1で洗い出した「分類2」の全リンクについて、実際にブラウザ
  で(もしくは実機相当の確認方法で)遷移先が正しいURLになっているか確認
  すること
- `ideco-nisa.md`等、分類1に該当していた記事のリンクが、実装後も二重
  付与されていないことを確認すること(これが今回のバグ修正で最も壊しやす
  い箇所)
- `full-verify.js`全PASS、`tsc`クリーンを確認すること
- 今回新規公開した`mortgage-prepay-vs-invest.md`は、前回のセッションで
  手動prefixをすでに施している。この記事のリンクが、今回の自動化ロジック
  導入後も二重付与にならないか確認すること

## 完了報告に含めるべき内容

- Phase 1の棚卸し結果(ファイル別・分類別の一覧)
- 実装した判定ロジックのコード(該当箇所を引用)
- Phase 3の検証結果(特に二重付与が起きていないことの確認)
- `full-verify.js`・`tsc`の結果
- 修正によって影響を受けたファイル一覧

## スコープ外(今回やらないこと)

- リンク以外のbasePath関連処理(画像src等、既存動作)の変更
- 記事本文の文章・数値の変更
- commit/push(調査・実装・検証まで完了後、プランニングチャットの承認を
  待つ)
