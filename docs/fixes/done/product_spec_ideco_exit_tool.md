## 1. 背景・位置づけ

- 第5弾(退職金手取り計算ツール)の自然な発展形。iDeCo/DC残高を「一時金」「年金」「併用」のどの方法で受け取るかによって手取りがどう変わるかを比較する単一目的ツール
- 類似の先行ツールとしてLifePlan Lab「iDeCo/DC 受取方法 比較」(https://lifeplan-lab.jp/tools/dc-receipt)が存在。入出力構成は類似するが、計算アーキテクチャ(下記2参照)で差別化する
- 本体シミュレーターとの関係:**本体は簡易(フラットレート20.315%・差分方式のまま)、本ツールは正確(累進課税+住民税を一次情報準拠で計算)**。第5弾と同じ立場。本体との数値差は許容し、methodologyページに明記する
- 「一時金・年金・併用の3パターンが見えるようにする」というUI上の踏襲であり、本体の計算方式(差分方式・フラットレート)は踏襲しない

## 2. 計算アーキテクチャの核心決定

### 2-1. 「直接合算計算」方式を採用(差分方式は不採用)

本体`calcPensionTaxDiff()`および競合ツールが採用する「合算後税額 − 公的年金のみの税額 = DC分の増分税額」という差分方式は、累進課税の非線形性により**基準の取り方で結果が変わり一意に定まらない**という構造的欠陥がある。単体ツールとしてゼロから3パターンを比較する本ツールにはこの方式を採る必然性がないため、各パターンの手取り総額を直接計算する方式にする。

- **一時金パターン**:DC一時金の手取り(退職所得課税) + 公的年金のみの手取り(総合課税、DCの影響なし)
- **年金パターン**:公的年金+DC年金を合算した一体の雑所得として総合課税を計算し、その手取りを1つの数字として出す
- **併用パターン**:DC一時金部分の手取り(退職所得) + (公的年金+DC年金部分)を合算した手取り(総合課税)

「DC受給によって公的年金部分の税金がいくら増えたか」という差分の数字は、主計算からは外し、見せる場合はあくまで補助的な参考指標として扱う。

### 2-1-1. 「手取り総額」の比較期間の定義(実装中に発見・確定)

3パターンを公平に比較するには、**annuityYears(年金受給期間)を全パターン共通の比較期間**とし、その期間全体で受け取れる合計手取り額を「手取り総額」とする。

- **一時金パターン**:DC一時金+退職金の手取り(一括・退職所得課税) + annuityYears年間、公的年金のみを受け取り続けた場合の合計手取り(総合課税、毎年同額と仮定)
- **年金パターン**:annuityYears年間、(公的年金+DC年金)を毎年受け取り続けた場合の合計手取り(総合課税)。会社の退職金がある場合は別途一時金として同年に受給(退職所得課税)
- **併用パターン**:DC一時金部分+退職金の手取り(一括) + annuityYears年間、(公的年金+DC年金の残り部分)を受け取り続けた場合の合計手取り

単年スナップショット比較(その年だけの手取り)は、一時金パターンが常に圧倒的に有利に見える無意味な比較になるため採用しない。

**追加の簡略化(実装上必須)**:
- 比較期間中に65歳の境界をまたぐケース(受取開始年齢+annuityYearsが65歳を超える場合)は、**受取開始年齢時点の区分(65歳以上/未満)を比較期間全体に固定適用**する。年ごとの区分切り替えは非対応とし、Methodologyに明記する
- `calcIdecoLumpSumTax(idecoLump, severance, idecoYrs, sevYrs)`のmax()による勤続年数調整は、**iDeCo一時金と退職金が実際に同一年に同時受給される場合(idecoLump>0 かつ severance>0)にのみ適用**する。どちらか一方のみの場合はその年数のみを使う(年金パターンでidecoLump=0・severance>0のケースなどで誤って他方の年数が混入しないようにする)

### 2-2. 「年金以外の課税所得」の扱い:C案(概算課税所得を直接入力)を採用

- A案(給与収入等を入力し内部で給与所得控除を計算)は給与所得控除・事業所得計算ロジックの新規実装が必要になり、ツールのスコープが「iDeCo出口ツール」から逸脱するため不採用
- B案(その他所得を区分判定のみに使い税率計算に反映しない)は、直接合算計算方式と内部的に矛盾するため不採用
- **C案**:ユーザーに「年金以外の所得(概算)」を直接入力してもらう。**「課税所得」ではなく「所得」を入力させる**(下記理由)。デフォルト0円、詳細設定に格納
  - 概念の整合性:年金側で計算するのは`雑所得`(公的年金等控除後・基礎控除等の人的控除を引く**前**の金額)。もし「その他所得」を`課税所得`(人的控除後)で入力させると、「年金は控除前・その他所得は控除後」という異なる段階の数字を合算することになり税法上不整合になる。したがって入力させるのは「所得」(給与所得控除・事業所得の必要経費控除後、基礎控除等の人的控除は引く前の金額)に統一する
  - ラベル・注記:「年金以外の所得(概算)」/「給与所得・事業所得など、年金以外の所得額です(収入額そのままではありません)。分からない場合は0円のままで概算できます」
  - **FREENOUGHユーザー層特有の注意点**:FREENOUGHのブランド思想は「FIRE(完全リタイア)」ではなく「FI(自己決定的な働き方の継続)」であり、iDeCo受給を検討する層ほど副業・個人事業・継続雇用等の収入を持つ可能性が一般的な高齢者像より高いと想定される。この項目を「わからなければ0円でOK」という受け身の説明だけにすると、まさにこの層で誤差が大きくなるケースを軽視することになる。Methodology・UI注記は受け身の表現に加えて「退職後も収入がある方は、この項目の入力を推奨します」など能動的な呼びかけを併記する
  - 内部計算での合算順序(投資調査完了、国税庁No.1000一次情報で確認):①雑所得(公的年金等控除後)とその他所得(C案入力、給与所得控除等を引いた後の「所得」)を単純合算して総所得金額を算出 → ②所得税の基礎控除(合計所得金額に応じた変動制、現行は132万円以下95万円〜655万円超2,350万円以下58万円の段階制)を1回だけ差し引いて課税所得金額を算出 → ③累進税率を適用。**所得税の基礎控除と住民税の基礎控除(原則43万円、所得に応じ逓減)は別テーブルである点に注意**(令和7年度改正は所得税のみが対象で住民税基礎控除は改正対象外)

段階的開示は第5弾を踏襲(税法用語を出さない・詳細設定は折りたたみ)。

### 常時表示

| 項目 | 内容 | 備考 |
|---|---|---|
| iDeCo/DC残高 | 万円 | 3パターン共通の分配元(受取原資) |
| iDeCo/DC加入年数 | 年 | 退職所得控除の計算基準 |
| 受取開始年齢 | 歳(60〜75) | 65歳以上/未満の公的年金等控除区分判定に使用 |

### 年金・併用パターンに関わる入力

| 項目 | 内容 | 備考 |

```
┌─────────────┬─────────────┬─────────────┐
│   一時金      │    年金      │    併用      │
├─────────────┼─────────────┼─────────────┤
│ 手取り総額    │ 手取り総額    │ 手取り総額    │ ← メイン数値
```

- 「この前提では〇〇での受取が手取り最大(概算)」のような結論サマリー行を設ける(競合ツールと同種の機能。ただし内訳の常時展開で差別化)

## 5. 計算ロジック設計

### 5-1. モジュール配置

`src/lib/tax/ideco.ts`として新規モジュール化(`retirement.ts`と同じ`src/lib/tax/`配下方針)。

想定する関数構成(投資調査で確定させる):

```
calcPublicPensionDeduction(pensionTotal, age)
  → 公的年金等控除額(速算表ベース、65歳以上/未満の2区分、令和2年分以後)

calcPublicPensionTaxableIncome(publicPensionAnnual, idecoAnnual, age)
  → { deduction, taxableIncome } を返す(controlDeductionと雑所得を両方UI表示できるよう、
     第5弾の内訳表示思想に合わせてオブジェクトで返却)

calcComprehensiveIncomeTax(taxableIncome, otherIncome)
  → { incomeTax, reconstructionTax, residentTax, totalTax } を返す
  → 雑所得とotherIncome(C案入力、「所得」ベース)を合算した金額に累進税率表を適用

calcIdecoLumpSumTax(idecoLump, severance, idecoYrs, sevYrs)
  → 既存calcRetirementIncomeTax()系ロジックのラッパー、または合算対応版への拡張(5-3参照)
```

### 5-2. 累進所得税計算ロジックの共通化(投資調査完了・対応可能)

投資調査の結果、現状`calcRetirementIncomeTax()`内に累進税率計算がインラインで実装されており、独立関数として切り出されていないことを確認。切り出し自体は機械的なリファクタリングで済む規模。**実装時は切り出し後、既存の検証スイート(`scripts/verify-retirement-tax-tool.js`、40 PASS)で第5弾側の動作が一切変わっていないことを回帰確認すること**を実装指示に明記する。

### 5-3. 一時金部分と退職金の合算処理(投資調査完了・対応確定)

投資調査の結果、`calcRetirementDeduction()` / `calcRetirementTaxableIncome()` / `calcRetirementIncomeTax()`は「単一の勤続年数・単一の収入額」を受け取る汎用的な純粋関数であり、その値の出所(単一の退職金かDC一時金との合算か)を関知しない設計であることが判明。**`retirement.ts`本体は無変更のまま**、呼び出し側で`income = idecoLump + severance`・`serviceYears = Math.max(idecoYrs, sevYrs)`を計算してから渡す薄いラッパー(`ideco.ts`に`calcIdecoLumpSumTax()`として新規実装)で対応できる。第5弾ツール側への影響もゼロ。

**対応する(v1スコープに含める)ことを確定。** 3章「詳細設定:退職金額・勤続年数」欄は維持する。次善策(対象外・UI警告)の検討は不要になった。

### 5-4. 住民税計算ロジックの共通化(投資調査完了・対応可能)

`calcRetirementIncomeTax()`内の住民税計算(市民税6%・県民税4%をそれぞれ100円未満切り捨てしてから合算)もインライン実装であることを確認。累進所得税(5-2)と同様、切り出し自体は機械的なリファクタリングで済む規模。5-2と合わせて同一の回帰確認プロセス(`scripts/verify-retirement-tax-tool.js`、40 PASS)で実装する。

## 6. Methodology文言(反映/非反映事項)

### 反映している要素(一次情報準拠)

| 要素 | 一次情報の根拠 |
|---|---|
| 退職所得(一時金部分) | 所得税法・退職所得控除の計算式、1/2課税 |
| 公的年金等控除(年金部分) | 国税庁No.1600速算表(令和2年分以後、65歳以上/未満の2区分)。公的年金等の年間受給総額に対して1回のみ適用される控除であることを明記 |
| 所得税(超過累進税率) | 所得税法の税率表(5%〜45%) |
| 復興特別所得税 | 復興財確法(所得税額×2.1%) |
| 住民税 | 地方税法(道府県民税4%+市町村民税6%、所得割) |
| 各パターンの手取り総額 | 差分方式による経路依存性を避け、各受取方法の手取り総額を直接計算している点を明記(2-1参照) |

### 対象外とした要素(意図的に非反映)、影響の方向を明記

| 要素 | 対象外とした理由 | 手取りへの影響方向 |
|---|---|---|
| 国民健康保険料・後期高齢者医療保険料・介護保険料 | 自治体・世帯構成等により算定方法が大きく異なる | **年金・併用パターンで手取りを実際より高く見せる方向**(一時金は分離課税で通常対象外、年金部分の雑所得は算定基礎に含まれるため、3パターン間で非対称に効く点を明記) |
| 19年/9年ルール(会社退職金とDC一時金の近接受給時の控除重複調整) | 5-3の投資調査で退職金+DC一時金の合算課税(max年数)に対応した場合でも、過去の受給履歴(何年前に退職金を受け取ったか等)まで踏み込んだ重複調整は範囲外とする。第5弾の既存方針を継承 | 手取りを実際より高く見せる方向 |
| 基礎控除以外の各種所得控除 | 個人差が大きく網羅的な入力は非現実的 | 手取りを実際より低く見せる方向(上記2項目と逆方向) |
| 年金受取中の運用 | 受取開始時点の残高を受給期間で単純に割った額を年額とする | 運用実績次第で不定 |
| 税制年度ごとの基礎控除差 | 現行制度をベースに固定計算 | 将来の税制改正により数値がズレる可能性 |

### まとめ文言(案)

「本ツールは制度の主要な税制(所得税・復興特別所得税・住民税)を反映した概算です。特に年金・併用パターンでは、税負担に加えて社会保険料の増加も別途考慮する必要があります。実際の手取りは社会保険料や各種所得控除、受給履歴などの影響により増減する可能性があります。」

※LifePlan Lab側の開示文と表現が近くならないよう、FREENOUGH独自の言い回しで最終文言を作成すること(実装完了後のUI文言最終レビューで確認)。
