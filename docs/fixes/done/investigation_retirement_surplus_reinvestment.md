# 投資調査指示書:退職後 余剰キャッシュフロー再投資機能

## 背景・目的

現行の資産シミュレーター(`simulate.ts`)は、退職後(取崩期)に年間収支が黒字
(収入 > 支出)の場合、その黒字分を**運用されない現金として滞留させるだけ**
という設計になっている(旧HTML版のロジックから推測。Next.js版で同様の実装に
なっているかを本調査で確認すること)。

これは、年金等の収入が生活費を上回っている退職者が、その黒字分を従来通り
運用に回すという現実の行動を表現できていないというギャップである。

本機能は、このギャップを埋めるためのオプトイン機能として、退職後の黒字を
特定口座(課税口座)で運用継続できるようにする。

## 確定済みの仕様方針(前セッションで決定済み・変更不可)

- **対象口座は特定口座のみ**:NISA・iDeCoには一切触れない
  - 理由:NISAは時価管理のため生涯上限(1,800万円)の判定ができないという
    既存の制約と衝突する余地をなくすため
  - 理由:iDeCoは受給開始後の追加拠出が制度上不可能なため、ステータス分岐の
    実装コストを避けるため
- **利率は取崩期の設定値(`rR`相当・MC時はショック込み)をそのまま使う**:
  新規のレートパラメータは追加しない
- **黒字の全額を対象とする**:金額指定・按分率などのUIは追加しない
- **3つの取崩戦略(比例取崩・現金優先・課税優先)のいずれを選んでいても、
  黒字の行き先は一律で特定口座**:取崩戦略は「不足時にどの口座から取り崩すか」
  のみを決定するものとし、黒字の処理とは独立に扱う
- **UIはON/OFFトグルのみ**:デフォルトはOFF(既存キャラクター・過去記事の
  数値への影響をゼロにするため)。トグル文言は「退職後、収入が支出を上回った
  分を運用する」(文字数調整の余地あり、UI実装フェーズで最終決定)

## 調査すべき項目

### 1. 現行ロジックの特定(最重要)

- `simulate.ts`内で、取崩期(`age >= retAge`相当)における年間収支計算箇所を特定する
- 黒字時(`income - expense >= 0`)の現在の処理を正確に確認する
  (旧HTML版の`if(surplus>=0){cash+=surplus;}`相当のロジックがNext.js版にも
  存在するか、あるいは既に異なる実装になっているか)
- 赤字時(取崩処理)のロジックとの対称性を確認し、黒字処理を追加する場合の
  実装箇所(関数・行番号ではなく関数名で報告すること)を特定する

### 2. 特定口座(tax)の状態変数・costBasis更新箇所の確認

- 積立期における特定口座への拠出処理(`tax += taxCon`相当)が、`taxCostBasis`
  (簿価)をどう更新しているかを確認する
- 黒字を特定口座に加算する際、同様に`taxCostBasis`へも同額を加算する必要が
  あることを踏まえ、その実装が積立期のロジックを流用できるか、独立実装が
  必要かを確認する
- ここを漏らすと、黒字分(本来元本)が将来含み益として誤って課税される
  バグになるため、既存の`retirementTaxCalc`等の課税処理関数との関係も
  合わせて確認する

### 3. MC(モンテカルロ)実行時の利率適用箇所の確認

- 取崩期の`rR`+ショックが、現在どの関数・どのタイミングで各口座の残高に
  適用されているかを確認する
- 黒字を特定口座に加算するタイミングが、運用益計算(利率適用)の前か後かで
  結果が変わりうるため、既存の積立期ロジック(年末積立方式:「前年末残高を
  1年運用後、年末に積立を加算」)との整合性を確認し、黒字も同じ「年末加算」
  方式にすべきかを確認する

### 4. トグルパラメータの設計

- `SimParams`型に新規追加するフィールド名の案を提示する(例:
  `retirementSurplusReinvest: boolean`。既存の命名規則に合わせて調整)
- デフォルト値が`false`になることで、既存のプロファイル・保存データに
  影響がないことを確認する

### 5. 既存フリーズ済みキャラクター(田中・山本・中村)への影響確認

- 3キャラクターのいずれかのシナリオで、取崩期に黒字(収入>支出)が発生する
  年が存在するかを確認する(存在する場合、デフォルトOFFなら数値への影響は
  ないはずだが、念のため確認)
- 影響がないことを前提に進めるが、もし何らかの理由でデフォルト挙動に
  影響が出る箇所があれば、投資調査の時点で報告する

### 6. `analyze.ts`側への影響確認

- `finalAssets`・`bankruptcyRate`・`assetLife`等の指標算出ロジックが、
  黒字を特定口座に振り替えることで参照する変数(現金残高 vs 特定口座残高)
  に依存していないか確認する
- 現金・特定口座の内訳を表示しているUIコンポーネントがあれば、
  黒字の振替によって表示上の口座内訳が変わる可能性があるため、
  影響範囲を洗い出す

## 追加調査依頼(1回目の調査完了報告を受けて)

### 背景

1回目の調査完了報告により、以下が確定した:

- 黒字判定時点の`income`は本人・配偶者の収入(年金・給与・収入イベント)が
  合算済みの単一変数であり、`owner`情報は失われている
- ただし`baseInc`構築ロジック(年金・給与収入の加算条件分岐)は既存パラメータ
  (`p.penAmt`・`p.spouse.penAmt`・`p.spouse.inc`等)から再計算可能であり、
  新規の状態変数を持たずに本人分・配偶者分の内訳を復元できる
- `severanceGross`/`spSeveranceGross`(退職金)は`income`を経由せず、
  直接cashへ計上される別経路であることが確認済みのため、黒字按分の
  対象には含まれない

### 確定した按分ルール

退職後の収支が黒字となった場合、その年の本人・配偶者それぞれの収入
(給与・年金・収入イベント。ただし`income`を経由しない別経路の収入
[退職金・iDeCo一時金等]は対象外)の比率に応じて黒字額を按分し、
各自の特定口座(`tax`/`spTax`)へ積立する。両者の収入合計が0の場合は
50:50で按分する。

### 追加確認事項

`idecoAnnualGross`/`spIdecoAnnualGross`(iDeCoを年金形式で受け取っている
場合の年次受取額)が、黒字判定に使われる`income`変数に合流しているか、
それとも退職金と同様に`income`を経由しない別経路(cash直接計上等)に
なっているかを確認すること。

- **`income`に合流している場合**:按分比率の計算に、本人・配偶者それぞれの
  iDeCo年金受取額も含める必要がある(按分ルールの「収入」の定義に追加)
- **別経路の場合**:退職金と同様に按分対象外のまま、仕様変更は不要

この1点のみを確認し、`investigation_retirement_surplus_reinvestment.md`への
追記で報告すること。実装は行わない。

## 追加調査完了報告(2回目)

### 結論:`income`に合流している

`simulate.ts`の「Main/Spouse iDeCo pension payout」ブロック(275〜311行、
取崩期の黒字判定より前に実行される)を確認したところ、本人・配偶者とも
iDeCo年金受取額(税引後手取り)は`income`に直接加算されていた:

```typescript
// ── Main iDeCo pension payout ──
...
income += Math.max(0, idecoAnnualPension - pensionTax);   // 286行目

// ── Spouse iDeCo pension payout ──
...
income += Math.max(0, spIdecoAnnualPension - spPensionTax); // 306行目
```

- 退職金(`severanceGross`/`spSeveranceGross`)・iDeCo一時金(`retirementIncomes`経由)は
  `cash`へ直接計上される別経路だったのに対し、**iDeCo「年金形式」受取(`idecoReceiveType`
  が`pension`または`split`の年金部分)は退職金と異なり、素通しで共通の`income`変数に
  合流する**という非対称な扱いになっている
- この加算は取崩期の黒字判定(`surplus = income - expense`)より前に実行されるため、
  黒字判定・黒字額そのものにはすでに本人・配偶者のiDeCo年金手取り分が織り込み済み

### 按分ルールへの影響

前回確定した按分ルール(「`income`を経由しない別経路の収入は対象外」)に照らすと、
**iDeCo年金受取額は対象外にできない**。按分比率の計算に含める「収入」の定義に、
本人は`idecoAnnualGross`相当(正確には`idecoAnnualPension - pensionTax`の税引後手取り、
`idecoTaxPaid`加算前の値と同一)、配偶者は`spIdecoAnnualGross`相当
(`spIdecoAnnualPension - spPensionTax`)をそれぞれ追加する必要がある。

按分ルールを以下のように更新することを提案する:

> 退職後の収支が黒字となった場合、その年の本人・配偶者それぞれの収入
> (給与・年金・収入イベント・**iDeCo年金受取の税引後手取り**。ただし`income`を
> 経由しない別経路の収入[退職金・iDeCo一時金]は対象外)の比率に応じて黒字額を
> 按分し、各自の特定口座(`tax`/`spTax`)へ積立する。両者の収入合計が0の場合は
> 50:50で按分する。

実装は行っていない(調査のみ)。
