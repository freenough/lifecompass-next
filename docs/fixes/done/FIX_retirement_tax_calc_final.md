# 実装依頼：retirementTaxCalcの受取年判定修正 + methodologyページへの注記追加

## 背景(経緯まとめ)

一連の調査で以下が判明した。

1. `AUDIT_severance_ideco_deduction_mixup.md`:`retirementTaxCalc`が`severanceAmount>0`だけで`max(dcYears,sevYears)`を適用しており、iDeCoを実際に受け取っていない年の退職金にまで無関係な`dcYears`が混入するバグを発見
2. 一度`FIX_retirement_tax_calc_year_match.md`で3分岐修正のGOを出したが、田中誠シリーズの確定値(772万円)が変わり回帰FAILしたため実装を中断・revert
3. 国税庁資料(No.2735、東京国税局文書等)で実際の税制を確認した結果:
   - 退職金とiDeCo一時金を**同一年**に受け取る場合:控除を一本化(長い方の年数を使用)するのが正しい税制上の扱い
   - **異なる年**に受け取る場合:後から受け取る側の控除が重複期間分だけ減額調整される(退職金が先なら19年以内、iDeCo/DCが先なら9年以内が調整対象)。**どちらの順序でも、先に受け取った側の控除が後発の出来事によって増減することはあり得ない**
   - 田中さんのケース(55歳退職金→65歳iDeCo、10年差)は「19年ルール」の対象期間内であり、本来はiDeCo側(後発)の控除が減額調整されるべきケース

結論:2で一度revertした3分岐修正(同年受取のみ`max()`で一本化、異なる年は分離)は、**方向性としては正しかった**。ただし「重複期間の按分減額」という正確な調整計算までは実装しない、という簡略化をKENZOの設計方針として採用する。

**設計方針(確定)**:
> 本シミュレーターの退職所得税計算は、FIRE計画に必要な精度を目的とした近似実装とする。19年ルール・9年ルールなどの複雑な控除調整は実装対象外とし、税務申告レベルの正確性は目指さない。ただし、近似であっても実際の税制と矛盾する計算ロジックは採用しない。

GO済み。実装を再開してください。

## 実装内容

1. `src/lib/helpers.ts`の`retirementTaxCalc`(または呼び出し元の`src/lib/simulate.ts`)で、本人・配偶者それぞれについて、その年の`idecoBalance`(実際に受け取るiDeCo額)と`severanceAmount`(実際に受け取る退職金額)の両方を見て、以下の4分岐にする
   - 退職金のみ(その年にiDeCo受取なし) → `sevYears`のみ使用
   - iDeCoのみ(その年に退職金受取なし) → `dcYears`のみ使用
   - 同一年に両方受け取る → `max(dcYears, sevYears)`で一本化(現状維持・正しい税制上の扱い)
   - (別年受取は、上記「退職金のみ」「iDeCoのみ」の分岐がそれぞれの年で個別に適用されることで自然に処理される)
2. 本人・配偶者どちらの呼び出しにも同じロジックを適用すること(前回調査で「関数自体に内在する共通の欠陥」と判明しているため)

## methodologyページへの注記追加(新規)

`/methodology`ページ(計算ロジックの説明ページ)に、以下の文面をそのまま追記してください。見出しレベル・配置は既存ページの他セクションに合わせて自然な形にしてください。

```
退職所得税計算(近似実装)

本シミュレーターでは、退職金およびiDeCo一時金は、それぞれ独立して退職所得控除を計算します。
実際の税制に存在する退職所得控除の重複調整(19年ルール・9年ルール)は実装していません。
そのため、対象となるケースでは実際より税負担が軽く表示される場合があります。
```

## 回帰テスト(4ケース・本人/配偶者双方で確認)

1. 退職金のみ(iDeCo受取なしの年)
2. iDeCoのみ(退職金なしの年)
3. 同一年受取(退職金とiDeCo一時金を同じ年に受け取る) → `max(dcYears,sevYears)`が維持されること
4. 別年受取(今回の主眼。例:退職金55歳・iDeCo65歳) → それぞれ自分の年数のみで計算されること(前発側に後発側の年数が混入しないこと)

## 重要な注意事項
