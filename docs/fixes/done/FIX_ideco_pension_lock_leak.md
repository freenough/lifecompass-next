# 実装依頼：iDeCo年金受取中(pension状態)の追加取り崩し漏れの修正

## 背景

`AUDIT_ideco_pension_sevyrs_dependency.md`の調査で、以下が判明した。

- `src/lib/simulate.ts:401`の`idecoLocked = idecoStatus === 'accumulation'`は、iDeCoが「積立中(受給開始前)」の場合のみ比例取崩等の対象から除外している
- 受給開始年齢に達し`idecoStatus`が`'pension'`に遷移すると`idecoLocked=false`となり、iDeCoが`withdraw()`の対象口座(`ci`)に含まれてしまう
- その結果、iDeCo年金受取中(固定スケジュールで毎年`ideco/idecoRemainingYears`を払い出しているはず)であっても、その年の収支ショートを埋めるための追加取り崩しがiDeCo残高からも行われてしまい、翌年以降の固定スケジュール払い出し額まで狂っていく(実測で複利的に乖離が拡大することを確認済み)

これは実際のiDeCo制度と矛盾する。年金形式で受給を開始した場合、受取期間・受取回数は開始時に確定し、**受給開始後に任意のタイミングで追加の引き出しを行うことはできない**(唯一の例外は、受給開始から5年経過後に残額を一括受け取りに切り替える「繰上一時金」のみで、本シミュレーターはこれを扱っていない)。したがって、これは近似の妥当性の話ではなく、単純なバグとして修正する。

## 修正方針

iDeCoは、`idecoStatus`が`'accumulation'`(積立中・受給開始前)であるか`'pension'`(年金受給中)であるかを問わず、**固定スケジュールによる払い出し以外の経路では一切残高が減らないようにする**。具体的には、`idecoLocked`の判定条件に`'pension'`状態も含める(実質的に、iDeCoは自身の専用の払い出しロジック以外からは常にロックされている状態にする)。

- 一時金受取(`idecoReceiveType === 'lump'`)の場合:受取イベントの発生時に一括でcash等へ振り替えられ、以降iDeCo残高は0になるため、この修正による影響はない
- 年金受取(`idecoReceiveType === 'pension'`)の場合:`idecoLocked`を`'accumulation'`または`'pension'`のいずれかであれば真とする(＝常にロック)よう修正する

## 実装内容

1. `src/lib/simulate.ts`の`idecoLocked`判定(401行付近)を、`idecoStatus === 'accumulation' || idecoStatus === 'pension'`(またはそれに相当する、iDeCoが専用ロジック以外から触られないための条件)に修正する
2. `withdraw()`(`src/lib/helpers.ts:82-108`付近)への呼び出し側で、`idecoLocked`が真の場合はiDeCo残高を対象口座(`ci`)から確実に除外することを確認する
3. 比例取崩だけでなく、現金優先・課税優先の他の戦略でも同様にiDeCoが除外されているか確認する(前回7/3の修正時と同様の確認観点)
4. 配偶者側のiDeCo(該当プロファイルがあれば)にも同じ修正を適用する

## 回帰テスト

1. **今回の再現ケース**:田中さんプロファイルで、sevYrs=5とsevYrs=13それぞれで「iDeCo受取:年金15年」を実行し、iDeCo残高の年次推移が**完全に一致する**ことを確認する(現状は65歳以降に乖離が生じている)
2. **固定スケジュールとの一致**:iDeCo残高が、毎年`前年残高×(1+利回り) - (前年残高/その時点の残存年数)`という固定スケジュール通りに推移し、65〜79歳の15年でちょうど0になることを確認する
3. **既存キャラクターへの影響確認**:iDeCo年金受取を使っている佐々木誠一シリーズ等、他のプロファイルでも同様に数値が変わる可能性があるため、影響を受けるプロファイルを洗い出し、変更前後の値を報告すること
4. **他の戦略(現金優先・課税優先)でも同様の漏れがないか**:3パターンすべてでiDeCo残高の推移を確認する
5. **6-A/6-B回帰確認**:iDeCo年金受取を使っていないプロファイル・シナリオには影響がないことを確認する
