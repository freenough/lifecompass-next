## 背景

前回実装（ブランチ`feature/lp-asset-allocation-demo`、未コミット）で、「資産クラス内訳」ドーナツ＋凡例＋明細テーブルを動的化したが、レビューの結果、以下の問題が見つかった：

1. 凡例・明細テーブル（資産クラス／金額／割合の一覧）のフォントが大きく、ドーナツ本体と被って見える
2. カード下部の「目標達成率68%」「前回比+3.2%」が固定値のまま残っている（今回のスコープ外の仮置き）

これを踏まえたKENZOとの設計チャットでの結論：

- **ドーナツ本体（グラフ）は残す。明細テーブル（資産クラス／金額／割合の一覧）は削除する**（縦長になる上、参考情報の位置づけとしては過剰）
- **固定値のKPIは削除せず、動的な実データに作り直す**。ただし前回私が提案した「2つのボックス」構成ではなく、**実際の資産管理ツールにある「FIRE進捗」3枠デザイン（目標資産額／目標までの進捗／前回記録比）をそのまま踏襲する**

### 設計方針の確定理由（ドーナツの実装方式について）

ドーナツを「本体`AssetAllocationChart.tsx`を直接呼ぶ」か「LP専用に新規実装する」かで検討した結果、**ヒーロー（`HeroDemo.tsx`）と同じ「計算・分類ロジックは本体と共有し、描画（UI）はLP用に別実装する」方式に統一する**ことで確定した。

- ヒーローは、本番の計算ロジック（`simulate()`/`analyze()`/`runMC()`）はそのまま呼び出すが、グラフの描画自体（Recharts構成・軸目盛りの簡略化等）は本体の結果画面とは別にLP用として独自に実装している（本体側のグラフ描画コンポーネントを拡張・共有してはいない）
- ドーナツもこれに揃え、**色・ラベルの分類ロジック（`getAssetClassColor`/`getAssetClassLabel`）は本体と共有**し、**描画（Pie構成・凡例の有無・フォントサイズ等）はLP専用に実装する**。この方式なら、ロジック側（色の割り当て・ラベル名）は本体の変更に自動で追随し、UI側（見せ方）だけがLP用に独立する。これはヒーローで既に採用されている設計思想と一致しており、新たなリスクを追加するものではない

---

## 1. ドーナツ表示をLP専用の軽量コンポーネントとして作り直す

**`AssetAllocationChart.tsx`（本体）は呼び出さない。** 理由：このコンポーネントは「ドーナツ＋凡例＋明細テーブル」が一体で、明細だけを非表示にするprops等が現状なく、無理に隠そうとすると別途懸念のある「ロック対象疑義のあるファイルを編集する／CSSで無理やり打ち消す」対応が必要になり筋が悪い。**LP用に新規の軽量コンポーネントを作る。**

- 新規コンポーネント（例：`src/components/lp/AssetBreakdownDonut.tsx`）を作成する
- `AssetManagementPromoSection.tsx`側にある、前回実装した`<AssetAllocationDemo />`の呼び出しは外し、新規コンポーネントに差し替えること（`AssetAllocationDemo.tsx`自体は下記の通りファイルとしては削除しない）
- ドーナツ本体はRechartsの`Pie`で独自に実装してよい（ヒーロー・前回のドーナツ実装と同様のパターンを踏襲）
- 色・ラベルは、`lib/assetManagement/classColors.ts`の`getAssetClassColor`、`lib/assetManagement/categories.ts`の`getAssetClassLabel`をそのまま再利用する（これらは他に依存のない自己完結したユーティリティ関数であることを調査済みなので、再利用してよい）
- 中央には合計金額（前回同様カウントアップ演出）を表示する
- **明細テーブル（資産クラス／金額／割合の一覧）は実装しない**。凡例が必要な場合は、色チップ＋ラベル程度のシンプルな表示に留め、LPのカードサイズに収まる適切なフォントサイズ（本体ツール画面と同じサイズを踏襲する必要はない）にすること
- 前回実装した`AssetAllocationDemo.tsx`・`AssetAllocationChart.tsx`（本体）は削除せず、ファイルとしては残してよい（呼び出しを外すのみ。今後別の用途で使う可能性があるため）

### ダミーデータ（内訳）の整合性確認・調整

- 前回実装した`DEMO_HOLDINGS`（日本株500万／全世界株400万／先進国株300万／現金300万）が、`HeroDemo.tsx`の`DEMO_PROFILE`（NISA/iDeCo/特定口座/現金の4口座構成）の実際の値を参照・変換して作られたものか、それとも合計額だけを合わせて独立に作成された値なのかを、まず実装済みコードの経緯から確認すること
- `DEMO_PROFILE`側に口座ごとの資産クラス情報（各口座がどの資産クラスに投資している想定か）が含まれているか確認する
  - 含まれている場合：その情報に基づいて`DEMO_HOLDINGS`を作り直し、金額・資産クラスともに`DEMO_PROFILE`と正しく整合させること
  - 含まれていない場合：`DEMO_PROFILE`の口座ごとの金額（NISA/iDeCo/特定口座/現金）と合計額が一致するように`DEMO_HOLDINGS`を調整した上で、口座→資産クラスの対応づけ（例：NISA→全世界株、特定口座→先進国株、現金→現金、等）を実装側で妥当な形で決めてよい。その場合、どういう対応づけにしたかを完了報告に明記すること
- 最終的に「ヒーローと资産クラス内訳が同じ入力データに基づいていると言えるか」を、事実に基づいて完了報告で明確に結論づけること

## 2. 「FIRE進捗」3枠KPIブロックを実データで実装する

実際の資産管理ツールにある「FIRE進捗」ブロック（添付イメージ参照：目標資産額／目標までの進捗／前回記録比の3枠）と同じ**情報構成**でLP用に実装する。ただし**タイポグラフィ（フォントサイズ）は、本体の「FIRE進捗」ブロックではなく、ヒーロー（`HeroDemo.tsx`）のバッジ（「FIRE達成」「資産寿命」「MC破綻率」の3つ）と同じ小さめのサイズに合わせること**。本体の「FIRE進捗」ブロックはページ全幅を使える前提の大きめのフォント（値部分が28px程度）だが、LPのこのカードはその幅がないため、そのままのサイズでは3枠が収まらない。ヒーローのバッジで使われているクラス・スタイルをそのまま参照し、同じ寸法感で実装すること。

- **目標資産額**：ヒーロー（`HeroDemo.tsx`）が既に計算している、`DEMO_PROFILE`でのFIRE達成年齢（52歳）時点の資産額を使う。`simulate()`の結果（スナップショット配列）から、FIRE達成年齢と一致する年齢のスナップショットの資産合計額を取得する
  - 実装方法（この計算を共通化するか、進捗カード側で同じ`simulate()`/`analyze()`を同じ`DEMO_PROFILE`/`DEMO_EVENTS`で独立に呼び出すか）は、コード重複が少ない方でよい。選んだ方法と理由を完了報告に明記すること
- **目標までの進捗**：前回実装の`DEMO_HOLDINGS`合計（1,500万円）÷ 目標資産額 で算出し、%表示する。表示前に必ず丸め処理（`Math.round()`等）を通すこと
- **前回記録比**：実データに基づく必要はなく、適当な固定値でよい（KENZO了承済み）。実際のツールの表示形式（絶対額＋%、例：「+1,000万円」「+7.0%（2026-09比）」）を踏襲するか、シンプルに%のみにするかは実装側の判断でよいが、進捗が順調であることが伝わる自然な値にすること
- 3枠とも、前回実装したカウントアップフック（`src/hooks/useCountUp.ts`）とIntersectionObserverによるスクロールイン検知の仕組みを流用し、画面内に入ったタイミングで数値がカウントアップする演出にする

## 3. カード全体のレイアウト

- 「毎月の資産を、記録する。」カード（`AssetManagementPromoSection.tsx`右側）は、**ヒーローと同じ縦構成（上にKPI3枠のバッジ、下にグラフ）**にする。具体的には、上段に2で作ったKPI3枠（目標資産額／目標までの進捗／前回記録比）を横並びで配置し、その下に1で作った軽量ドーナツを配置する（ヒーローの「上にバッジ3つ、下にチャート」というレイアウトをそのまま踏襲すること）
- ドーナツはカードが縦長になりすぎない程度のサイズに収めること
- 左側（見出し・説明文・3つの箇条書き・CTAボタン）は今回も変更しない
- モバイル幅（375px相当）で縦長になりすぎないか、要素が重ならないか確認すること

## 遵守事項

- `AssetAllocationChart.tsx`・`classColors.ts`・`categories.ts`への変更は不要（`classColors.ts`/`categories.ts`の関数はimportして使うのみ、`AssetAllocationChart.tsx`自体は呼び出さない）
- `HeroDemo.tsx`への変更は、目標資産額の計算ロジックを共通化する場合に限り発生してよいが、既存の見た目・挙動は変えないこと
- ロックファイル（`types.ts`/`profile.ts`/`PortfolioPanel.tsx`/`simulate.ts`/`analyze.ts`/`montecarlo.ts`/`blog.ts`/`blogTopics.ts`/`concerns.ts`/`ConcernCard.tsx`）への依存・変更は一切ゼロを維持すること（`simulate()`/`analyze()`の呼び出しは可、変更は不可）
- 表示する数値（目標資産額・進捗率・前回記録比）は、画面表示前に必ず丸め処理を通すこと
- 既存の`feature/lp-asset-allocation-demo`ブランチで作業を継続してよい（新規ブランチを切る必要はない）
- コミット・push・Vercel Preview作成は、KENZOの確認・指示を受けるまで行わないこと
- 完了報告には必ず実際のコード抜粋・実機確認結果（スクリーンショット、デスクトップ幅・375px幅の両方）を添付すること
