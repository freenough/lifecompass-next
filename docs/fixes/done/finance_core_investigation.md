# 調査指示書:積立額逆算ツール向け「finance-core」切り出し可能性の調査

## 背景・目的

9記事目「新NISAは毎月いくら積み立てればいい?」と連携させる、単独URL(`/tools/monthly-investment`
を想定)の軽量な積立額逆算ツールを新規開発する計画がある。

このツールは複利計算(目標資産・想定利回り・積立期間の関係)のみを扱う軽量版だが、
**LifeCompass本体(simulate.ts)と異なる計算式を独自実装すると、将来的に両者の数字が
食い違い、プロダクト全体の信頼性を損なうリスクがある。**

そのため、逆算ツールは可能な限り**LifeCompass本体と同じ計算ロジックの一部を共有**
する形で作りたい。本セッションは、その共有が技術的にどこまで現実的かを調査するのみ
の投資判断前フェーズであり、**実装は一切行わない**。

## 前提条件(必ず守ること)

- `simulate.ts` / `analyze.ts` は変更禁止という既存ルールがある。本調査でもこの
  前提は変えない。変更が必要そうな場合は「変更が必要」と報告するに留め、絶対に
  実際の変更は行わないこと
- 本セッションの成果物は調査報告のみ。コードの追加・修正・新規ファイル作成は
  一切行わないこと
- `full-verify.js` や既存のフィクスチャ回帰テストには一切触れないこと

## 調査してほしいこと

### 1. simulate.tsの内部構造の切り分け可能性

- `simulate.ts`の内部で、「口座残高・積立額・利回りから将来の資産推移を計算する」
  という複利計算のコア部分が、税制計算(NISA非課税/iDeCo控除等)・ライフイベント処理・
  取崩戦略ロジックと**関数レベルでどの程度分離されているか**を確認してほしい
- 具体的には、「積立期(所得あり・拠出中)における単純な複利積立計算」に相当する
  処理が、他のロジック(退職判定・年金・税金計算など)と混在せず独立した関数
  (またはそれに近い単位)として存在するか、それとも一連の処理の中に分散して
  埋め込まれているかを報告してほしい

### 2. 逆算ツールに必要な最小計算の特定

逆算ツールが必要とする計算は、概ね以下のような入力→出力を想定している:

- 入力:現在資産・目標資産(またはFIRE年齢)・毎月積立額・想定利回り・現在年齢
- 出力:目標資産到達までの年数、または目標達成に必要な毎月積立額

この計算に対応する処理が、`simulate.ts`のどの部分(関数・ロジックブロック)に
相当するかを特定してほしい。対応する処理が現状ないか、他の処理と密結合している
場合はその旨を報告してほしい。

### 3. 依存関係の調査

`simulate.ts`の該当ロジックを単体で呼び出そうとした場合、以下を確認してほしい:

- `simulate(p, events, strategy, shockOverrides?)`のような既存シグネチャを
  そのまま使う場合、`SimParams`型・`events`配列など、逆算ツールの4〜6項目の
  入力だけでは埋まらないフィールドがどれだけあるか(ダミー値で埋める必要が
  あるフィールドの一覧)
- 型定義(`types.ts`)のうち、逆算ツールにとって「本質的に不要」なフィールドは
  どの程度の割合を占めるか(体感でよい)

### 4. 切り出し方法の選択肢の整理(提案は複数出すこと、実装はしない)

調査結果を踏まえて、考えられるアプローチを2〜3案挙げてほしい。例えば:

- 案A:`simulate.ts`内の複利計算部分を独立した小関数として新規に切り出し
  (`simulate.ts`自体は変更禁止のため、新規ファイルに複利計算のみを複製する形。
  ただし「独自再実装」であり、本体とのズレを完全には防げない点に注意)
- 案B:`simulate.ts`に手を入れず、ダミー値で埋めた`SimParams`を構築して
  既存の`simulate()`をそのまま呼び出す(変更禁止ルールを守れるが、逆算ツールの
  軽量さが損なわれる可能性)
- 案C:その他、調査の中で見えてきた現実的な方法があれば提案

各案について、メリット・デメリット・「本体との計算結果の一致がどこまで保証
されるか」を整理してほしい。

## 報告フォーマット

- 現状構造の要約(1で調査した内容)
- 該当ロジックの所在(2で特定した内容)
- 依存関係の調査結果(3の内容)
- 切り出し方法の選択肢と比較(4の内容、複数案を並べること)
- 全体を通しての推奨アプローチと、その理由
- 想定される実装工数感(概算でよい、後続の実装判断材料として)

**繰り返しになるが、本セッションでは調査・報告のみを行い、コードの変更・新規
作成は一切行わないこと。**
