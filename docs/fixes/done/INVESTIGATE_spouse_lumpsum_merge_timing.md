# 調査指示書:配偶者「一時金」選択時のiDeCo残高合算タイミングの妥当性

**種別:調査のみ(実装はしないこと)**
**背景:** `IMPL_spouse_ideco_pension_and_split_parity.md`(Stage B)の実装中に、`simulate.ts`内の「本人のiDeCo受取開始時に配偶者のiDeCo残高を合算する」旧来ロジック(コメント「旧HTML版は単一プール」)が発見された。配偶者が「年金」「併用」を選択している場合はこの旧ロジックを迂回する修正(`!spIsPension && !spIsSplit`条件追加)を実施済み。

一方、**配偶者が「一時金」を選択している場合の合算タイミング自体(本人のiDeCo受取開始年齢を基準に発火する、という設計)が正しいか**は未検証のまま残っている。今回はこの点のみを調査する。

---

## 調査してほしいこと

### 1. 現状の挙動を正確に特定する
- 該当ロジック(`simulate.ts`内の合算処理ブロック、関数名・コンポーネント名で報告)が、配偶者「一時金」選択時に**具体的にいつ発火するか**を特定する。
  - 本人の`idecoStartAge`(iDeCo受取開始年齢)に到達した年か
  - それとも配偶者自身の`idecoStartAge`(配偶者側の受取開始年齢設定)を見ているのか
  - 両者が異なる年齢に設定されているケース(例:本人60歳・配偶者65歳)で、実際どちらの年齢を基準に合算処理が発火するか、実測すること

### 2. 「単一プール設計」の経緯を確認する
- 旧HTML版(STEP35など)でこの合算ロジックがどう実装されていたか(配偶者の受取開始年齢という概念自体が旧版に存在しなかったことは既知。だとすれば旧版は「世帯で1つのiDeCo受取開始年齢」という前提だったはずで、今の「本人・配偶者で別々の受取開始年齢を持てる」設計と矛盾しないか)
- Next.js版で配偶者に独自の`idecoStartAge`を持たせた際、この合算ロジックのタイミング基準を配偶者自身の年齢に更新し忘れていないか(Stage Bで発見した「受取方式の握りつぶし」と同種の同期漏れの可能性)

### 3. 期待される正しい挙動を提示する(実装はしないこと)
- 「配偶者が一時金を選んでいる場合、配偶者自身の`idecoStartAge`に到達した年に、配偶者自身のiDeCo残高が一時金として支払われる」という、本人と対称な挙動が本来あるべき姿だと考えられるが、これで認識が合っているか
- 現状の実装がこの認識とズレている場合、どの程度のズレか(例:本人の受取開始年齢の方が早い場合は前倒しで合算されてしまう/遅い場合は本来より遅れて合算される、等)を具体的なシナリオで示すこと

---

## 検証してほしいシナリオ例
- 本人`idecoStartAge`=60、配偶者`idecoStartAge`=65、配偶者は一時金選択 → 実際に合算処理が発火するのは60歳時点(本人基準)か65歳時点(配偶者基準)か
- 本人`idecoStartAge`=65、配偶者`idecoStartAge`=60、配偶者は一時金選択 → 同様に確認
- 本人・配偶者とも`idecoStartAge`が同一(デフォルト60歳)の場合 → 現状の回帰確認済みシナリオではこの区別がつかない可能性があるため、あえて年齢を分けたテストケースで確認すること
