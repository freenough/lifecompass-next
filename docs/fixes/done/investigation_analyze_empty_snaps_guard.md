# 調査専用指示書:analyze.tsの空snaps配列アクセスの根本原因調査

**`simulate.ts`・`analyze.ts`・`montecarlo.ts`は変更禁止・読むだけ。**
コードの変更は一切行わず、調査結果の報告のみでお願いします。

## 背景

`docs/fixes/done/investigation_lifeEx_input_bug.md`(前回調査・修正)で、
`simulate()`が空配列(`snaps=[]`)を返すケース(`curAge > lifeEx`)があり、
それを`analyze.ts:87`の`snaps[snaps.length - 1].totalAssets`が無防備に
読むことでクラッシュすることが判明した。前回は呼び出し元(`profile.ts`)側で
`lifeEx`を防御的に補正することで、このパターンでの空配列発生を回避したが、
`analyze.ts`自体の「空配列が来たら無条件で落ちる」という弱点は未解消の
まま残っている。将来別の入力の組み合わせで同じ脆弱性が再発する可能性が
あるため、根本的な対処方針を検討したい。

## 調査項目

1. **`simulate()`が空配列を返しうる全ての条件を洗い出してください。**
   前回判明した`curAge > lifeEx`以外にも、空配列(または要素数が極端に
   少ない配列)を返しうる入力の組み合わせがないか、`simulate.ts`の
   年次ループ・早期return・breakの条件を全て確認してください。

2. **`analyze.ts`内で、`snaps`配列(または`simulate()`/`runMC()`の戻り値の
   配列)に対して、要素の存在を確認せずにインデックスアクセス・
   `.length-1`アクセス・分割代入等を行っている箇所を全て洗い出して
   ください。**(`snaps[snaps.length-1].totalAssets`以外にも同種の
   無防備なアクセスがないか、ファイル全体を確認すること)

3. **`analyze()`・`runMC()`の呼び出し元を全て洗い出してください。**
   (`profileToSimParams`経由だけでなく、検証スクリプト等の直接呼び出しも
   含む)。今回のような「呼び出し元で入力を防御的に補正する」対症療法を
   全ての呼び出し元で個別に行うのが現実的か、それとも呼び出される側
   (`analyze.ts`)で一元的にガードする方が保守性が高いか、所感を報告して
   ください。

4. **ロックファイルへの変更が必要になった場合の影響範囲を報告してください。**
   `analyze.ts`に空配列ガードを追加する場合、想定される変更(例:関数冒頭で
   `if (snaps.length === 0) return <安全なデフォルト値>;`のような早期return)
   が、既存の`full-verify.js`のフィクスチャ(正常系)の結果に影響を与えない
   ことを、変更を実施せずに机上で確認できる範囲で報告してください。

## 出さなくてよいもの

- ファイルの変更は一切行わないこと
