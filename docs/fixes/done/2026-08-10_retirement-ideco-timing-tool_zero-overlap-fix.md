## 背景

データ収集フェーズで、受給間隔15年(B-3相当:退職金60歳受給・iDeCo75歳受給)のケースを実行したところ、甲(退職金)のみなし調整後の実効期間終了と、乙(iDeCo)の実期間開始がちょうど一致し、重複期間の計算式`max(0, min(乙終了,甲実効終了) - max(乙開始,甲実効開始))`が**0**を返すケースが見つかった。

現行実装では、この「重複期間0年」を`calcRetirementDeduction(0)`に渡しており、その結果80万円下限が適用されて(ロ)=80万円となり、乙の控除額から80万円が差し引かれている。

**これは誤りと判断する。** 施行令70条1項2号がこの減額規定(甲固定・乙減額方式)を適用する条件は「その年に支払を受けた退職手当等につき...計算した期間の基礎となつた勤続期間等の一部が...前の退職手当等に係る勤続期間等と重複している場合」であり、**重複期間が実際にはゼロ(=期間が接しているだけで実質的な重複がない)場合、この規定自体の適用条件を満たさない**。つまり、(ロ)として80万円(下限適用値)を差し引くのではなく、**重複が存在しないため減額規定自体を適用しない(乙は満額控除のまま)**が正しい。

これは前回のタスクF(重複期間1年・2年のケースで80万円下限が正しく適用されることを確認したテスト)とは異なる論点である。1年・2年は「実際に重複が存在する」ケースなので下限適用は妥当だが、0年は「重複という事実自体が存在しない」ケースであり、扱いを区別する必要がある。

## タスクG:重複期間0年の場合、減額規定自体をスキップする

### 対応内容

`retirementIdecoTiming.ts`内の重複調整ロジック(`calcDuplicateAdjustment`関数、タスクFでコメント追加した箇所)を以下のように修正する。

**重要:「重複期間の長さを計算してから0かどうかを見る」のではなく、「そもそも重複が存在するかどうかを先に境界値で判定してから、存在する場合のみ長さを計算する」という2段階に分離すること。** 理由は、長さの計算(`max(0, end-start)`によるクランプ)と存在判定を一体化すると、境界条件(`<`か`<=`か)の誤りが後段の判定に埋もれて発見しにくくなるため。今回のバグ自体が、この一体化によって見逃されたという性質のものだった。

```
overlapStart = max(乙の実期間の開始, 甲の実効期間の開始)
overlapEnd   = min(乙の実期間の終了, 甲の実効期間の終了)

hasOverlap = overlapStart < overlapEnd   # 境界が接するだけ(等しい)場合はfalseにすること。ここが今回の核心

if hasOverlap:
    重複期間 = overlapEnd - overlapStart
    (ロ) = calcRetirementDeduction(重複期間)
    乙の控除額 = max(0, (イ) - (ロ))
else:
    # 重複が存在しないため、減額規定(施行令70条1項2号)を適用しない
    (ロ) = 0
    乙の控除額 = (イ)   # 満額控除のまま
```

`hasOverlap`の判定と`重複期間`の実長さ計算を別ステップの変数・別の処理として実装すること(1行の式に統合しない)。レビューしやすくするため、`hasOverlap`単体のコメントに「施行令70条1項2号の『重複している場合』に該当するかどうかの判定。期間が接するだけ(開始=終了)の場合はfalseとする」と明記すること。

### 追加すべきテストケース

境界条件(0年)と80万円下限(1年・2年)を1つのテーブルとして並べて検証すること。以下4パターンを`verify-retirement-ideco-timing-tool.js`に明示的に追加する(このうち10年は既存のB-1相当ケースで実質的にカバー済みだが、この表の一部として改めて位置付けてよい)。

| 重複期間 | hasOverlap | (ロ)の期待値 | 備考 |
|---|---|---|---|
| 0年(境界が接するのみ) | false | 0円 | 今回の修正の核心。減額規定自体を適用しない |
| 1年 | true | 80万円 | 40万円×1年=40万円だが80万円下限が適用される(タスクFで確認済み) |
| 2年 | true | 80万円 | 40万円×2年=80万円で下限とちょうど一致する境界(タスクFで確認済み) |

- 上記のうち「0年」を新規テストとして追加すること(B-3相当のケースをそのまま使ってよい)
- 「1年」「2年」はタスクFで追加済みのテストが該当するため、重複がないことを確認したうえで、このテーブルの一部として整理・コメントを揃えること(重複して同じテストを二重に作らないこと)
- 加えて、期間が完全に離れている(重複期間の計算が大きく負になる)ケースでも`hasOverlap`が正しく`false`になることを確認するテストを1件追加する
