# 指示: 「入力を編集」実行時のスクロール不具合調査（幅依存の再発パターン）

## 現象
「入力を編集」ボタンを押して入力フォームを開いたとき、

- 狭い画面幅（KpiGridが2列表示の範囲）: 正しく入力パラメータセクションの
  最上部までスクロールする
- 広い画面幅（KpiGridが3列表示の範囲、640px以上）: スクロールが発生せず、
  ボタンを押す前の位置（MCモードタブ〜KPIカード付近）に留まったまま

という差異がある。今回のセッションで繰り返し発生している「KpiGridの列数
切り替え（`sm:` 640px）という無関係な条件に、別の挙動が引きずられる」
パターンの再発が疑われる。

## 調査・報告（実装前に必須、具体的な実測値で報告すること）

1. 「入力を編集」を押した際にスクロールを発生させている実装箇所を特定する
   （`formOpen` の false→true 変化を監視する既存のuseEffect、あるいは
   別の仕組みか。該当ファイル・該当行を報告）。
2. その実装が、何らかのブレークポイントや画面幅条件（例:
   `window.innerWidth` を見る分岐、CSSクラスの有無での分岐等）に
   依存していないか確認する。依存している場合、その値を報告する。
3. 640px未満と640px以上（および1024px前後）で、実際にこのスクロール処理が
   呼び出されているかどうかを、コンソールログ等で実測して報告する
   （呼ばれているが移動量が0になっているのか、そもそも呼ばれていないのかを
   切り分けること）。
4. 前回のセッションで追加した `scroll-mt-28` や `tabAnchorRef` が、
   この「開く」方向の処理にも意図せず影響していないか確認する
   （閉じる方向の処理と開く方向の処理が別々の実装であることを確認し、
   混線していないか見ること）。

上記の実測結果を報告したうえで、原因に応じて修正する。
**幅依存の条件式自体をこの機能のために新設しない**こと。もし何らかの
条件分岐が必要になる場合は、既存の `lg:`（1024px、縦積み⇔横並びの境界）を
再利用し、新しいブレークポイントを作らないこと。

## 期待される最終動作
画面幅・KpiGridの列数（2列/3列）によらず、「入力を編集」を押した際は常に
入力パラメータセクションの最上部（「入力パラメータ」という見出しが画面上部
付近に見える位置）までスクロールする。

## 制約・確認事項
- `simulate.ts` / `analyze.ts` は変更禁止。
- 前回までの「閉じる」時のスクロール（固定モード/MCモードタブ直上への移動）の
  挙動には影響を与えないこと。
- 完了後、`full-verify.js` がPASSすることを確認。

## 動作確認観点
1. 640px未満・640〜1023px・1024px以上、それぞれの幅で「入力を編集」を押し、
   入力パラメータ最上部まで正しくスクロールするか
2. 「入力を閉じる」時のスクロール（タブ直上への移動）が引き続き正しく動作するか
   （回帰確認）
