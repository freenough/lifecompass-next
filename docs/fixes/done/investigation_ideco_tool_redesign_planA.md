# 指示書: ideco-withdrawalツール再設計(案A)のための調査(調査のみ・実装なし)

作成日: 2026-08-03
このチャットの役割: 企画・Spec作成・意思決定 / 実行: Claude Code
フェーズ: investigation-only(この指示書では実装は行わない。次フェーズでSpec作成→実装)

## 背景

`ideco-withdrawal`ツールの「手取り総額」比較カードで、「年金受給期間」を変更すると
一時金パターンの合計手取り額まで変化するという挙動が発見された。検算の結果、
これは一時金自体の額が変わっているのではなく、比較の集計期間を伸ばした分だけ
公的年金の受取額が合算されて増えているだけ、と判明した(ロジック自体にバグはない)。

ただしUXとして「一時金という受け取り方式そのものが変わったように見える」という
誤解を招くため、以下の方向で再設計する方針が確定した(案A採用):

- 3パターンの主比較カードは「iDeCo単体の手取り額」のみで構成する
  (一時金:受給期間に依存しない固定値。年金・併用:選んだiDeCo受給期間分の合計)
- 公的年金額は「参考:年間◯◯万円」として別枠に格下げし、主比較の合計には含めない

この指示書では、上記の再設計を実装する前段階として、現状の実装を正確に把握することのみを行う。

## 調査内容

### 1. 「年金受給期間」パラメータの実体確認(最重要)
- 現在UIに表示されている「年金受給期間」(例:10年/20年)という単一の入力が、
  内部的にどの変数・状態にマッピングされているかを特定する
- 特に、以下が**同一のstate/propsを共有しているか、独立しているか**を明確にする:
  - (a) iDeCo年金の受給年数(年金・併用パターンの「iDeCo年金分の手取り」計算に使う年数)
  - (b) 手取り総額比較の集計期間(公的年金を何年分合算するかを決めている年数)
- 共有されている場合、その変数名・型定義・使用箇所(ファイル名・関数名)を報告する
- 独立している場合(ChatGPTの推測が外れていた場合)、なぜ今回の現象が起きたのかを
  実際のコードに基づいて別途説明する

### 2. 現状の「手取り総額」計算ロジックの構成要素の特定
- 一時金パターン・年金パターン・併用パターンそれぞれの「手取り総額」が、
  実際にどの内訳(iDeCo一時金分/iDeCo年金分/公的年金分)の合算で構成されているか、
  関数名・計算式ベースで報告する
- 「一時金分の手取り」のように、公的年金を含まないiDeCo単体の数値が、
  現在の実装内に**既に個別の変数として存在しているか**を確認する
  (画面の内訳表示に使われている数値がそれに当たる可能性が高い。存在するなら
  再設計時に流用できるため、新規計算ロジックの追加が最小限で済む)

### 3. 「併用」パターンの内部構成の確認
- 併用パターンが「一時金分×割合+年金分×割合」のような単純な加重合成なのか、
  それとも税制上の相互作用(退職所得控除や公的年金等控除の按分等)を含む
  独自計算なのかを確認する
- 「併用時の一時金割合」スライダーが、iDeCo残高をどう分割しているか
  (例:残高を一時金割合分と年金割合分に分けてそれぞれ課税計算しているか)を確認する

### 4. UI変更の影響範囲の洗い出し(案Aを実装する場合に触る箇所)
- 主比較カード3枚のコンポーネント名・ファイルパス
- 「参考:公的年金」を別枠表示に変更する場合、現状どこに公的年金の入力・表示ロジックが
  あるか
- 内訳表示部分(現状「一時金パターンの内訳」として展開表示されている部分)との
  重複・流用可能性

## 報告フォーマット

- 「年金受給期間」パラメータが共有か独立かの結論を最初に明記
