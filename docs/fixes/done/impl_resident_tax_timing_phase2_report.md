# 完了報告:resident-tax-timing フェーズ2(社会保険料控除・調整控除)+ 前提条件の追加開示

`docs/fixes/active/impl_resident_tax_timing_phase2.md` の実装。

## 実装前の一次情報再確認(指示書の必須事項)

### 雇用保険料率(0.5%)の mhlw.go.jp 再確認
`https://www.mhlw.go.jp/content/001692566.pdf`(厚生労働省、令和8年度雇用保険料率)を
WebFetch→(バイナリ抽出失敗のため)Readツールでローカル保存PDFを直接読み取り、
「一般の事業」の被保険者負担分が **5/1,000(0.5%)** であることを確認した。フェーズ1調査時点の
仮定値と同一だったため、14.6%/15.4%の合計値は変更なし。

### 調整控除・課税所得5万円未満ケースの再確認
フェーズ1報告書(`investigation_shakai_hoken_kojo_report.md`)は「課税所得金額が205万円超:0円」
「多くのケースで調整控除は0円になる」と記載していたが、これは**誤り**だった。諏訪市
「人的控除の差と調整控除の計算方法」(https://www.city.suwa.lg.jp/soshiki/4/4918.html)・
京都市「調整控除」(https://www.city.kyoto.lg.jp/gyozai/page/0000028147.html)の公式説明を
確認したところ、いずれも「計算結果がマイナスの場合(=課税所得金額が205万円を超える場合)も
2,500円が適用される」と明記されていた。フェーズ1報告書62行目に記載していた生の計算式
`調整控除額 = max(2,500円, (人的控除額の差の合計額 − (課税所得金額 − 200万円)) × 5%)` 自体は
正しかったが、63-64行目・80-87行目・119-120行目の文章による解釈がこの`max()`の意味を
「計算結果がマイナスなら0円」と取り違えていた(正しくは「計算結果が2,500円を下回っても
2,500円を下回らない」という下げ止まりの意味)。`investigation_shakai_hoken_kojo_report.md`の
冒頭に訂正の注記を追記済み。

課税所得5万円未満のケース(調査報告書に明記がなかった下限ケース)についても同じ2自治体の
説明で「(人的控除の差)と(課税所得金額)のいずれか小さい方 × 5%」という定義を確認できたため、
`min(50,000円, 課税所得金額) × 5%`(下限のフロア処理なし・0円まで連続的に逓減)として実装した。

## パート1:社会保険料控除

### 実装
- `SOCIAL_INSURANCE_RATE_UNDER_40 = 14.6`(40歳未満)、`SOCIAL_INSURANCE_RATE_40_OR_OVER = 15.4`
  (40歳以上65歳未満、介護保険料込み)を定数としてexport。
- `calcSocialInsuranceDeduction(incomeYen, ratePercent) = floor(incomeYen × ratePercent/100)`。
- `calcTaxableSalaryIncome()`の変換チェーンを
  `年収 → 給与所得控除 → 給与所得 → 社会保険料控除(年収×料率) → 住民税基礎控除(43万円) → 課税所得`
  に変更。指示書の指定通り、各ステップでは個別に0円クランプせず、最終的な課税所得算出時に
  `Math.max(0, ...)`で1回だけクランプしている。
- `ResidentTaxTimingInput`に`isAge40OrOver?: boolean`・`socialInsuranceRateOverride?: number`を追加。
  料率の優先順位は`socialInsuranceRateOverride ?? (isAge40OrOver ? 15.4 : 14.6)`。波1・波2に同じ料率を適用。
- `CurrentYearTax`・`NextYearTax`に`socialInsuranceDeductionApplied: number`を追加。

### UI
- 「より正確に試算する」内に「40歳以上65歳未満(介護保険料を含む)」チェックボックスと
  「社会保険料率が分かっている」チェックボックス+料率入力欄(%、小数対応)を追加
  (`useRetirementYearOverride`と同じ表示パターン)。
- 「計算根拠を見る」内に、波1・波2それぞれの社会保険料控除額を文中の数値として表示。

## パート2:調整控除

### 実装
- `calcAdjustmentDeduction(taxableIncome)`:
  - `taxableIncome <= 2,000,000`: `floor(min(50,000, taxableIncome) × 0.05)`
  - `taxableIncome > 2,000,000`: `max(2,500, floor((50,000 − (taxableIncome − 2,000,000)) × 0.05))`
- `calcResidentTax()`本体は無改修。代わりに`calcIncomeTaxPartWithAdjustment(taxableIncome)`という
  ヘルパーを新設し、`calcResidentTax()`の`total`(所得割)から調整控除を差し引いて
  `Math.max(0, ...)`でクランプする。波1(`calcAnnualResidentTax()`)・波2(`calcNextYearTax()`)の
  両方がこの共通ヘルパーを呼ぶ(二重実装なし)。
- `CurrentYearTax`・`NextYearTax`に`adjustmentDeductionApplied: number`を追加。

## パート3:「退職は今年」前提の開示

`calcResidentTaxTiming()`内で算出済みの`retirementYear`(`new Date().getFullYear()`)を
`ResidentTaxTimingResult`型に追加し、UIの前提条件ボックスに
「本ツールは、退職が今年({retirementYear}年)であることを前提に、その時点の税制で
試算しています。実際の退職が翌年以降になる場合、適用される税制(控除額等)が変わり、
結果が異なることがあります。」を動的に埋め込んだ(ハードコードなし)。あわせて、
社会保険料控除を考慮するようになったことで不正確になっていた既存の前提文言
(「社会保険料控除等は未考慮」)も「社会保険料控除は概算料率で考慮しています」に修正した
(アコーディオン内の同趣旨の文言も同様に修正)。

## Python(Decimal相当の整数演算)による独立検算

本番コードと同じ整数演算(floor + 100円未満切り捨て等)を手計算で再現し、
`calcResidentTaxTiming()`の実出力と完全一致することを確認した代表2ケース:

### ケース1:退職前年年収600万円・9月退職(200万円境界を跨ぐ課税所得)
- 波1(現在の住民税残り、所得基準=2025年分・年収600万円):
  給与所得控除(2025年表・360万超660万以下:×20%+44万)= 1,640,000円
  → 給与所得4,360,000円 → 社会保険料控除(14.6%)= floor(6,000,000×0.146) = 876,000円
  → 課税所得 = 4,360,000 − 876,000 − 430,000(住民税基礎控除) = **3,054,000円**
  → 市民税 floor(3,054,000×0.06/100)×100 = 183,200円、県民税 floor(3,054,000×0.04/100)×100 = 122,100円
  → 所得割(調整前)= 305,300円 → 課税所得>200万円のため調整控除は`max(2,500, 負の値)` = 2,500円
  → 所得割(調整後)= 302,800円 → 年間税額 = 302,800 + 5,000(均等割) = 307,800円
  → 残り月数(6-12月退職・退職月を含まない `17−9`)= 8ヶ月 → 残額 = floor(307,800×8/12) = **205,200円**
  → 本番出力(`remaining`)と完全一致
- 波2(翌年6月からの新規課税、所得基準=退職年の月割り収入 6,000,000/12×9 = 4,500,000円):
  給与所得控除(2026年表・220万円超のため上位区分と同一:×20%+44万)= 1,340,000円
  → 給与所得3,160,000円 → 社会保険料控除 = floor(4,500,000×0.146) = 657,000円
  → 課税所得 = 3,160,000 − 657,000 − 430,000 = **2,073,000円**
  → 市民税124,300円、県民税82,900円 → 所得割(調整前)207,200円
  → 課税所得>200万円のため調整控除は`max(2,500, 負の値)` = 2,500円 → 所得割(調整後)204,700円
  → 年間税額 = 204,700 + 5,000 = **209,700円**
  → 本番出力(`nextYearTax.total`)と完全一致

### ケース2:退職前年年収400万円・1月退職(1-4月・強制一括徴収)
- 波1(所得基準=前々年代用・年収400万円):
  給与所得控除(360万超660万以下:×20%+44万)= 1,240,000円 → 給与所得2,760,000円
  → 社会保険料控除 = floor(4,000,000×0.146) = 584,000円
  → 課税所得 = 2,760,000 − 584,000 − 430,000 = **1,746,000円**
  → 市民税104,700円、県民税69,800円 → 所得割(調整前)174,500円
  → 課税所得≤200万円のため調整控除 = floor(min(50,000, 1,746,000)×0.05) = 2,500円
  → 所得割(調整後)172,000円 → 年間税額 = 172,000 + 5,000 = 177,000円
  → 残り月数(1-4月退職・退職月を含む `6−1`)= 5ヶ月 → 残額 = floor(177,000×5/12) = **73,750円**
  → 本番出力(`remaining`)と完全一致

いずれも桁単位まで一致したため、実装の変換パイプライン・端数処理(社会保険料控除→
基礎控除の順で1回だけクランプ、市民税/県民税を個別に100円未満切り捨て、調整控除の
`max(2,500, ...)`下げ止まり)が意図通り動作していることを確認した。

社会保険料控除・調整控除それぞれの定数・境界値の直接検算(`calcSocialInsuranceDeduction`・
`calcAdjustmentDeduction`単体呼び出し、課税所得0円/3万円/5万円/200万円/200万1円/205万円/
300万円/1,000万円の8パターン、うち300万円・1,000万円は「205万円を大きく超えても0円にならない」
という訂正内容そのものを検証)は`scripts/verify-resident-tax-timing-tool.js`の
「【社会保険料控除】」「【調整控除】」ブロックに組み込み済み。

## 既存テストケースへの影響(回帰ではなく意図した変化)

社会保険料控除(概算14.6%/15.4%)を新たに課税所得の計算チェーンに追加したことで、
ほぼ全ての金額が変化した。代表例(退職前年年収600万円・9月退職、40歳未満デフォルト):

| 項目 | 導入前(コミットdccbfddの値) | 導入後 | 差分の理由 |
|---|---|---|---|
| 波1残額(remaining) | 265,333円 | 205,200円 | 社会保険料控除(876,000円)分だけ課税所得が縮小し税額が減少。ただし調整控除2,500円の減額も加わっている |
| 波2合計(NEXT_YEAR_TOTAL) | 278,000円 | 209,700円 | 同上(社会保険料控除657,000円+調整控除2,500円) |

いずれも「社会保険料控除により課税所得が下がる→税額が下がる」という設計通りの方向の変化であり、
`calcSalaryIncomeDeduction`・`calcTaxableSalaryIncome`(社会保険料率0%指定時)・
`calcSocialInsuranceDeduction`・`calcAdjustmentDeduction`の単体テストは導入前と同じ期待値のまま
全てPASSしているため、既存ロジック自体への回帰は確認されなかった(変化は新規パラメータの追加分のみ)。

`scripts/verify-resident-tax-timing-tool.js`のMATRIX・NEXT_YEAR_TOTAL・「前々年入力あり」・
「installment/lump」・「postRetirementIncome加算」・「override指定」・「不具合再現ケース」の
各期待値は、上記の理由により全面的に再計算した(旧値からの単純な差分ではなく、本番コードの
実出力を新たな期待値として採用。うち2ケースは上記のPython Decimal相当の手計算で独立検証済み)。
