# 調査専用指示書：CompanyState設計のための事前調査（①②③④スコープ）

作成日：2026-08-20

---

## 1. 背景・目的

一人法人(Hitori-Hojin)向けに、法人資産を含めたFIRE試算機能「CompanyState」を新設する。これは以下の4要素で構成される予定（詳細はこの指示書末尾の「参考：確定済み設計」を参照）。

1. 事業タイムライン（法人の「事業利益」「取崩」を、期間・金額/年で複数登録できる入力）
2. 法人ポートフォリオ（現在PF／積立期PF／取崩期PFの3フェーズ構成）
3. 法人資産成長計算（②の期待リターン×①の事業利益で年次成長）
4. 取崩→個人化変換（①の取崩額を実効税率で税引き後に変換し、個人側のシミュレーションに注入）

この指示書は**実装前の事前調査のみ**を目的とする。④の実装可否を判断するために、既存のシミュレーターエンジン(`simulate.ts`/`analyze.ts`)や、①②の複製元となる既存UIパターン(`LifeEventTimeline`相当・`PortfolioPanel.tsx`)の内部構造を正確に把握する必要がある。

---

## 2. 絶対にやってはいけないこと

- **実装・修正は一切行わないこと**。本指示書は調査専用。コードの新規作成・既存ファイルの変更は一切不要
- **ロックファイル（`simulate.ts`/`analyze.ts`/`profile.ts`/`PortfolioPanel.tsx`/`simulatorStore.ts`/`blog.ts`/`blogTopics.ts`/`concerns.ts`）には一切手を加えないこと**。読むだけ
- 独自に再実装したスクリプトで検証しないこと。既存のコード・型定義を読んで報告すること
- 調査結果から「こう実装すべき」という推測・提案を書かないこと。事実の報告に徹すること（実装方針はこのチャットで判断する）

---

## 3. 調査対象・確認事項

### 3.1 `simulate()`/`analyze()`の年次収入ストリーム受け入れ可否

**目的**：法人からの取崩額（税引き後・年ごとに変動しうる）を、既存のシミュレーションエンジンにどう注入できるかを把握する。

確認すること：

1. `simulate()`（および呼び出す場合は`analyze()`）の関数シグネチャ、引数の型定義（`SimParams`等）を確認し、全文を報告する
2. 「収入」を表すパラメータが、シミュレーター内部でどう扱われているか：
   - 単発イベント型（退職金のように、特定の年に1回だけ計上される）なのか
   - 継続収入型（給与収入のように、開始年齢〜終了年齢の間、毎年一定額または可変額が加算される）なのか
   - 上記どちらでもなく、別の構造（例：年齢ごとの配列を直接渡す等）なのか
3. 添付画像で確認された「ライフイベント」機能（`収入/支出`種別、`副業`等のカテゴリ、開始年齢・期間・金額/年）が、実際にどの型・どのファイルで実装されているか特定する。このイベント形式が「毎年金額が変動する複数期間の収入」を表現できる既存の仕組みなのかを確認する
4. 3で特定した「ライフイベント」の型が、`simulate()`の内部でどのように年次計算に反映されているか（コードの該当箇所を引用しつつ）追跡して報告する
5. 上記を踏まえ、「法人からの取崩額（税引き後）」を新しいライフイベント種別（例：`corporate_withdrawal`）として追加する場合に、型定義・計算ロジックのどこに新規追加が必要になりそうか（あくまで構造の報告。実装はしない）

### 3.2 `LifeEventTimeline`パターンの実装詳細

**目的**：法人側の「事業利益」「取崩」タイムライン入力を複製実装するための、複製元の正確な仕様を把握する。

確認すること：

1. 添付画像のUI（タイムライン、収入/支出セレクタ、名称、開始年齢、期間、金額/年、追加/キャンセルボタン）に対応する実際のコンポーネントファイルを特定する（ファイルパスを明記）
2. そのコンポーネントのProps構造、内部state管理方法（`useSimulatorStore`への依存有無を含む）を報告する
3. イベント種別（収入/支出、副業等のカテゴリ）の型定義（enum等）の全体を報告する。新しい種別（法人の事業利益・取崩）を追加する余地があるか、それとも種別リストが決め打ちで拡張しにくい構造か
4. このコンポーネントが`useSimulatorStore`や他のロック対象ファイルに直接依存しているか（Hitori-Hojin資産管理ツールの`AssetCard`調査時と同様の観点で、「新規実装が必要か、複製可能か」を判断できる情報を集める）
5. タイムラインのデータが最終的にどの型に格納され、`simulate()`にどう渡されているか（3.1の調査と接続する形で報告する）

### 3.3 `PortfolioPanel.tsx`の3フェーズ構成の実装詳細

**目的**：法人ポートフォリオ（現在PF／積立期PF／取崩期PF）を複製実装するための仕様を把握する。

確認すること：

1. 添付画像の「①現在PF／②積立期シミュレーションPF／③取崩期シミュレーションPF」「利回り設定」「MC設定」に対応する実装箇所（`PortfolioPanel.tsx`内、または関連ファイル）を特定する
2. 資産クラス別％配分から μ・σ を自動算出するロジック（`calcMu`/`calcPortfolioMetrics`等、Hitori-Hojin資産管理ツール調査時に発見済みの関数）が、この3フェーズ構成とどう連動しているか報告する
3. 「①現在PFのみ」「②③は積立期/取崩期で別設定 or 同じ設定を使う」というフェーズ間の連動・独立の仕組み（トグルの有無等）を報告する
4. このコンポーネントが`useSimulatorStore`や他のロック対象ファイルにどう依存しているか（3.2と同様の観点）
5. 資産クラス一覧は、Hitori-Hojin資産管理ツールで既に複製済みの`ASSET_CLASSES`（+不動産）と同じものを使うことを想定している。もし法人側の想定資産クラスが個人側と異なる可能性がある場合（例：非上場株式など法人特有の資産）、既存の`ASSET_CLASSES`定義に触れつつ、その可能性の有無を報告する（判断はしない、事実確認のみ）

## 5. 参考：確定済み設計（このチャットでの合意事項、変更不可）

- 法人資産の成長：`前年末残高 × (1+資産クラス別期待リターン) + 事業利益(タイムライン入力)`
- 取崩：`法人資産 -= 取崩額(タイムライン入力)`、`個人側の年次収入 += 取崩額 × (1−実効税率)`
- 実効税率は単一パラメータ（ユーザー入力、目安20〜30%）。法人税・個人所得税・社会保険料を分けて精緻計算することはしない（Stage Aではやらない、将来のバックログ）
- 事業タイムラインの切替タイミングは「退職時」等に固定せず、個人側ライフイベントと同様、ユーザーが任意のタイミングで複数イベントを登録できる
- 法人ポートフォリオは個人側と同じ3フェーズ構成（現在PF／積立期PF／取崩期PF）
- 資産管理ツールとの連携（実績データの取り込み、目標配分との比較、実績×予測の重ね合わせ表示）は別スコープ。今回の調査には含めない
