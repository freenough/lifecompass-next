# 調査報告:退職翌年の住民税ロジック調査(調査のみ・実装なし)

指示書:「退職翌年の住民税」ブログ記事の執筆に向けた事前調査。本セッションはコード変更を一切行っていない。

---

## 1. 現状ロジックの実装場所・構造

### `calcResidentTax()` — 住民税計算の唯一の共通関数
- 場所: `src/lib/tax/retirement.ts:176-186`
- シグネチャ: `calcResidentTax(taxableIncome: number): { municipal: number; prefectural: number; total: number }`
- 中身: 標準税率のみ。市民税6%・県民税4%(=合計10%)をそれぞれ100円未満切り捨てしてから合算。
  ```ts
  const MUNICIPAL_TAX_RATE = 0.06;
  const PREFECTURAL_TAX_RATE = 0.04;
  ```
- **これが唯一の住民税計算ロジックであり、リポジトリ内に他の実装は存在しない**(`src/`全体を`住民税`で検索し確認)。

### 呼び出し元(3箇所、すべて「その年の分離課税所得 or 総合課税所得」に対する計算)
1. `retirement.ts` `calcRetirementIncomeTax()` — 退職金手取り計算ツール(`/tools/retirement-tax`)本体。課税退職所得金額に対して直接適用。
2. `retirementIdecoTiming.ts` `calcTaxFromDeductionAndIncome()` — 退職金×iDeCo受給タイミングツール。施行令70条調整後の控除額を使う退職所得側の税額計算で再利用。
3. `ideco.ts` `calcComprehensiveIncomeTax()` — iDeCo年金(雑所得)ツールの総合課税。住民税だけ所得税と別の基礎控除43万円を使う独立計算。

### retirement-taxツールとの関連
`retirement-tax`ツール(`src/app/tools/retirement-tax/page.tsx` → `RetirementTaxTool.tsx` → `src/lib/tax/retirement.ts`)は`calcResidentTax()`の直接の主要利用者。ただしこのツールが計算しているのは**退職金(退職所得)そのものに対する住民税**であり、記事のテーマである「給与所得の前年課税タイムラグ」とは別物(詳細は2.)。

### 本体シミュレーター(simulate.ts/helpers.ts)側
- `simulate.ts`・`helpers.ts`を`住民税`で検索してもヒットなし。本体シミュレーターは給与収入(`baseInc`/`spInc`)を**手取り額として入力させる設計**であり、給与に対する所得税・住民税計算を一切行っていない。
- `helpers.ts`の`retirementTaxCalc()`(93-122行目)は退職金+iDeCo一時金に対して**所得税と住民税を分離せず一律20.315%**で近似する簡易ロジック(`methodology`ページで「①税率は簡易計算」として明記された既知の簡略化、`src/app/methodology/page.tsx:153-159`)。住民税単体の金額は取り出せない。

## 2. 前年所得ベースのタイムラグ: **非対応(できない)**

- `calcResidentTax(taxableIncome)`は「ある年の課税所得」を受け取ってその場で税額を返すだけの純粋関数で、「前年の所得」「翌年度に課税される」という年度をまたぐ概念は一切持たない。
- ただし、これは3つの呼び出し元にとってはむしろ**正しい**挙動: 退職所得(退職金・iDeCo一時金)にかかる住民税は、地方税法上「分離課税に係る所得割」として**現年分離課税**(支払われた年に他の所得と分離して特別徴収)されると総務省が明記している(出典6.参照)。給与所得のような翌年度課税ではない。
- 一方、**給与所得の住民税は「前年中(1月〜12月)の所得を基準に翌年度課税」**というのが総務省の公式説明(出典6.参照)。この「退職前年の給与所得 → 退職翌年に住民税が来る」というタイムラグそのものをモデル化した関数・計算経路はリポジトリ内に**存在しない**。
- 結論: 記事の核心である「退職前年の給与を基準に、収入が下がった(または無収入の)退職翌年に住民税の請求が来る」という現象は、現状のツール・本体シミュレーターのどちらでも計算不可能。給与は手取り前提の入力値であり、そこから所得税・住民税を逆算する経路自体がない。

---

## 3. 均等割・所得割の分離状況

- **分離されていない、というより均等割自体がコード上に一切存在しない**。`calcResidentTax()`は所得割(6%+4%)のみを計算し、均等割(定額部分)を加算する処理はどこにもない(`均等割`で`src/`全体を検索してもヒットなし)。
- 均等割の標準額は、総務省の資料によれば道府県民税1,000円+市町村民税3,000円=4,000円、これに森林環境税(国税・令和6年度から均等割と併せて賦課徴収)1,000円を加えた**合計5,000円/年**が現在の標準(出典6.参照)。
- 記事の論点への影響: 「退職翌年、収入が激減しても住民税だけは前年所得ベースで重くのしかかる」という論点のうち、**所得割部分は既存の`calcResidentTax()`ロジックを流用して試算可能**だが、**均等割(無収入でも原則かかる定額約5,000円)は現状ゼロとして扱われており、別途手動で加算しないと過小評価になる**。

---

## 4. 退職所得(退職金)の住民税の扱い

- **含まれている**(退職金手取り計算ツール・退職金×iDeCo受給タイミングツールの2つ)。課税退職所得金額(控除・1/2適用後)に対し`calcResidentTax()`で6%+4%を適用。
- ただし本体シミュレーター(`simulate.ts`)側は上記の通り所得税・住民税を分離しない一律20.315%近似であり、退職金部分の住民税額単体を取り出す経路はない。
- したがって「退職金そのものの住民税」は一部のツールでのみ正確に扱われており、記事が扱う「給与所得の翌年度課税タイムラグ」とは計算経路が完全に別(退職金は現年分離課税、給与は翌年度課税で制度自体が異なる)。

---

## 5. 特別徴収・普通徴収の扱い

- **計算ロジック・説明文どちらにも一切登場しない**。`特別徴収`・`普通徴収`で`src/`全体を検索してもヒットなし。
- 実務上、この徴収方法の切り替わり(在職中は給与天引きの特別徴収 → 退職後は自分で納付する普通徴収、または退職金から一括徴収)こそが「退職翌年の住民税」が家計インパクトとして可視化されるタイミングそのものだが、これは制度説明としても数値計算としても現状ノータッチ。

## 7. 記事執筆にあたっての予備判断(category軸の判定材料)

- **シミュレーター/ツール実出力はそのまま使えない**。既存の`retirement-tax`・`retirement-ideco-timing`ツールが計算する住民税は「退職金(退職所得)自体への現年分離課税」であり、記事の核心である「給与所得の前年課税タイムラグ」とは制度上別物。本体シミュレーターは給与を手取り前提の入力としており、所得税・住民税の逆算経路自体が存在しないため、退職前後の給与に対する住民税額はどのツールからも出力できない。
- **独自試算が必要**。ただし完全な独自実装ではなく、`calcResidentTax()`の所得割ロジック(6%+4%、標準税率)は部品として流用可能。均等割(標準約5,000円/年)は現状コードにないため、記事内で手動加算するか、少なくとも「本シミュレーターの均等割相当額」として明記が必要。
- 予備判断としては、**「シミュレーター活用」ではなく「制度解説+簡易試算(独自計算ベース)」寄りのcategoryになる可能性が高い**。給与所得の翌年度課税・特別徴収と普通徴収の切り替えという実務の説明が数値計算以上に記事の主軸になる見込み。
