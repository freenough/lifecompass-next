# 調査報告:給与所得控除テーブルの令和8年度税制改正対応(調査のみ)

`docs/fixes/active/investigation_kyuyo_koujo_reiwa8_taiou.md` の実装。**コード変更は一切行っていない。**

---

## 1. 法的状態の確認(最優先)

**既に法律として成立・公布済み。** 「令和8年度税制改正の大綱」(令和7年12月26日閣議決定)の内容を
盛り込んだ「所得税法等の一部を改正する法律」は、令和8年2月20日に閣議決定・国会提出、
3月13日に衆議院可決、**3月31日に参議院本会議で可決・成立、同日官報に公布**され、
**原則として令和8年4月1日に施行**された。地方税(個人住民税)側も同様に改正法が成立している。

出典:[税のしるべ電子版「8年度税制改正法が成立、原則8年4月1日に施行」](https://shirube.zaikyo.or.jp/article/2026/03/31/10345296.html)、
[税理士法人山田&パートナーズ「2026年度税制改正法、3月31日に成立」](https://www.yamada-partners.jp/tax-topics/r080406)

→ **本ツールでは「未確定の法案」ではなく「既に確定した法律」として扱ってよい段階にある。**

## 2. 給与所得控除の完全なテーブル(全区分・財務省一次資料で確認)

財務省の一次資料(「給与所得控除制度・給与所得控除の最低保障額の特例の概要」)に掲載されている
公式グラフ・表から、以下の通り正確に確認した。

出典:[財務省 https://www.mof.go.jp/tax_policy/summary/income/049.pdf](https://www.mof.go.jp/tax_policy/summary/income/049.pdf)

### 最低保障額と、その適用上限額(＝「フラット部分」の範囲)
| 年分(所得税ベース) | 最低保障額 | フラット部分の上限額 |
|---|---|---|
| 令和7年分 | 65万円 | **190万円**(既存実装のまま) |
| 令和8年分・令和9年分(特例) | 74万円(69万円+特例5万円) | **220万円** |
| 令和10年分以降(特例終了後・恒久) | 69万円 | **204万円** |

(住民税は1年遅れで適用されるため、令和8年分所得→令和9年度住民税、令和9年分所得→令和10年度住民税、
令和10年分所得以降→令和11年度住民税以降、という指示書記載の対応表で正しい)

### 190万円/204万円/220万円を超える部分の速算表(**全時代共通・変更なし**)
| 給与収入 | 控除額 |
|---|---|
| 360万円以下 | 給与収入×30%+8万円 |
| 660万円以下 | 給与収入×20%+44万円 |
| 850万円以下 | 給与収入×10%+110万円 |
| 850万円超 | 195万円 |

**重要な発見**:190万円・204万円・220万円という3つの閾値は、いずれも「給与収入×30%+8万円」という
**単一の直線上に正確に乗る点**になっている(190×0.3+8=65、220×0.3+8=74。204は69.2≒69万円で
近似的に同一線上)。つまり、**この改正は「フラット部分の高さと幅」だけを変更するものであり、
220万円(または204万円・190万円)を超える範囲の速算表(360万・660万・850万円の閾値、
×30%/×20%/×10%+定額という式そのもの)は、令和7年分・令和8〜9年分・令和10年分以降の
いずれにおいても完全に同一である**。この点は財務省一次資料のグラフで、3本の折れ線が
190万円台〜220万円台超の領域で完全に1本の線に収束していることから確認できる。

### 対象外の追加控除(本ツールのスコープ外・参考)
給与収入850万円超で「特別障害者に該当する」または「23歳未満の扶養親族を有する」等の場合に
適用される「所得金額調整控除」(最大15万円)も同じ資料に記載されているが、**本ツールは
独身・扶養なし前提のため該当しない**(前回セッションの前提明示フェーズ0で「独身・扶養家族なし」
であることをUIに明記済み)。

## 3. 住民税の基礎控除(43万円)への影響

**変更なし。** 大阪市の令和9年度改正解説ページの対照表に「改正なし(最高43万円)」と明記されている。
これは前回セッションで確認済みの令和7年度改正時の資料(「②基礎控除の見直し:個人住民税は改正なし
(最高43万円)」)と同じ扱いが今回の令和8年度改正でも継続されていることを意味する。

出典:[大阪市「令和9年度から実施される市民税・府民税の税制改正について」](https://www.city.osaka.lg.jp/zaisei/page/0000678587.html)

→ `RESIDENT_TAX_BASIC_DEDUCTION`(43万円)は**変更不要**。

---

## 4. 非課税限度額(45万円)への影響

**「基本額等」(所得ベースの45万円)自体は変更なし。** 大阪市の同ページに「課税されない給与収入金額
(単身者)は改正前110万円から、令和9・10年度は119万円、令和11年度以降は114万円に引き上げられる」
との記載がある。この収入ベースの引き上げ額(119-110=9万円、114-110=4万円)は、給与所得控除の
最低保障額の増加分(74-65=9万円、69-65=4万円)と完全に一致しており、**「基本額等」(所得ベースの
45万円)そのものは変わらず、給与所得控除の増加分がそのまま収入ベースの非課税ラインに上乗せされて
いるだけ**であることが、この数値の整合性から裏付けられる。

→ `NON_TAXABLE_SALARY_INCOME_THRESHOLD`(45万円、所得ベース)は**変更不要**。ただしUI上で
「給与収入110万円以下」等、収入ベースの目安値を表示している箇所があれば、年度に応じて
110万円→119万円→114万円と表示を変える必要が生じる(現状の実装は所得ベースの45万円で
判定しているため、コード自体は無修正で正しい判定を維持できる)。

## 5. 実装方針への示唆

### 重要な再評価:影響範囲は指示書の想定より大幅に狭い

指示書は「大多数のユーザーが該当し、緊急度は高い」としていたが、**2.の発見(220万円・204万円を
超える範囲の速算表が全時代で完全に同一)を踏まえると、この評価は修正が必要**:

- 波1(`incomeBasisAmount`、前年/前々年の**年収**が基準)は、本ツールの典型的な入力値
  (400〜800万円)であれば**常に220万円を大きく超えている**ため、どの年度のテーブルを使っても
  **控除額は1円も変わらない**。→ 波1には実質的に影響なし。
- 波2(`retirementYearIncome`、退職年の**推計所得**)は、月割り推計(`年収÷12×退職月`)により、
  退職月が早い(1〜3月頃)場合や年収そのものが低い場合に220万円を下回るケースがあり得る。
  **この場合にのみ、最大9万円(令和8・9年分)または4万円(令和10年分以降)の控除差が生じる。**
- 実際、既存の`verify-resident-tax-timing-tool.js`のMATRIX(400/600/800万円×1月退職)では、
  1月退職時の推計所得が33〜67万円程度(いずれも220万円を大幅に下回る)になっており、
  **これらのケースは影響を受ける**。5月以降の退職では推計所得が220万円を超えることが多く、
  影響を受けない。

→ **緊急度は「低所得帯・早期退職シナリオに限定された中程度」に修正すべき**。ただし該当する
ケース自体は実在し(月割り推計が低くなる早期退職パターン)、無視してよい問題ではない。

### 影響額の試算(200〜220万円未満の低所得帯のみ、指示書の要求通り概算)
- 令和8・9年分(住民税では令和9・10年度)に該当する低所得帯(推計所得≤220万円)のユーザー:
  控除差 最大9万円 → 課税所得が9万円減る → 住民税所得割が9万円×10%=**最大9,000円/年、過大表示**
- 令和10年分以降(住民税では令和11年度以降)に該当する場合:控除差 最大4万円 →
  **最大4,000円/年、過大表示**
- 220万円を超える所得(本ツールの主要な想定年収帯である波1側)には**影響ゼロ**

### 設計変更案
1. `calcSalaryIncomeDeduction(incomeYen, taxYear)`のように、**第2引数に「その収入が発生した
   暦年(西暦)」を追加**する設計が最小の変更で済む。テーブル自体は「フラット部分の閾値・金額」
   だけを年により切り替え、220万円(または204万円)超の部分は共通ロジックのまま流用できる
   (2.で確認した通り、上位区分の式は変更不要なため、実装上の分岐は最初の1行だけで済む)。
2. `taxYear`をどう取得するかが課題:本ツールは現在「西暦年」の入力を一切持たず、
   `retirementMonth`(1〜12)のみで年をまたぐ判定(前年/前々年/退職年)をしている。
   - 案A:サーバー/クライアントの実行時点の西暦年(`new Date().getFullYear()`)を「退職年」と
     みなし、そこから前年・前々年を逆算する(ユーザー入力の追加が不要、実装コストが最小)。
   - 案B:ユーザーに「退職年(西暦)」の入力欄を追加する(過去・未来のシナリオも試算できる
     柔軟性がある一方、UI変更・入力必須項目の増加というコストが伴う)。
   - 案Aの方が既存設計(「今日」を暗黙の基準にしている)と整合し、実装コストも低いという所見。
3. 波1・波2でそれぞれ異なる年のテーブルを参照する必要がある(波1は前年/前々年、波2は退職年)。
   両方とも同じ`calcSalaryIncomeDeduction(incomeYen, taxYear)`を呼ぶだけでよく、
   呼び出し側(`calcCurrentYearTax`/`calcNextYearTax`)で`taxYear`を計算して渡す形にすれば、
   共通関数自体の二重実装は避けられる。
