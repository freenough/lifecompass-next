# 調査報告:1〜5月退職時の「波2」所得基準年の誤りの検証と設計修正案

`docs/fixes/active/investigation_wave2_1to5gatsu_taisho.md` の実装。**本調査ではコード変更を一切行っていない。**

---

## 1. 現状のコードの動作確認結果:**疑いは事実として確認された**

`src/lib/tax/residentTaxTiming.ts`の`calcNextYearTax()`(454-497行目)を確認したところ、
退職月による分岐は一切なく、常に以下の単一の式で「退職年の所得」を合成していた。

```ts
const estimatedRetirementYearIncome = (priorYearIncome / 12) * retirementMonth + postRetirementIncome;
```

これは`retirementMonth`の値(1〜12のいずれでも)に関わらず無条件に適用される。`calcCurrentYearTax()`
(波1側)は`retirementMonth <= 5`で所得基準年(前々年/退職前年)・徴収区分を分岐させているのに対し、
`calcNextYearTax()`側にはこれに相当する分岐が一切存在しない。

さらに、`ResidentTaxTimingComparisonTable.tsx`(退職月別の比較表)も内部で`calcResidentTaxTiming()`を
そのまま呼んでいるだけのため、比較表の「3月」行(1〜5月グループの代表)も同じ誤りの影響を受けている
ことを確認した。UIの見出し文言「② 退職した年の所得をもとにした、翌年6月からの新しい住民税」
(`ResidentTaxTimingResult.tsx`)・比較表の列見出し「翌年6月〜」も、この誤った計算式の前提
(退職年Yの部分所得を基準に、翌年Y+1年6月から課税)をそのまま反映した文言になっている。

## 2. 制度上の整理の再確認結果:**指示書の整理は正しい**

既存の2本の調査報告書と照合した結果、指示書の制度整理と矛盾しなかった。

- `investigation_juminzei_taimurag.md`が総務省一次情報で確認済みの「個人住民税は前年中(1〜12月)
  の所得を基準に翌年度(6月〜翌5月)課税される」という基本ルールに、指示書の波1・波2・波3の
  整理はそのまま従っている。
- `investigation_juminzei_futsuchoshu_wariate_result.md`(1章)が確認した「1〜4月退職は強制一括徴収・
  5月退職は通常徴収で完了・6〜12月退職は任意一括徴収/普通徴収」という3区分ルールは、
  波1(進行中の年度)の徴収方法の話であり、これ自体は指示書・現状実装のどちらとも矛盾しない。
- ただし、**「波2の所得基準」を退職月で分岐させるべきという論点そのものは、この2本の既存報告書の
  どちらでも直接検討されていなかった**ことも確認した。`investigation_juminzei_futsuchoshu_wariate_result.md`
  5章(87-89行目)は`nextYearTax.taxableIncome`の設計として「退職前給与(自動算出)+退職後給与収入
  (入力)を合算し、給与所得控除を1回だけ適用する」という**賞与近似の妥当性**は論じているが、
  「そもそもこの合成対象の基準年が6〜12月退職と1〜5月退職で違うはずだ」という年度またぎの
  分岐については触れていない。つまり、現状の設計・実装は「6〜12月退職を想定した合成ロジックを
  1〜5月退職にもそのまま流用してしまった」ものであり、当時の報告書が誤っていたわけではなく、
  1〜5月退職のケースの検討自体が抜けていたと理解するのが正確。

### 1〜5月退職時の「波2」が前年(Y-1)まるまる1年分を基準にするという理解の裏付け
指示書の主張(1〜5月退職の波2は`priorYearIncome`をそのまま使うべき)は、以下の理由で
既存の一次情報の範囲内で導出できる(新たな一次情報調査は不要と判断した)。

- 波1(進行中)の徴収期間は「(Y-1)年6月〜Y年5月・所得基準=前々年(Y-2)」であることは
  現状実装・調査報告書1で確認済み。
- 個人住民税の徴収サイクルは「前年所得を基準に6月〜翌5月課税」という規則的な1年周期
  (`investigation_juminzei_taimurag.md`69行目)であるため、波1の直後(Y年6月)に始まる
  次のサイクルは、機械的に「基準年を1年進める」だけで求まる: 基準年は(Y-2)の次、つまり
  (Y-1)年。
- 退職者は1〜5月に退職しているため、(Y-1)年(前年)は**年間を通じて在職していた**
  (退職月が1〜5月ということは、前年は1月から12月まるまる会社に在籍していたことを意味する)。
  したがって(Y-1)年の所得は「部分所得の月割り推計」ではなく、**確定した1年分の給与収入
  (=`priorYearIncome`そのもの)** を使うのが制度上正しい。これは月割り推計が必要な
  「退職した当年(Y年)の部分所得」とは性質が異なる。
- 一方、6〜12月退職の波2(現状実装が正しく計算できているケース)は、退職者が退職した
  「その年(Y年)」自体が部分所得(1月〜退職月)になるケースであり、月割り推計が必要になる
  ・タイミングも1年後(Y+1年6月)になる、という点で1〜5月退職の波2とは根本的に別物。

以上より、指示書の整理(1〜5月退職の波2は前年まるまる1年分・月割りしない)は、既存の
一次情報(前年課税の1年周期性、給与所得控除は年間ベースという確認済みルール)から矛盾なく
導出でき、新たな一次情報確認は不要と判断した。

## 3. 影響額の試算(退職前年年収600万円・5月退職)

`calcResidentTaxTiming({ priorYearIncome: 6_000_000, retirementMonth: 5, postRetirementIncome: 0 })`
を実行して確認した現状の出力と、指示書の整理に基づく「本来の波2」を試算した(いずれも
40歳未満デフォルト料率14.6%、`incomeYear`はセッション実行時点=2026年を退職年Yとして
`retirementYear - 1 = 2025`を使用)。

### 現状の実装が返す「②」(誤り。実質は「波3」の計算)
- 基準:退職年(2026年)の部分所得の月割り推計 = `6,000,000 ÷ 12 × 5` = 2,500,000円
- **年間税額(=②として表示される額) = 90,000円**(`scripts/verify-resident-tax-timing-tool.js`の
  `NEXT_YEAR_TOTAL['6000000-5']`の実測値)

### 本来「波2」として表示すべき金額(前年まるまる1年分基準)
`priorYearIncome`(6,000,000円)をそのまま使い、既存の`calcAnnualResidentTax()`
(波1が使っているのと同じヘルパー、`incomeYear=2025`)に通した年間税額。これは同じ「600万円・
2025年分基準」を使う既存MATRIX(600万円・9月退職/12月退職の波1)の`annualTax`と共通の値になる
(月数による按分をしない、満額の年間税額)。
- 給与所得控除(2025年表・360万超660万以下)= 1,640,000円 → 給与所得4,360,000円
- 社会保険料控除(14.6%)= 876,000円 → 課税所得 = 4,360,000 − 876,000 − 430,000 = 3,054,000円
- 市民税183,200円+県民税122,100円 = 所得割(調整前)305,300円 → 調整控除2,500円差引後302,800円
- 均等割5,000円を加算
- **年間税額(=本来の②) = 307,800円**

### 差分
`307,800円 − 90,000円 = 217,800円`(現状の実装は本来の約29%しか表示できておらず、
残り約71%・217,800円が家計へのキャッシュアウト予測から丸ごと欠落している)。

さらに深刻なのは金額だけでなくタイミングの誤りである。現状の②は「退職翌年(2027年)6月から」の
課税として表示されるが、本来の波2は**退職の翌月である2026年6月から**始まる、はるかに近い将来の
支出である(波1が2026年5月に終わった直後に始まる、間を置かない新しいサイクルのため)。
つまり現状のツールは、1〜5月退職のユーザーに対して「最も緊急度が高く・最も金額の大きい
支出」を一切見せられていない状態にある。

`totalCashNeeded`(確保しておきたい現金の目安)への影響: 現状は`0(波1) + 90,000(誤った②) = 90,000円`
だが、本来最優先で示すべき額は少なくとも`0 + 307,800 = 307,800円`(案Aを採用し波3を表示しない場合)、
案Bで波3も併記するなら`0 + 307,800 + (現状の90,000円相当の波3) ≒ 397,800円`規模になる
見込みで、いずれにせよ現状の表示額の3倍以上に修正される可能性が高い。

## 4. 設計修正案

### 案A:波2の所得基準を退職月で分岐させる(推奨)

**変更内容**
- `calcNextYearTax()`に`retirementMonth`による分岐を追加:
  - 6〜12月退職:現状通り(退職年Yの部分所得、月割り推計、`salaryDeductionApproxNote`等も現状通り)
  - 1〜5月退職:`priorYearIncome`をそのまま使う(月割りしない)。`incomeYear = retirementYear - 1`
    (波1の`incomeYear = retirementYear - 2`から1年進めた値)。実質的には、波1側の
    `calcCurrentYearTax()`が「退職前年」ケース(6〜12月退職時)で行っている計算とほぼ同じ形
    (`calcAnnualResidentTax(priorYearIncome, retirementYear - 1, rate)`をフル(12ヶ月分)で使う)
    になる。
- **`postRetirementIncome`の扱いに注意が必要**:1〜5月退職の場合、`postRetirationIncome`
  (退職後・同一年内の給与収入)は前年(Y-1)の所得には含まれない(それはY年の所得であり、
  波3の基準になる)。1〜5月退職時は`postRetirementIncome`を波2の計算に加算しないよう
  明示的に分岐させる必要がある(現状の`estimatedRetirementYearIncome`の式にそのまま
  `postRetirementIncome`が足されている挙動を、1〜5月退職では使わないようにする)。

**UI・文言への影響**
- `ResidentTaxTimingResult.tsx`の「② 退職した年の所得をもとにした、翌年6月からの新しい住民税」
  という見出しは、1〜5月退職時には実態と合わなくなる(基準は「退職した年」ではなく「退職前年」、
  タイミングは「翌年6月」ではなく「今年(退職と同じ年)6月」になるため)。見出し文言を
  `currentYearTax.incomeBasisYearLabel`と同様に退職月で出し分ける必要がある
  (例:6〜12月退職は現状の文言のまま、1〜5月退職は「退職前年の所得をもとにした、今年6月からの
  新しい住民税」のような文言に変更)。
- `assumptionNotes`の「退職前の給与は前年の年収を月割りした仮定値です。賞与の時期により
  実際の所得とは差が生じます。」という注記は、1〜5月退職では月割りをしなくなるため出し分けが必要
  (1〜5月退職では単に「前年の年収をそのまま使用しています」等に変更、または注記自体を出さない)。
- `ResidentTaxTimingComparisonTable.tsx`の「翌年6月〜」という列見出しも、1〜5月退職の行では
  実際には「今年6月〜」を意味することになるため、列見出しの文言または注記の見直しが必要
  (現状の3月・9月比較のように基準年ラベルだけでなく、開始時期も月によって変わる旨の注記が
  追加で必要になる可能性がある)。
- `postRetirementIncome`の入力欄(ラベル「退職後、同一年内の給与収入」)自体は1〜5月退職でも
  意味を持つ(波3のための入力として残る、後述)が、波2の計算には使われなくなるため、
  1〜5月退職時にこの入力欄が波2に反映されない旨をUI上どう伝えるかも検討事項になる。

**メリット**: 指示書が指摘した「本来最優先で見せるべき最も金額が大きく緊急度の高い支出」を
正しく②として表示できる。UIの構造(①・②の2枠)を変えずに済む。
**デメリット**: 1〜5月退職と6〜12月退職とで②の意味(基準年・タイミング)が変わるため、
UI文言の出し分けが増え、ユーザーへの説明が複雑になる。現状の「波3」に相当する情報
(退職した年の部分所得を基準にした、より先の課税)が表示されなくなる。

### 案B:波3(退職年の部分所得を基準にした、さらに先の新規課税)を別途追加する

**変更内容**
- 案Aの修正(波2を正しい基準に修正)に加えて、1〜5月退職の場合のみ、現状の計算式
  (`priorYearIncome/12×retirementMonth + postRetirementIncome`、退職年Yの部分所得、
  Y+1年6月開始)を「波3」として保持し、③として追加表示する。

**UI設計の所見**
- ③として追加する場合、`ResidentTaxTimingResult.tsx`に新しいセクションを増やすことになるが、
  1〜5月退職時のみ表示される可変構成になるため、`ResidentTaxTimingComparisonTable.tsx`の
  列構成(現状「今の住民税の残り」「翌年6月〜」「合計」の3列)をどう扱うか(1〜5月退職の行だけ
  列が増える、または比較表自体は波2のみに統一するなど)の設計判断が追加で必要になる。
- 比較表・「確保しておきたい現金の目安」の見出し(ヘッドライン)に③を含めるかどうかも論点になる。
  ③は最も遠い将来(1〜5月退職の場合、退職の1〜2年後)の支出であり、「今すぐ確保すべき現金」
  という本ツールのコンセプトからやや外れる可能性があるため、ヘッドライン(`totalCashNeeded`)には
  含めず、注記・別枠での参考情報として表示するという設計も考えられる。
- 最小の変更で済ませるなら、③を独立セクションにせず、既存の「計算根拠を見る」アコーディオン内に
  「なお、退職後さらに翌年(Y+1年)6月からは、退職した年(Y年)の部分所得を基準にした新たな住民税が
  発生します(概算◯◯円)」という注記文だけを追加する、という軽量な折衷案も可能。

**メリット**: 1〜5月退職のユーザーに対しても、6〜12月退職のユーザーと同程度の「先の見通し」
情報(波3相当)を維持できる。既存のテストケース・ドキュメント資産(月割り推計ロジック自体)を
捨てずに再利用できる。
**デメリット**: UIの複雑さが増す(条件によって②③の意味・表示個数が変わる)。ツールのスコープを
「直近2つの支出」から「直近1つ+参考情報」に広げることになり、指示書にある通りスコープ判断が必要。

### 両案共通の検討事項

**`totalCashNeeded`の算出範囲への影響**
- 両案共通で、1〜5月退職のケースは`totalCashNeeded`が現状より大幅に増額される
  (今回の試算例では90,000円→307,800円、約3.4倍)。既存のテストケース
  (`scripts/verify-resident-tax-timing-tool.js`のMATRIX・NEXT_YEAR_TOTAL)のうち、
  `retirementMonth`が1〜5のもの(1月・5月のケース)は期待値の全面的な再計算が必要になる。
  比較表(`ResidentTaxTimingComparisonTable.tsx`)の「3月」行も同様に再計算が必要。
- 案Bでヘッドラインに波3を含めない設計を採る場合、`totalCashNeeded`自体は案Aと同じ増額幅
  (約3.4倍)に留まる。ヘッドラインに波3を含める設計を採る場合は、さらに大きく増額される。

**6〜12月退職のケースへの影響がないことの確認方法**
- `calcNextYearTax()`の分岐を`retirementMonth <= 5`で切るため、6〜12月退職の経路
  (`estimatedRetirementYearIncome`の式・その他のロジック)はコード上一切変更しない。
  影響がないことは、既存の`scripts/verify-resident-tax-timing-tool.js`のうち
  `retirementMonth`が6〜12のテストケース(9月・12月のMATRIX行、比較表の6月・9月・12月列、
  「前々年入力あり」以外のブロックの大半)が、実装後も一切の期待値変更なくPASSし続けることで
  確認できる(6〜12月退職のケースは1件も期待値を変えずに済むはずであり、もし変わってしまえば
  分岐の実装ミスを意味する)。

### 推奨案
**案Aを最小実装として先に行い、案Bの③(またはその折衷案である注記追加)は別チケットとして
検討することを推奨する。** 理由:
1. 指示書の試算(3.)が示す通り、現状の最大の問題は「①②の合計が実際より約3倍過小」という
   金額面の致命的な誤りであり、これは案Aだけで解消できる。③の追加は「情報の充実」であり、
   バグ修正の緊急度としては②の是正より低い。
2. 案Bは比較表の列構成・ヘッドラインの範囲など追加のUI設計判断を伴うため、②の是正
   (バグ修正)と③の追加(機能拡張)を同一の実装単位で扱うと、指示書の禁止事項
   (「実装はしない、方針の提案のみ」)の範囲を超えて設計が肥大化しやすい。まず案Aで
   正しい②を実装し、③が本当に必要かはユーザーの実際のフィードバック(手動テストでの
   反応)を見てから改めて判断するのが安全。

## 5. 実装時に追加で必要になりそうな一次情報確認事項

- 特になし。本調査の範囲(2.)で確認した通り、1〜5月退職時の波2の基準年について、既存の
  一次情報(前年課税の1年周期性、給与所得控除は年間ベースという確認済みルール)から矛盾なく
  導出できるため、実装(案Aの場合)にあたって新たな一次情報の調査は不要と判断する。
- ただし、案Bで③を実装する場合、「退職した年(Y年)の部分所得を基準にした課税が、退職から
  何年後に発生するか」というタイミングの説明文言をUIに正確に載せる必要があるため、実装直前に
  1〜5月退職の場合のタイミング(Y+1年6月開始)を改めてコードコメント上で図示し、既存の
  6〜12月退職の波2(こちらもY+1年6月開始)と混同しないよう注意喚起する社内的なチェックが
  望ましい(一次情報の再調査ではなく、実装レビュー上の注意点)。

## 6. 影響範囲の補足(コード確認で判明した追加事実)

- `ResidentTaxTimingComparisonTable.tsx`の「3月」行も本バグの影響を受けている(1章参照)。
  修正時はMATRIX・NEXT_YEAR_TOTAL以外に、比較表の期待値(現状ハードコードされていないが、
  同関数を経由するため実行結果が変わる)も再確認が必要になる。
- `calcCurrentYearTax()`(波1)は本バグの影響を受けていない(退職月による分岐は既に正しく
  実装されている)。修正対象は`calcNextYearTax()`のみ。
- `assumptionNotes`のうち「退職翌年6月からの新規課税は、自己納付(普通徴収)を前提に
  試算しています」(`postRetirementIncome > 0`の場合に追加される注記)も、案A実装時は
  1〜5月退職では`postRetirementIncome`を波2の計算に使わなくなるため、この注記の発火条件
  (現状は`postRetirementIncome > 0`のみで判定)を退職月で分岐させる必要がある
  (1〜5月退職時は、`postRetirementIncome`が入力されていても波2には無関係になるため、
  この注記を出すべきではない)。
