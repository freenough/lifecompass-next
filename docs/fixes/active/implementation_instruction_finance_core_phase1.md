# 実装指示書:フェーズ1 finance-core(積立額逆算エンジン)+ 検証スクリプト

## 背景

積立額逆算ツール(`/asset-simulator/tools/monthly-investment`、Product Spec:
`product_spec_monthly_investment_tool.md`参照)向けの計算エンジンを実装する。

調査(`finance_core_investigation.md`)の結論(案C)に基づき、以下の方針で進める:

- `simulate.ts`/`analyze.ts`は**無変更**(既存の変更禁止ルールを継続)
- 新規ファイル`financeCore.ts`に、積立の複利計算を「年金終価(ordinary annuity)の
  閉じた式」として独立実装する
- `simulate.ts`本体との数値的な整合性を、新規の検証スクリプトで継続的に確認できる
  仕組みを用意する(コードを共有するのではなく、数値を突き合わせて検証する)

本フェーズのスコープは**エンジンと検証スクリプトのみ**。UIの実装は含まない
(次フェーズで別途指示する)。

## スコープ

### 実装するもの

1. `src/lib/financeCore.ts`(新規ファイル)
2. `scripts/verify-finance-core.js`(新規ファイル、既存`scripts/full-verify.js`は無変更)

### 実装しないもの(スコープ外)

- UIコンポーネント
- 「何年(何歳)で目標に到達するか」を求める関数(第2弾ツール用、今回は実装しない)
- `simulate.ts`/`analyze.ts`/`types.ts`への変更

---

## 1. `financeCore.ts`の要件

### 1-1. 実装する関数

Product Spec(v1スコープ)に対応する、以下1関数のみを実装する。関数名は
`calcRequiredMonthlyContribution`とし、既存コードベースの命名規則
(`calcMu`・`calcPortfolioMetrics`・`calcIdecoEligibleAge`・`calcMortgage`・
`calcPensionTaxDiff`・`calcAggregatedSigma`)にならって`calc`プレフィックスで
統一すること(`calculate...`のような別プレフィックスにしないこと):

```ts
/**
 * 目標資産に到達するために必要な毎月積立額を計算する。
 * 年金終価(ordinary annuity)の閉じた式に基づく。
 *
 * @param currentAssets 現在の資産額(万円)
 * @param targetAssets  目標資産額(万円)
 * @param years         積立期間(年)。呼び出し側で `目標達成年齢 - 現在の年齢` を渡す
 *                      (UI/Controller層で年齢差から算出したものを渡す想定であり、
 *                      本関数自体は年齢を扱わない)
 * @param annualRatePct 想定利回り(年率%、例: 5 は年率5%)
 * @returns 必要な毎月積立額(万円/月)。`years`が0以下など計算そのものが成立しない
 *          場合は`null`を返す。`currentAssets >= targetAssets`(既に目標達成済み)
 *          の場合は「積立不要」という正常値として`0`を返す。
 *          `null`と`0`を呼び出し側で明確に区別できるようにするため、戻り値の型は
 *          必ず `number | null` とし、`undefined`は使わないこと。
 */
export function calcRequiredMonthlyContribution(
  currentAssets: number,
  targetAssets: number,
  years: number,
  annualRatePct: number
): number | null
```

### 1-2. 計算式の根拠

`simulate.ts`の積立期ロジック(口座残高の複利成長+年末積立加算)が表す漸化式は、
数学的に年金終価の閉じた式と一致する(調査報告で確認済み)。この式に基づき、
目標資産・現在資産・年数・利回りから毎月積立額を代数的に解いて実装すること。

- **年末積立方式であることに注意する**(`CLAUDE.md`記載の前提と合わせる。積立は
  各年末に発生するという前提で式を立てる)
- 利回りが0%(またはそれに近い)場合のゼロ除算を必ず考慮し、0%のケースでは
  単純な線形計算(target - current) / years / 12 にフォールバックすること
- `years`が0以下など、**計算そのものが成立しない入力に対しては、必ず`null`を
  返すこと**(例外を投げない)
- 一方、`currentAssets >= targetAssets`(既に目標に到達している)場合は、
  「積立不要」という**正常なケース**であり、この場合は`0`を返すこと
- **`0`(積立不要という正常値)と`null`(計算不能)を明確に区別し、戻り値の型は
  `number | null`に固定する。`undefined`は使わないこと。**

### 1-3. 単位の一貫性

`financeCore.ts`内では、Product Spec通り「万円」「万円/月」「年率%」の単位で
統一する。`simulate.ts`側の内部単位(既存コードの単位系)と混同しないよう、
関数のJSDocに単位を明記すること。

### 1-4. テストしやすさ

`financeCore.ts`は`simulate.ts`や`SimParams`型に一切依存しない、純粋関数として
実装すること(入力→出力が決定的で、副作用を持たない)。

### 1-5. 非機能要件

`financeCore.ts`は将来Next.js以外の環境(Node CLIスクリプト、将来的なAPI化等)
からも呼ばれる可能性を見据え、以下を満たすこと:

- **純粋関数であること**(副作用を持たない、1-4と重複するが改めて明記)
- **環境非依存**:Node・ブラウザのどちらでも動作すること(DOM API・Node固有API
  に依存しない)
- **外部ライブラリへの依存を追加しないこと**(標準のMath関数のみで完結させる)
- **ESM形式でエクスポートすること**(既存コードのモジュール形式に合わせる)
- **計算時間は1ms未満を目安とする**(閉じた式のためループを伴わず、通常は
  問題にならないはずだが、念のため明記する)

## 2. `scripts/verify-finance-core.js`の要件

### 2-1. 目的

`financeCore.ts`の計算結果が、`simulate.ts`(本番エンジン)を「積立期のみ・
他ロジックが一切発火しない条件」で動かした場合の結果と整合しているかを、
複数の代表的な入力パターンで確認する。既存の`full-verify.js`と同様、
Claude Codeが「完了」と報告する前に必ず自分で実行し、結果を貼ること。

### 2-2. simulate()呼び出し用のダミープロファイル設計(重要)

調査報告で特定された通り、`simulate()`を「積立の複利計算のみ」が発火する形で
動かすには、以下の設定が必要:

| フィールド | 設定値 | 理由 |
|---|---|---|
| `curAge` | テストケースの現在年齢 | |
| `retAge` | `curAge + years + 50`程度、十分先に設定 | 検証対象の期間中に取崩期へ切り替わらないようにするため |
| `lifeEx` | `retAge`よりさらに先に設定 | シミュレーション自体が`years`年分より前に終了しないようにするため |
| `acct.nisa.bal` | テストケースの現在資産 | |
| `acct.nisa.con` | 検証したい積立額(万円/年、`financeCore.ts`の月額×12) | |
| `acct.nisa.rW` | テストケースの想定利回り | |
| `baseInc`/`baseExp` | 積立が満額実行されるよう、収支が積立額を十分賄える値に設定(例:`baseInc`を積立額+生活費より大きく、`baseExp`を小さく) | 収支不足による按分取り崩しロジックが発火するのを防ぐため |
| `hasIdeco` | `false` | iDeCo関連ロジックを無効化 |
| `idecoStartAge` | `retAge`より確実に後の値(例: `retAge + 100`)を明示的に設定 | `hasIdeco=false`でも参照されうるため、発火しない値を保険として入れておく(調査報告の注意点) |
| `acct.ideco.*` / `acct.tax.*` | すべて0 | |
| `acct.cash` | 0 | |
| `sevYrs` | 0 | 退職金ロジックを実質無効化 |
| `spouse` | `null` | 配偶者ロジックを無効化 |
| `events` | `[]` | ライフイベントを無効化 |

このダミープロファインの構築ロジックは、検証スクリプト内に
`buildDummyProfileForVerification(currentAssets, monthlyContribution, years, ratePct)`
のような専用ヘルパー関数としてまとめ、テストケースごとに使い回せるようにすること。

### 2-3. テストケース

最低限、以下の組み合わせを検証すること(Product Specの初期値・早見表のレンジを
カバーする):

1. 現在資産0万円・積立額7.2万円/月・利回り5%・20年
2. 現在資産100万円・積立額5万円/月・利回り3%・15年
3. 現在資産500万円・積立額10万円/月・利回り7%・10年
4. 利回り0%のケース(ゼロ除算フォールバックの検証)
5. 積立期間1年のみの短期ケース(境界値の確認)

### 2-3-1. ランダムケースによる追加検証(100件程度)

上記の代表ケースに加えて、以下のレンジでランダムに生成した100件程度のケースも
検証すること。境界値の見落としは手動で書いたケースだけでは潰しきれないため、
`financeCore.ts`のような数学的な純粋関数とはランダム検証の相性が良い。

- 現在資産:0〜5,000万円
- 利回り:年率0〜10%
- 積立期間:1〜40年

各ケースについて2-4の許容誤差の範囲内でPASSすることを確認し、FAILしたケースが
あれば、その具体的な入力値(再現可能な形)を報告に含めること。

各ケースについて、`financeCore.ts`側は「必要積立額」を求める関数だが、検証では
逆に「その積立額を`simulate()`に渡した場合の`years`年後の資産額」を`simulate()`
側で計算し、`financeCore.ts`が想定する目標資産額と比較する形にすること(関数の
向きが違うため、検証スクリプト内で適切に変換すること)。

### 2-4. 丸め誤差への対応(重要、必ず確認すること)

`simulate.ts`は年次スナップショット保存時に口座残高を`Math.round()`している
(既存資料に記載あり)。**この丸めが、次のイテレーションで使われる実際の状態変数
に対して行われているのか、それとも表示用スナップショットのみに行われているのか
を、`simulate.ts`を実際に読んで確認すること。**

- 表示用のみの丸めであれば、`financeCore.ts`(丸めなしの連続計算)とほぼ完全に
  一致するはずなので、許容誤差は小さく(例:1万円未満)設定してよい
- 状態変数自体が毎年丸められている場合、年数が長いテストケースほど誤差が
  累積する可能性があるため、許容誤差を年数に応じて緩める(例:
  `年数 × 0.1万円`程度を上限とする、など)必要がある。この場合、許容誤差の
  根拠をスクリプト内のコメントに明記すること

いずれの場合も、**「完全一致」を検証条件にしないこと**。妥当な許容誤差の範囲内で
一致することを確認する形にし、許容誤差の数値と根拠を必ずコメントで残すこと。

### 2-5. 出力形式

各テストケースについて、以下を標準出力に表示すること:

```
[ケース1] 現在資産0万円・積立7.2万円/月・利回り5%・20年
  financeCoreの想定目標資産: 3000万円
  simulate()実測資産(20年後): XXXX万円
  差分: XX万円(許容誤差: XX万円) → PASS/FAIL
```

全ケースPASSの場合のみ「検証成功」、1つでもFAILがあれば「検証失敗」と
明確に表示すること。

## 3. 完了報告の形式

- `financeCore.ts`の実装内容(関数シグネチャ、計算式の要点)
- `verify-finance-core.js`の実行結果(全ケースの数値・PASS/FAIL)
- 丸め誤差の調査結果(2-4で確認した内容)と、採用した許容誤差の根拠
- `full-verify.js`が引き続きPASSすることの確認(既存機能に影響がないことの確認)
- 関数名・ファイル名で報告すること(行番号ではなく)

**繰り返しになるが、`simulate.ts`/`analyze.ts`/`types.ts`への変更は一切行わない
こと。** もし実装を進める中でこれらの変更が必要だと感じた場合は、変更せずに
その旨を報告し、KENZOの判断を仰ぐこと。
