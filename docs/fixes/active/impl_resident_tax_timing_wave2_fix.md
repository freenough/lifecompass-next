# 実装指示:1〜5月退職時の「波2」所得基準の修正(案A、バグ修正のみ・波3の追加表示は含めない)

## 背景
`investigation_wave2_1to5gatsu_taisho_report.md`で確認された不具合の修正。
`calcNextYearTax()`が退職月によらず常に「退職年の部分所得を月割り推計」する式を使っていたため、
1〜5月退職のユーザーに対して、本来最優先で表示すべき「前年まるまる1年分を基準にした、
最も近く・最も金額の大きい新規課税」が一切計算・表示されていなかった
(600万円・5月退職の例で、本来307,800円のところ90,000円しか表示されていなかった)。

**本指示は案A(バグ修正)のみを対象とする。案B(波3の追加表示)は実装しないこと。**

## 修正内容

### 1. `calcNextYearTax()` の分岐追加
- `retirementMonth <= 5` かどうかで分岐すること:
  - **6〜12月退職(現状維持)**:`estimatedRetirementYearIncome = priorYearIncome/12×retirementMonth
    + postRetirementIncome`、`incomeYear = retirementYear`(退職年)。既存ロジックを一切変更しないこと
  - **1〜5月退職(新規)**:`priorYearIncome`をそのまま使用(月割りしない)。
    `postRetirementIncome`は**加算しないこと**(前年の所得には含まれないため)。
    `incomeYear = retirementYear - 1`(波1側の`calcCurrentYearTax()`が使っている年の算出方法を
    参考に、1年進めた値にすること)
- 年間税額の算出には、波1側で既に使われている`calcAnnualResidentTax()`(またはそれに相当する
  共通ヘルパー)をそのまま呼び出すこと。**新しい計算ロジックを重複実装しないこと**
  (`calcCurrentYearTax()`の6〜12月分岐が行っているフル12ヶ月分の計算とほぼ同じ形になるはず)

### 2. UI文言の出し分け(`ResidentTaxTimingResult.tsx`)
- セクション見出し「② 退職した年の所得をもとにした、翌年6月からの新しい住民税」を、
  退職月に応じて動的に変更すること:
  - 6〜12月退職:現状の文言のまま
  - 1〜5月退職:「② 退職前年の所得をもとにした、今年6月からの新しい住民税」のような、
    実態(基準年=前年、開始時期=今年6月)に合った文言に変更すること
- `assumptionNotes`のうち「退職前の給与は前年の年収を月割りした仮定値です。賞与の時期により
  実際の所得とは差が生じます。」は、1〜5月退職では月割りをしなくなるため、この注記を
  出さないようにする(または「前年の年収をそのまま使用しています」のような文言に差し替える)こと
- `assumptionNotes`のうち「退職翌年6月からの新規課税は、自己納付(普通徴収)を前提に
  試算しています」(`postRetirementIncome > 0`の場合に追加される注記)は、1〜5月退職では
  `postRetirementIncome`が波2の計算に使われなくなるため、**発火条件に`retirementMonth >= 6`を
  追加**し、1〜5月退職では表示しないようにすること

### 3. 比較表(`ResidentTaxTimingComparisonTable.tsx`)への影響確認
- 比較表は`calcResidentTaxTiming()`を内部で呼んでいるため、上記の修正により「3月」行の数値は
  自動的に正しい値に変わるはずである。これを確認すること
- ただし、キャプションまたは列見出し「翌年6月〜」が、1〜5月退職の行では実態(今年6月〜)と
  合わなくなる。この列見出し・キャプションについても、退職月グループに応じた注記や、
  「①②とも、退職月によって開始時期が異なります」といった一般的な注記への変更を検討し、
  実装すること

## 検証要件
- 報告書の試算例(退職前年年収600万円・5月退職)で、②が307,800円(所得割302,800円+均等割5,000円)
  になることを確認すること
- 6〜12月退職のケースについて、既存のテストケース(9月・12月のMATRIX行、比較表の6月・9月・12月列)
  が**期待値を一切変更せずに**すべてPASSし続けることを確認すること
  (1件でも変わってしまえば、分岐の実装ミスを意味するため、報告書の指摘通り厳密にチェックすること)
- `scripts/verify-resident-tax-timing-tool.js`のMATRIX・NEXT_YEAR_TOTALのうち、
  `retirementMonth`が1〜5のケース(1月・5月)を、修正後の正しい値に全面的に再計算すること
- `postRetirementIncome > 0`かつ1〜5月退職のケースで、波2の計算に`postRetirementIncome`が
  一切反映されないこと(意図的に無視されること)を検証項目として追加すること
- `full-verify.js`全PASS・`tsc --noEmit`エラーなしを確認すること
- 完了報告書に、修正前後の`totalCashNeeded`の変化(1月・5月退職の代表パターンについて、
  約3倍規模の増額になるはず)を明記し、これが意図した修正であることを説明すること
