## 背景：前回調査の何が誤っていたか

前回、「重複行のうち2行目の金額欄が空欄」という**仮定のケース**を作って再現し、「0万円になる原因が分かった」と報告した。しかし、KENZOが実際に使ったCSV（本指示書に添付、以下「実ファイル」）を確認すると、重複行は**両方とも同じ500万円**であり、空欄の行は存在しない。さらにKENZOによれば、**重複を除いた（各月1行にした）CSVでも、9月分の500万円は反映されない**。前回の「9件のスナップショットが正しく保存されることを確認した」という再現結果も、実際のスクリーンショットでは2026-09の1件（しかも0万円）しか表示されておらず、一致していない。

**つまり前回の調査は、実態を再現できていないまま「原因が分かった」と誤って報告したことになる。** 今回は、推測でケースを組み立てることを禁止し、以下の実ファイルをそのまま使って、実際のブラウザ操作で何が起きるかを一から確認すること。

## 【重要な前提の追加】ID列が空欄であることは異常なケースではない

新規にCSVを作成してアップロードする場合、ユーザーは内部IDを知りようがないため、**ID列が空欄になるのはむしろ最も基本的・標準的な使い方**である。「実績をCSVで過去分含めて登録できる」という、この機能の根幹の用途そのものが、この空欄IDのケースにあたる。エッジケースではなく、正面から対応すべき主要な入力パターンとして扱うこと。

**正しい挙動（自明のため、これは仕様として確定する）**：ID列が空欄の行は、それぞれ独立した新規行として扱い、インポート処理側で行ごとに新しいIDを発行すること。空欄同士を「同一のID」とみなして統合・上書きし合う実装になっている場合、それは明確な設計ミスであり、**調査1でこれが原因と特定できた場合、今回に限り、その場で修正してよい**（本指示書冒頭の「修正は一切行わない」を、この項目に限り解除する）。修正する場合は、CSVインポート全体・既存の他の年月グループ・既存のIDを持つ行の扱いに影響が出ないよう、変更範囲を空欄ID行の新規ID発行ロジックに限定すること。

## 調査1：ID列が空欄であることの影響（最有力の仮説）

**確認したいこと**
- インポート処理（`rowToHolding()`・`mergeById()`・`applyGroupsToStore()`等）が、ID列を実際にどう扱っているかを正確に読む
- ID列が空欄の行が複数ある場合、それらが「別々の行」として扱われるのか、「同一のID（空文字列）を持つ1つの行」として扱われ、後続の行で上書きされてしまうのかを特定する
- 特に、**この「同一視」が年月グループの範囲内で閉じているのか、それとも年月をまたいで全行に対してグローバルに行われているのか**を確認する（後者であれば、月をまたいで行が誤って統合され、最終的に1件しか残らないことの説明になる）

**対象ファイル**
- `src/lib/assetManagement/csvHistory.ts`・`exportImport.ts`（該当するインポート処理一式）

**報告フォーマット**
- ID空欄行の扱いを実装コードで正確に示す
- 年月グループ内で閉じているかグローバルかを明記

## 調査2：実ファイルでの厳密な再現（推測を挟まない）

**手順**
1. 安全なテストデータで、まず「現在のプロファイル」の状態を確認・記録する（保有資産・スナップショット履歴、いずれも空の状態から始めること）
2. 上記の実ファイルの内容を**一字一句そのまま**CSVとしてインポートする
3. インポート直後の状態を、以下すべてについて記録する：
   - `localStorage`の生データ（`lifeCompassAssetHoldings`・`lifeCompassAssetSnapshots`等、関連キーすべて）をそのまま貼り付ける
   - 画面上の「保有資産」の表示（合計・カテゴリ別）
   - 画面上の「資産推移」の表示（記録日一覧が何件、それぞれ何万円か）
4. 前回の報告（「①現在PFは今月分の行だけで総入れ替え」「スナップショットは9件正しく保存される」）と、実際の結果が一致するかどうかを明記する。一致しない場合、前回の報告のどの部分が誤っていたかを具体的に指摘すること

**報告フォーマット**
- 上記1〜4の結果をそのまま報告する。解釈・原因の考察は調査1・3に譲り、ここでは事実（何が起きたか）のみを正確に報告すること

## 調査3：アクティブなプロファイルとインポート先の`profileId`の整合性

**背景**：前回、「CSVインポートは`profileId`を常に`'default'`固定で書き込むため、アクティブなプロファイルが`default`以外だと表示から漏れる」という仮説を提示した。KENZOの実際の画面では現在のプロファイル名が「デフォルト１」と表示されている。

**確認したいこと**
- 「デフォルト１」という名前のプロファイルの、実際の内部`id`（`profileId`として使われる値）が`'default'`固定文字列と一致するのか、それとも別の値（例：UUID、タイムスタンプ等）が振られているのかを確認する
- CSVインポートが書き込む`profileId`の値（前回報告では`'default'`固定とされていた）と、現在アクティブなプロファイルの`id`を実際に突き合わせ、一致するかどうかを明記する
- 不一致であれば、これが調査2で再現した表示されない症状の原因になっているかどうかを確認する

**報告フォーマット**
- 「デフォルト１」プロファイルの実際の`id`値
- CSVインポートが書き込む`profileId`の実際の値
- 両者が一致するかどうか、一致しない場合はそれが表示欠落の原因として説明がつくかどうか
