このファイルにある数値は、旧HTML版（STEP35まで）のシミュレーターから実際にCSV出力して確認済みの値、または
SIMULATION_GUIDE.mdに記録された確定値です。Next.js版の計算結果がこれと一致するかどうかが、

## 検証用ロジック（参考：旧版の簡易検証スクリプト）

固定利回りシナリオの3つのFIRE定義（最低限・最速・安心）を計算する参考ロジック。
実際の移植先エンジンはこれと同じ結果を返す必要がある。

```javascript
function getThreeDefinitions(p) {
  const needed = p.baseExp * 25;
  let def1 = null, def2 = null, def3 = null;

  for (let retAge = p.curAge + 1; retAge <= 80; retAge++) {
    let nisa = p.nisaBal, cash = p.cashBal;
    for (let age = p.curAge; age < retAge; age++) {
      nisa += nisa * (p.rW / 100);
      const avail = p.baseInc - p.baseExp;
      const con = Math.min(p.nisaCon, Math.max(0, avail + cash));
      nisa += con; cash += avail - con;
      nisa = Math.max(0, nisa); cash = Math.max(0, cash);
    }

    const retTotal = Math.round(nisa + cash);
    if (!def1 && retTotal >= needed) def1 = retAge;

    let nisa2 = nisa, cash2 = cash;
    let survived90 = true, neverBelow = true;
    for (let age = retAge; age <= 90; age++) {
      nisa2 += nisa2 * (p.rR / 100);
      const pension = age >= p.penAge ? p.penInc : 0;
      const netExp = p.baseExp - pension;
      const total2 = nisa2 + cash2;
      if (total2 <= 0) { survived90 = false; neverBelow = false; break; }
      const ratio = nisa2 / total2;
      const draw = Math.min(netExp, total2);
      nisa2 -= draw * ratio;
      cash2 -= draw * (1 - ratio);
      nisa2 = Math.max(0, nisa2); cash2 = Math.max(0, cash2);
      const t = Math.round(nisa2 + cash2);
      if (t <= 0) survived90 = false;
      if (t < needed) neverBelow = false;
    }
    if (!def2 && survived90) def2 = retAge;
    if (!def3 && neverBelow) def3 = retAge;
    if (def1 && def2 && def3) break;
  }
  return { def1, def2, def3 };
}
```

### 旧・合算口座版フィクスチャとの乖離について
口座分割版は上記「中村夫婦シリーズ（確定・厳密検証可能）」の合算口座版フィクスチャとは
一致しない（56歳までは一致するが58歳以降で乖離が生じる）。原因は積立の再配分：
合算版はNISAへ180万/年を集中投資していたが、分割版はNISA生涯枠内に収めるため
NISA70万＋特定口座35万（翔太）＋NISA75万（美咲）に再配分した（合計180万/年で総投資額は同じ）。
特定口座への新規積立により取崩期の含み益課税対象残高が増え、比例取崩時の課税負担が増加する分、
高齢になるほど資産が目減りする——という一貫した説明がつく差異でありバグではない。

### 重要な実装上の注意（口座分割版で判明）
- `retAge`を延長するシナリオでは、`cNisaTo`/`cIdecoTo`/`cTaxTo`も同じ年齢まで延長しないと、
  `simulate()`内の`nisaActive = !isRet && age <= toAge`により意図した年齢まで積立が続かない
  （旧`toAge`のままだと、退職年齢だけ延ばしても積立は旧年齢で止まってしまう）。
- プロファイルの`spSevYrs`（配偶者の勤続年数、退職所得控除の計算に使う）を実態に合わせて
  正しく設定すること。`0`のままだと退職所得控除がほぼ効かず、配偶者の退職金の大部分が課税され、
  それ以降複利で乖離が拡大していく（`spSevYrs: 0→13`の修正で実機と完全一致した実例あり）。
- 同一イベント・同一パラメータの複数の出力箇所（例：第9話ステップ2／第10話／ブログシナリオA）は、
  MCを箇所ごとに別実行しない。乱数試行が変わるだけで数%ずれた値になるため、1回の実行結果を
  共有すること。

## 繰上返済（単発）フィクスチャ（2026-08-06追加・本番関数実測）

新ツール企画（繰上返済 vs 投資比較ツール、第8弾候補）の事前実装として、`simulate.ts`の住宅ローン計算に
繰上返済（単発・期間短縮型/返済額軽減型）対応を追加した際の確定値。`src/lib/helpers.ts`の
`calcMortgage`/`calcMortgageBalance`/`calcMortgageTermFromPayment`と`simulate()`を実際に呼び出して算出
（独自再現スクリプトなし）。`scripts/full-verify.js`の「【繰上返済(単発)】」セクションに同一のケースを
回帰チェックとして組み込み済み。

### 前提
- 元本4,100万円・金利1%・返済期間30年・開始年齢30歳（`calcMortgage(4100,1,30)`=158.25万円/年、
  `calcMortgageMonthly(4100,1,30)`=13.2万円/月）
- 37歳時点（経過7年）で500万円を単発繰上返済
- `calcMortgageBalance(4100,1,30,7)` = 3,250.23万円（繰上返済前の残高）
- 繰上返済後の新元本 = 3,250.23 − 500 = 2,750.23万円

### 一括支出の計上（2026-08-06追加）
繰上返済額そのもの（手元資金からの一括支出）は、繰上返済年（`prepayAge`の年）に一時支出として
`extraExp`に計上される（`simulate.ts`の`hasPrepay`ブロック内、`age === expEv.prepayAge`のとき
`extraExp += expEv.prepayAmount!`）。将来の返済負担軽減という「メリット」と対になる「コスト」であり、
繰上返済年のexpenseには常に`（その年の返済額）+ (繰上返済額)`が計上される。以下の全ケースでこの
一括支出込みの値になっている（この計上漏れは2026-08-06にバグとして発見・修正された。修正前は
繰上返済額がいくらであっても繰上返済年のexpenseに変化がなく、「将来の返済負担軽減のメリットだけが
反映され、そのための手元資金を使うコストが一切反映されていない」状態だった）。

### 完済境界年の按分処理（2026-08-06実装）
期間短縮型の完済年齢は連続値（例:56.08歳）で算出されるが、`simulate.ts`の年次ループは整数年齢でしか
判定できない。按分処理導入前は「境界年の返済額が丸ごと発生する/しない」の二択（`age < endAge`）だった
ため、`endAge`の小数部分が0.5未満のケースで「試算表示は完済年齢が1年短縮と出るのに、実際のシミュレー
ションには一切反映されない」という表示とシミュレーションのズレが生じていた
（`docs/fixes/done/investigation_mortgage_shorten_display_mismatch.md`参照）。

按分処理導入後は、完済境界年（`boundaryAge = Math.floor(endAge)`）のみ返済額を端数比率
（`fraction = endAge - boundaryAge`）で按分計上する（`docs/fixes/done/investigation_mortgage_proration_feasibility.md`
の実現可能性調査に基づく）。`endAge`が整数の場合（繰上返済なし・返済額軽減型）は`fraction = 0`となり、
従来通り境界年の追加計上なし（後方互換）。この結果、モーダルの試算表示と実際のシミュレーション結果は
金額ベースで整合するようになったため、表示側の丸め方式（`Math.round`→`Math.ceil`）の修正は不要と判断し、
実装していない。

`simulate()`側は「期間短縮効果なし」として従来の終了年齢のまま計算を続ける（例外を投げない）。

**注**: `simulate()`の`prepayType: 'shorten'`パスは、月々返済額を常に同一ローンの
`calcMortgageMonthly(principal, rate, termYears)`（＝そのローン自身の当初返済額）から導出するため、
自己無矛盾な入力である限りこの解なしケースには到達しない（当初返済額は定義上、当初のより大きい残高の
利息を上回るため、繰上返済後のより小さい残高に対しても常に利息を上回る）。上記のバリデーションは
`calcMortgageTermFromPayment`を独立した関数として直接呼び出した場合の防御的な挙動確認であり、
現行の`simulate()`統合経路からは通常到達しない。
